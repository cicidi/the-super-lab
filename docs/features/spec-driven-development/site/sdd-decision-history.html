Evidence Appendix

ARD-A — Authority by concern replaces a single global source of truth

The previous rule was "code is the source of truth", stated in three places in doc-organize. It resolves every conflict in one direction and leaves a spec unable to protect intended behavior: under it, a spec that states a retry count of 3 while the code retries 5 is simply wrong, even when 3 was the requirement.

Considered and rejected:

  • *Keep "code is the source of truth"* — rejected because it makes the spec

unenforceable precisely where enforcement matters, and because a passing test would then also count as a requirement.

  • *Declare "spec is the source of truth"* — rejected for the mirror reason: a

spec cannot answer what the code currently does, and treating it as authoritative for implementation would force spec edits for every refactor.

  • *Single source with an exception list* — rejected as an unmaintainable middle

ground that still names one winner by default.

Adopted instead: authority by concern. Intended behavior belongs to the spec, current implementation to the code, contracts to the machine-readable artifact, database structure to migrations, and executable verification to the tests.

ARD-B — The standard lives in doc-organize, not a new skill

Placement, linting, and consolidation already belong to doc-organize, and its Sync mode is where drift is detected. A separate skill would have to duplicate the document standard to know what a spec is.

Considered and rejected: a new spec-driven-development skill with doc-organize keeping only a pointer. Rejected because the two would share the type list, the frontmatter contract, and the required sections, and the copy would drift.

ARD-C — Detail is carried in sibling files, not inline in SKILL.md

The material is seventeen sections. Inline it would have taken SKILL.md past 700 lines, and a skill that must be read in one pass cannot afford that.

Follows the existing pattern: domain-modeling/ADR-FORMAT.md and domain-modeling/CONTEXT-FORMAT.md. Sibling files travel with the directory, so the skill stays portable — it must not point at this repository's docs/, which does not exist in the projects the skill is deployed to.

ARD-D — The health field is named health, not status

state already tracks the authoring state (draft or final). A second field named status would be read as the same concept, and it accepted an overlapping vocabulary (draft, active, stale, deprecated) that made the overlap worse.

Considered and rejected: replacing state's vocabulary with draft | active | stale | deprecated. Rejected because it would invalidate every existing document to gain a distinction that a second field provides for free.

ARD-E — design and impl-plan cap at 1,000 lines; decision-history is exempt

The earlier guideline said feature specs run 500-1,500 lines, which contradicts a 1,000-line ceiling. The ceiling wins; the guideline is removed.

decision-history is exempt because it is append-only history. Trimming it would destroy the record that is its entire purpose. Exempting it also means the cap never creates pressure to delete a superseded decision.

ARD-F — A feature folder may hold more than one design or impl-plan

Supersedes the earlier rule "one file per type per feature" for these two types only, and removes the anti-pattern that forbade a second spec file.

prd, test-plan, decision-history, and how-to stay single-file: none of them grows without bound. design and impl-plan do, and capping them at 1,000 lines without allowing a second file would have made the cap unmeetable.

ARD-G — Spec parts take an aspect noun, plan parts take a number plus phase

payment-design-authorization.md        aspect noun, unordered
payment-impl-plan-01-schema.md       number plus phase, ordered

Considered and rejected: numbering both (payment-design-01.md). A number says nothing about the contents, and inserting a part forces a renumber across the set. A plan is genuinely ordered, so a number carries meaning there; a spec is cut by bounded context, so a noun carries meaning there.

ARD-H — Four content priority levels; L1 is never deleted

L1 decisive (behavior, contracts, invariants, constraints, error semantics, security rules, architecture boundaries, out of scope, assumptions, compatibility constraints, open questions), L2 rationale, L3 alternatives, L4 support. Trim L4, then L3, then compress L2. Never delete L1.

out of scope, assumptions, compatibility constraints, and open questions are filed at L1 rather than L2 because dropping any of them breaks the implementation in the same way as dropping a stated requirement.

A fact whose authoritative home is another document is L4 as a link, never a restated copy. This connects the level model to the duplication rule: restating a fact is a defect, not a level.

ARD-I — This feature carries two spec documents

Deliberate exception to decision ARD-F's one-spec-per-feature default, recorded here because the rule requires a logged reason rather than a silent breach.

This feature is named for the standard itself, so the standard's own spec belongs to it. wayfinder-import-design.md already occupied spec-driven-development/design/, and the wayfinder import is a distinct effort with its own lifecycle.

Considered and rejected:

  • *Rename the feature* — rejected because the initiative name is established in

the project's working context.

  • *Put the standard's spec in its own feature* — rejected because the standard

and the import are the same initiative; splitting them into two features would misrepresent the work.

  • *Fold the standard into wayfinder-import-design.md* — rejected as a

restatement: two unrelated documents in one file.

The two files are distinguished by name, following decision ARD-G's aspect rule: spec-driven-development-design.md for the standard, wayfinder-import-design.md for the import.

ARD-J — Five stages plus an optional how-to

The PRD said six artifacts; pipeline-design.md and the document standard said five. The pipeline spec is right about stages: how-to is an output for the case where a human must operate the result, not a step every feature runs.

Considered and rejected: keeping six to match the PRD — rejected because it invents a stage most features never execute.

ARD-K — Every AI edit to a docs file is small

A large edit lands unreviewed and is hard to attribute when it breaks something. The limit is 10 lines or 200 characters; satisfying either is enough. A larger change is split into sequential edits. A restructure needs explicit human instruction, which is how this PRD's own revision was applied.

Considered and rejected: hard rejection of oversized edits — rejected because it blocks a legitimate restructure; warning only — rejected because nothing stops the edit.

ARD-L — Blind spots come from existing skills

research already has a Discover Unknowns branch and grill-with-docs already runs an adversarial interview. P4 says to use the current tools first.

Considered and rejected: a new dedicated skill — rejected while the existing mechanism works. A future skill may replace them without changing the requirement that the step runs.

ARD-Z — Five PRD fields, then design and decision history

Replaces the undefined six inputs in PIPE-E2. The PRD must state limitation, preference, timeline, resource, and tool. A missing one is marked not apply, not left blank. Downstream starts only after that PRD, the design, and the decision history all exist. Rejected: the word building, and a pointer at PIPE-F for a definition PIPE-F does not hold.

ARD-Y — Map split uses a 20-hour estimate

Provisional rule (PIPE-D item 6). AI shows several split options. One person able to understand the work within 20 hours stays one feature spec. AI estimates above 20 hours, so it splits into a peer or a sub-feature. AI both estimates and judges. Creating directories still waits for human confirmation (PIPE-D item 5).

ARD-X — Execution delivery is a mock MCP log

No live booking or trading. A mock MCP client calls a mock MCP server; the printed call log is success (PRD-O). Rejected: real side effects.

ARD-W — Readability judge is an undergraduate programmer

A second LLM plays a bachelor's-level programmer. Pass only if it understands; otherwise not delivery (PRD-M). ISO 24495-1 was found and not used as the score.

ARD-V — Hard problems stay on the same five artifacts

Shed, Beijing, a famous math problem, and a stock stay in this PRD (PRD-K) on the same five artifacts. Sub-problems name who acts; claims cite a found fact (PRD-L, PRD-N). Rejected: a new feature.

ARD-U — spec-pipeline orchestrator and Map/state model

SDD adds spec-pipeline as the entry skill that calls spec-organize and spec-write and prompts for spec-review before commit. Map relies on human interview; outputs (split, decision, scratch) are AI-judged, not a fixed file template. State lives in CLAUDE.local until feature create sets <f>, then in docs/features/<f>/raw/state/. Rejected: rigid Map MUST artifacts and repo-root BMAD-style state trees.

ARD-T — wayfinder-import is not an SDD sub-feature

Wayfinder import is a separate skill-factory / import effort, not part of the SDD deliverable (spec-organize, spec-review, spec-write). The nested tree under spec-driven-development/features/wayfinder-import/ is removed; wayfinder work continues elsewhere if needed. ARD-I's multi-spec exception remains historical.

ARD-O — Skills are spec-organize (main), spec-review, spec-write

Deliverable skills use the spec- prefix because they serve spec-driven development, not generic document editing. The standard file stays inside the main skill as SPEC-STANDARD.md, continuing ARD-B's placement rule. Rejected: a separate spec-standard skill — three consumers, one extra copy to drift.

ARD-P — spec-review detects mechanical MUST violations too

Review outputs modification suggestions, not fixes. Mechanical MUST gaps must appear in that list or the user gets an incomplete review. Organize Lint may fix; review detects and suggests. Rejected: semantic-only review — gold-based eval cannot score review against the same MUST set as organize.

ARD-Q — Tests live under skills/<skill>/tests/

Skills ship to arbitrary projects; tests must travel with them. Cross-skill checks, gold, and HTML reports live under spec-organize as the main skill. Rejected: repo-root tests/sdd/ — assets would not deploy with the skill bundle.

ARD-R — Two eval scores and gates

MUST compliance is a hard floor (x/total full pass). Exemplar comparison uses (plus−minus)×10/total and must not regress within one gold version. Rejected: a fixed exemplar cutoff — gold version bumps change the denominator.

ARD-S — Gold set grows and is versioned

New good and bad examples from runs append to annotations.yaml; gold.version increments. Scores compare only within one version. Rejected: frozen gold — no accumulation of review findings.

ARD-AA — Multi-participant decisions use the latest history entry, otherwise ask

PRD-F is closed. When two decisions conflict, the later entry in decision-history wins; if the order cannot be established, ask the user. The AI never guesses who is authoritative. Supersedes ARD-M.

ARD-AB — Four skills including spec-pipeline

The deliverable is four skills: spec-pipeline (orchestrator), spec-organize (standard/lint), spec-review (findings), spec-write (edits). Supersedes ARD-O, which listed three.

ARD-AC — PRD and document standard changes

PRD required sections drop Non-Functional Requirements; the parent PRD fills Overview, Goals and Success Metrics, User Stories, Functional Requirements, and Out of Scope. IDs are scoped to feature + type; cross-feature references use <feature>/<ID>. HLD architecture sections do not require DSGN IDs; how-to stays defined but unchecked.

ARD-AD — Eval uses deepseek-flash with 3 independent runs

Only the DeepSeek API is available, so gold generation and checker verdicts use three independent runs of deepseek-flash; cross-model bias is Unverified. Gold uses four terms: gold case, gold version, exemplar, annotations. runs/ and reports/ are not committed. The four non-software examples (shed, Beijing, math, stock) are skill-doc examples; their gold lives elsewhere. Supersedes the gold-example part of ARD-V.

ARD-AE — Non-software mapping, ownership, evidence, and UNKNOWN

Non-software problems use the same five artifacts: research in raw/research/, decisions in decision-history, execution in design/impl-plan, verification in test-plan. Each feature design carries a sub-question ownership table (AI查 / 人决定 / AI查完人决定); every claim cites a source; unknowns are marked UNKNOWN. Unverified items use Unverified: <reason> (<condition>).

ARD-AF — Deliberately undefined areas

Failure policy, skill/spec versioning, source-trust grading, and data cleanup are intentionally not defined. Existing non-compliant features are not migrated; only the SDD tree is fixed.

ARD-AG — Convergence is auto-decided

PIPE-E1–E3 are checked automatically; every open decision must carry a structured blocking flag. The AI does not self-declare the spec "stable": the automatic check passes only when no blocking item remains.

ARD-AH — Reader is the only HTML deliverable

spec-driven-development-reader.html is the human-readable deliverable. The legacy spec-driven-development.html summary is deleted; references point to the reader.

ARD-AI — This consolidation is an authorized restructure

The human explicitly authorized a one-shot consolidation of the SDD spec docs. Edits larger than the normal 10-line / 200-character cap are allowed for this batch; the normal cap resumes afterward.
