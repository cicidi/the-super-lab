PRD

Spec-Driven Development — PRD

Overview

本 PRD 定义 spec-driven development：用 PRD、decision-history、design 篇、impl-plan、test-plan 五篇，把有门槛的问题分析清楚，并交给四个 skill（spec-pipeline、spec-organize、spec-review、spec-write）执行。

Problem Statement

今天，AI 模型的能力已经非常强大。它们可以阅读、搜索最新、最前沿的技术，帮助我们解决问题。

但是，问题是什么？

1. Problem 经常没有被定义清楚，更何谈解决

比如这样一个问题：

嘿，AI，我买 iPhone 18 Duo 还是 iPhone 18 基础版？

看似是一个简单的问题，但实际上，我们并没有告诉 AI 我们的真实需求。

比如：我们买新的 iPhone 是用来做什么的？我们的 budget 是多少？我们之前是否一直使用 iPhone？我们喜欢 iPhone 的哪些优点，又有哪些缺点？

这些 context，AI 并不知道，因此 AI 的推荐肯定不会准确。

这正是很多人抱怨 AI 不好用的原因。事实上，对于我们自己来说，这看似是一个清楚的问题，但实际上，可能不是 AI 不好用，而是人没有把 problem 定义好。

2. AI 真正赋予我们的 superpower，是帮助我们发现 unknown

在我们把问题问清楚以后，AI 也提供了一些思路，甚至 solution。

但是，由于人的能力有限，我们可能根本没有见过某些解决方法或方案。

我们利用已知的信息，找到我们不知道自己知道的信息，同时学习我们知道自己不知道的知识，最后把我们不知道、甚至不知道自己不知道的 blind spot 发掘出来。

这才是 AI 真正赋予我们超能力的地方。

3. Decision 不断变化，AI 需要理解、记录并同步这些变化

经常，我们做了一段时间，或者和 team 里的其他人讨论后，会发现一些 decision 一直在改变。

比如：我们买 iPhone 的 budget，和父母、妻子商量未果。我们之前说买 iPhone 的 budget 是 2,000 美金，现在突然变成了 1,000 美金，那么 AI 整个 decision 的方向就会发生彻底的转变。

紧接着，一系列新的问题又会被引入：去哪里买？是不是能够接受二手 iPhone 18 Duo？

当然，随之而来的，去哪里买、如何找 deal 等具体实现方式都会发生改变。

今天的例子比较简单，以后可能会有更复杂的例子：多个人做出多个 decision，到底谁是真理？而这个真理，可能还需要 impact、覆盖其他一些之前的 decision。

比如：爸爸的 budget 是 1,800 美金，妈妈说 1,500 美金；爸爸说下个月可以买，妈妈说这个月可以买。

到底谁是真理？根据这个真理，我们又要如何修改之前的 decision？

这里真正的问题是：当多个参与者做出不同的 decision 时，AI 如何理解这些 decision 之间的关系，判断哪些 decision 是有效的，并根据最新的 decision 更新整个 decision-making process？

4. 即使 problem、solution、update、sync 都做好了，人依旧是整个 AI 世界最大的 bottleneck

首先是阅读。

怎么让文件好读、好懂？文件怎么好查找？如何清晰地知道每个文件是做什么的？如何做好 file management？

大的项目不可能只有一个 spec，那么如何切分 spec？如何让不同的 spec 之间保持清晰的关系？以后 AI 和人又该怎么读、怎么查找？

当项目越来越大，文件越来越多，spec 越来越复杂时，我们如何让人和 AI 都能够快速理解整个项目，并准确找到自己需要的信息？

这些都是 AI 真正落地到实际工作中，需要解决的问题。

5. 有门槛的难题不只在软件里

盖一个 shed、去北京旅游、看懂一道著名数学题、不靠猜地分析一只股票——人往往从没做过，不知道怎么拆、盲区在哪、哪些要自己拍板。

AI 要把大问题拆成小的：能查的 AI 自己查（合规、财报、交通），要选的人来选（预算、偏好、风险），人想不到的 AI 主动问。spec 既是学习笔记，也是决策记录，最后交给 AI 执行。

Goals and Success Metrics

  • 目标：任何有门槛的难题都能拆成可查、可决策、可执行的小问题。
  • 验收：四个 skill 的测试结果（test-plan）；这不是产品 success metric。
  • PRD-G 的产品级 success metric 与 baseline 仍 deferred（ARD-N）。

User Stories

  • 作为写 spec 的人，我希望先被 interview，把已知/未知/盲区问出来。
  • 作为 reviewer，我希望机械 MUST 和语义缺陷都能检出，且建议可执行。
  • 作为执行者，我希望 spec 能落到 design/impl-plan，并有 mock 执行与可追溯证据。

Solution

Spec-driven development

我们不重复什么是 spec-driven。这里要做的是开发一些 skill；这些 skill 会在一起工作，而不是单个 skill。这些 skill 的目标是：通过一组 skill，把具体问题分析清楚。

PRD、decision history、design 篇 是互相打磨的循环，不是只走一遍的直线；循环收敛到「够稳」后，impl plan 与 test plan 各自独立：都从 design 篇 总结出来，彼此不串行依赖。

  1. PRD — 我们到底要做什么、解决什么；当前的 limitation 是什么；preference 是什么；timeline、各种 resource、tool 都有什么。design 篇 或 decision 暴露缺口时，回到 PRD 改 requirement。
  2. Decision history — 基于 PRD 作出 decision；任何跟产品方向相关的 decision 先 update decision history（约 50% AI、50% 人）。新 decision 可能改 PRD 范围；spec 里的 trade-off 也可能要求补 decision。
  3. Design 篇 — 与 PRD、decision 并行迭代：写设计（技术方案、contract、tool 等；HLD/LLD 不在此展开）。设计问清 problem、或发现 decision 不够，回到 1/2 继续磨。
  4. Impl plan — 从 design 篇 总结实现：先做什么、后做什么；各个 task 的细节、准备工作等（不依赖 test plan 先写完）。
  5. Test plan — 从 design 篇 总结验证：任务完成标准、可用性检查、regression guard（不依赖 impl plan 先写完）。

Functional Requirements

PRD-A — 做一个 pipeline，基于现在现有的 pipeline 做一些改进。

PRD-B — 做一些 skill；这些 skill 其实就是优质 prompt，或其他 popular 的 prompt，引导 AI 怎么工作：完成 spec 的书写、命名、校验、更新。

PRD-C — 每次改动不超过 10 行 或 200 字符；超出拆多次，restructure 需 human 授权。

PRD-D — 文档大小限制在 1000 行；太大几乎没法 maintain。

PRD-E — 文档的文件组织架构、folder 关系。

Additional constraints:

PRD-F — 多人 decision 冲突时，以 decision history 里时间较晚的那条为准。看不出先后就问用户。AI 不猜测谁为准。

PRD-G — （open）产品级 success metric 与 baseline — deferred，见 ARD-N。test-plan 的分数是 eval 指标，不是产品 success metric。

PRD-H — Spec-driven development 的 workflow 尽量使用 popular skill，不要自己重新发明。

PRD-I — 修改需要验证；没有能验证的，都需要在 spec 里面标注上。标明后不作为 test plan 的通过条件。

PRD-J — 提供 spec-pipeline skill：凡写/改 feature spec 经 pipeline 进入；编排 spec-organize / spec-write，提交 committed 变更前询问 spec-review；支持 recap 与轻量 state（feature 确定前 CLAUDE.local，之后 docs/features/<f>/raw/state/）。

PRD-K — 范围不限软件：任何有门槛的难题走同一套 spec。例子四个：盖 shed（合规、成本、施工）、北京旅游（行程、住宿、风险、预算）、看懂著名数学题（零基础逐步学）、分析股票（基本面、财报、新闻，有理有据）。这轮不在本仓库建 gold，放到别处。

PRD-L — 每个子问题标明归属：AI 查、人决定、或 AI 查完后人决定。人没问到的盲区和风险，AI 必须主动提出。

PRD-M — 把人讲明白是硬需求。交付前由一个 LLM 打分：它假设自己是一个本科水平的程序员真人，只按能不能看懂来判；看不懂不算交付。测试验不了，不作为通过条件。

PRD-N — 正式 spec 的结论必须能追溯到查到的事实（合规条文、财报、新闻、定义），不靠猜；查不到的标成未知。评测时答案只能来自 context 包。

PRD-O — 执行不真下单、不订票。一个共用 mock MCP server，若干固定工具；client call 打出 log 即算交付成功。

PRD-P — 最终交付是这一系列 skill（spec-organize、spec-review、spec-write、spec-pipeline）。它们引导人写出的 spec，要满足 PRD-K 到 PRD-O。

PRD-Q — 书写、命名、校验、更新，以及 PRD-K 到 PRD-O，都是需求。四个 skill 不限于这几件事，以后的新题也要能做。skill 正文要写出四个例子：盖 shed、北京旅游、数学题、股票。好不好用只看测试。

Out of Scope

  • 真实下单、订票、交易；执行只到 mock MCP log。
  • 多人 decision 的仲裁细则；按 decision-history 时间，仍看不出则问用户。
  • 本仓库不建非软件四例的 gold；例子写进 skill 正文，gold 放到别处。
  • 存量不合规文档的批量迁移。
  • skill / spec 的版本与迁移策略。

Resources Needed

  • 四个 skill + 一份 test plan;无外部服务、无数据库。
  • 评测需 deepseek-flash API 与 3 次 run 的预算;runs/reports 不入库(ARD-AD)。

Implementation Decisions

4. AI 文档编辑约束（SDD 全 pipeline）

来源： parent PRD Requirements §3。

适用范围： agent 对 docs/ 内 Markdown（feature spec 各篇）的单次编辑。

规则 说明
单次上限 ≤ 10 行 *或* ≤ 200 字符（满足其一）
超出时 拆多次；或 human 授权 restructure
与 document-standard cap、路径、frontmatter 见 document-standard design 篇
验证 测试验不了单次编辑大小。不作为 test plan 的通过条件

Implementation： spec-write 已有正文。人不读 skill 正文。本条上限看 skill 执行，不靠测试。

5. Decision history — 何时写（agent / 写 spec 时注意）

原则： decision-history 记 已对外生效或已强迫改 reality 的方向，不是 design 脑内迭代的日记。

应该写 不应写
他人 的 decision（review、配对、stakeholder 口径）需团队可见 仍在本人脑中、未 写入 design 篇 且 未 改 existing code 的探索性微调
本人 重大转向且 已改或必须改 existing code（contract、路径、rename、authority 换边、breaking behavior） 为「想过又改主意」每条 append；design 篇里改一句能表达的不单独开 entry
Pipeline 要求的 rename / collision / supersede 等（见 document-standard DSGN-J–DSGN-K） 仅 enrich design 篇 正文、尚未收敛的 rationale

未 commit 的 scratch 与 raw/design/ 不 替代 decision-history；升格 committed fact 时按上表判断。Agents 补写 feature spec 时 默认不 自动堆 decision-history；有疑问时 human 定夺。

6. Agent 规范落地：CLAUDE.md + skill

§4（小步编辑）、§5（decision-history 取舍）、feature spec 各篇职责等，须在 harness 全局 留下印象，不能只在 repo 内 skill 正文里写一遍（PRD-H：复用既有 skill，不另造）。

通道 作用
~/.claude/CLAUDE.md + 项目 CLAUDE.md / CLAUDE.local.md 跨 session、跨 feature 的 默认 agent 行为（含 walter-worker managed block）
Skills（spec-organize 主 skill、spec-review、spec-write） 任务级 procedure、机械检查

Implement SDD / document-standard 时：plan 必须含 skill 变更与 CLAUDE 层条目（managed block 或等价），二者对齐同一 norm；条文细节在 sub design 篇，本 HLD 只定双通道原则。

Further Notes

8. Parent vs sub-feature — review 齐备度

Parent（本 initiative 根 docs/features/spec-driven-development/，不含 features/<sub>/）： spec-review 须核对 feature spec 五篇 均在：prd、design、decision-history、impl-plan、test-plan（how-to 可选；类型见 document-standard DSGN-B）。缺任一篇 → severity ≥3 finding。

Sub-feature（features/<sub>/）： 不 要求五篇齐全；可以只有 design 等。review 只查已有文稿；不得因未计划的 type 缺失而 fail。

Spec-Driven Development — Skill Contracts

Problem Statement

四个 skill 各自的输入、输出和边界没有单独一篇设计承载。结果是 SKILL.md 成了事实权威，pipeline、organize、review、write 之间容易重叠或漏责；PRD-B / PRD-P / PRD-Q 无法被 review 和测试直接检查。

Solution

本篇定义四个 skill 的行为契约；SKILL.md 只是实现。规则细节仍以 document-standard 的 DSGN-* 和 pipeline 的 PIPE-* 为准，本篇只定接口与边界。

User Stories

  • 作为调用方，我希望知道每个 skill 在什么阶段被调用、需要给什么、会产出什么。
  • 作为 reviewer，我希望四个 skill 的责任不重叠，缺一条能找到唯一负责的 skill。
  • 作为维护者，我希望改 SKILL.md 时不改变契约；契约变了要先改本篇。

Implementation Decisions

  • Authority： 契约以本篇为准；SKILL.md 与正文冲突时，先改契约再改正文（DSGN-G）。
  • 不定义： 失败策略、版本/迁移、来源可信度分级、数据清理（ARD-AF）。
  • 四例： 四个 skill 正文都要点名 shed、北京旅游、数学题、股票（PRD-Q）；它们是说明性例子，不是本仓库 gold。
  • Unverified： pipeline 编排、单次编辑大小、可读性打分、跨模型偏差按 PRD-I 标 Unverified。

Design

Skill 阶段 输入 输出 边界
spec-pipeline 任意入口 用户请求、CLAUDE.local / raw/state、PRD/design/decision phase、recap、state、review 询问 不写正文；不 silent 改上游；不自行宣布收敛
spec-organize create / move / merge / lint feature 树、SPEC-STANDARD.md 路径/格式修正、findings 机械 MUST 可 fix；semantic 只 report
spec-review 提交前 / 设计审查 diff 或树、PRD/design/test-plan 带 severity 的 findings + 修改建议 不 fix、不改写；可读性 gate 在此流程内跑，但不作通过条件
spec-write Converge / Downstream 已确认的修改意图 改后的文稿 默认 ≤10 行/200 字符；restructure 需 human 授权；不 silent 改上游

共享能力落点：

  • 子问题归属表（PRD-L / PIPE-L）写在每个 feature 的 design 篇。
  • 证据与 UNKNOWN（PRD-N）由 spec-write 写、spec-review 查。
  • mock MCP client/server（PRD-O）放在 skills/spec-organize/tests/mock-mcp/；pipeline 在 Downstream 后调用。
  • 四个例子（PRD-Q）写进四个 SKILL.md 正文；由 TST-S 检查。

Testing Decisions

  • TST-S： 四个 SKILL.md 都包含四例。
  • TST-O / TST-P： PRD → design 追溯；归属/证据/UNKNOWN。
  • TST-Q： mock MCP call 打出 log，且无真实副作用。
  • Unverified： spec-pipeline 编排（PIPE-A4/A5/H）、单次编辑大小（PRD-C）、可读性打分（PRD-M）、跨模型偏差（ARD-AD）。

Out of Scope

  • 失败策略、版本/迁移、来源可信度分级、数据清理（ARD-AF）。
  • 存量不合规文档的迁移。
  • 各 skill 的具体 prompt 文案；由 SKILL.md 实现。

Further Notes

  • 新增 skill 时先补本表，再写 SKILL.md。
  • 契约变更需同步 document-standard / pipeline 的对应 DSGN-* / PIPE-*。

Reversibility

  • 契约变更可回退:改本篇 + SKILL.md,无数据迁移。
  • 新增 skill 只需追加一行;移除 skill 须同批改 pipeline 与 test plan。

Alternatives Considered

  • 四个 skill 合成一个 → 拒:职责重叠,review 无法独立。
  • 契约直接写进 SKILL.md → 拒:正文变权威,契约失去独立地址(ARD-AB / DSGN-G)。

Drawbacks

  • 多一层间接:改行为要同时动契约与正文。

Risks and Mitigations

  • 风险:正文与契约漂移 → 冲突时契约优先,spec-review 检查引用。

Open Questions

  • 新 skill(如可替换的 map 工具)是否要进契约表。

Spec-Driven Development — Test Plan

Initiative 级 test plan。被测对象 = spec-organize（主）、spec-review、spec-write（write 由 organize 覆盖）；spec-pipeline 编排 Unverified（PRD-I，暂无可执行测试）。Oracle = skills/spec-organize/SPEC-STANDARD.md（自 document-standard design）。Sub-feature 不另写 test-plan。

验收： 四个 skill 是产出。人不读 skill 正文；好不好用只看本计划的测试结果。

Test Scope

In scope： 上列三 skill 在「装进任意项目」场景下的行为；输入三类——本 repo docs/features/、外部 repo（eval.yaml 指定路径）、人工 fixture。Out of scope / Unverified： skill 正文改动（本 plan 只定义测什么）；设计合理性；merge 策略；spec-pipeline 阶段编排（Unverified，PRD-I）；单次编辑大小（PRD-C，Unverified）；可读性打分（PRD-M，在 spec-review 流程内，不作通过条件）；四套例子的 gold（PRD-K，放到别处；例子写进 skill 正文，由 TST-S 检查）。

Parent vs sub（spec-review）： 审 parent（docs/features/spec-driven-development/ 根，不含 features/<sub>/）时须核对五篇均在：prd、design、decision-history、impl-plan、test-plan（见 parent HLD §8）。Sub-feature 不要求齐全，只审已有文件。

Scoring

分数 1 — MUST 合规： x / total，total = must_registry.yaml 条目数；method: python → 检查器；method: llm → judge.model；逐条 pass/fail。

分数 2 — 对标 gold： 对 annotations.yaml 每条——GOOD 相似命中 +1、未命中 0；BAD 未犯 0、相似犯 −1（judge 判相似）。(Σ加分 − Σ减分) × 10 / annotations 条目总数，满分 10，可为负；仅同一 gold.version 内比较。

门槛： 分数 1 = total/total；分数 2 ≥ 同 gold 版本上一次 run。Checker：3 次独立裁决（同一 deepseek-flash），不得推翻 python 项；3/3 PASS。跨模型偏差标 Unverified cross-model。

指标边界： 分数 1/2 是 eval 指标，不是产品 success metric（PRD-G / ARD-N）。

Gold 增长： run 中发现新 good/bad → 追加 annotations.yaml，gold.version +1，added_in 标版本；报告须标 gold 版本。

Test Cases

TST-A — MUST registry 构建

目标： 扫描 document-standard design、pipeline design、parent HLD §4–§5 全部 MUST/禁止/必须 → must_registry.yaml；spec 定稿后重扫。输入： 三篇 design。断言： 覆盖率 100%；每条标 python 或 llm。判定： 锚点比对脚本。

TST-B — 机械检查器 + 负向 fixture

目标： 检查器有效。输入： fixtures/neg/*、fixtures/pos/*。断言： neg 必 fail；pos 必 pass。判定： pytest。

TST-C — Gold 生成（3 次 run）

目标： 基线下 3 次 iPhone feature spec。输入： gold/iphone/v1/requirement.md + context.md；grill.skills: []；只装 spec-organize；deepseek-flash。断言： 每次含 prd/design/decision-history/impl-plan/test-plan；interview.md 中模拟人回答均出自 context 或「未提供」。判定： Python（文件）+ judge（出处）。跨模型偏差 Unverified。

TST-D — Gold 提炼

目标： 3 次 run → exemplar/ + annotations.yaml v1。输入： TST-C 产出。断言： exemplar 过 TST-B、分数 1 全过；annotation 有 where/text；BAD 有 expected_fix。判定： Python + 人工认可（Change Log 记录）。

TST-E — spec-organize happy path

目标： 改 skill 后同需求重跑。输入： 同 TST-C。断言： 分数 1 全过；分数 2 不退步。判定： Python + judge。

TST-F — spec-organize unhappy（输入侧）

目标： context 带坑时不自猜。输入： context-variants/：budget-conflict、family-disagree、missing-info、midway-change。断言： 须 report/ask；budget/family 已有 decision history 先后则取较晚者，否则问用户，不得猜；midway-change 须新 ARD + strike+link；missing-info 不得编造。判定： judge + Python（ARD 结构）。

TST-G — 真实树 Lint

目标： 别人写的 spec 是否合规。输入： 本 repo docs/features/；外部 repo 路径。断言： spec-organize Lint 与 checks/ 一致；豁免不报。判定： Python 对比。

TST-H — spec-review 检出率

目标： 找全缺陷、不误报。输入： 11 个机械检查案例 + 5 个语义案例；干净 exemplar。断言： 植入项均检出并引用 DSGN/MUST id；干净零 3+ 发现；1–2 不进讨论。判定： id 集合比对。

TST-I — spec-review 建议质量

目标： 修改建议正确。输入： TST-H 检出项。断言： 建议 vs expected_fix：照改后缺陷消除且无新 MUST 违规。判定： judge；报 x / 检出数。

TST-J — Eval 配置矩阵

目标： 不同 grill 组合。输入： grill.skills: []、[wayfinder]、[grill-with-docs]、两者。断言： 每配置一份报告；基线先跑；只报分不设门槛。判定： 同 TST-E。

TST-K — 报告

目标： 单 HTML。输入： 任一 run。断言： run_id、分支、gold 版本、eval 配置、分数 1 逐条（python/llm）、分数 2 ±、TST-F 变体、3 次 checker。判定： 生成 + schema。

TST-L — 3 次独立裁决

目标： 最终 PASS/FAIL。输入： HTML + diff。断言： 3/3；不推翻 python；同一 deepseek-flash 的 3 次独立 run。判定： 3 次；跨模型偏差 Unverified。

TST-M — 变更联动

目标： 标准或 gold 变更后测试同步。输入： 改 SPEC-STANDARD / design；或 run 中新 good/bad。断言： design 改 → TST-A + registry/fixtures 同批；新标注 → gold.version +1。判定： 流程 + 覆盖率。

TST-N — Parent 齐备 / sub 豁免

目标： parent 五篇齐全；sub 不因缺篇 fail。输入： SDD parent 根 + features/pipeline/、features/document-standard/。断言： parent 缺任一篇 → spec-review ≥3；sub 仅 design 等仍 pass。判定： Python（路径）+ spec-review 报告。

TST-O — PRD → design 追溯

目标： 每条 PRD 需求都有 design 锚点。输入： 父 PRD、parent HLD、pipeline/document-standard design。断言： 每个 PRD-* ID 映射到至少一个 DSGN-* / PIPE-*；未映射 fail。判定： Python（ID 集合比对）。

TST-P — 归属 / 证据 / UNKNOWN

目标： design 篇有「子问题归属」表且结论可追溯。输入： 含归属表的 design；无依据结论；UNKNOWN 样例。断言： 缺表 fail；有结论无依据 fail；UNKNOWN 当事实 fail。判定： Python（表结构）+ judge（依据质量）。

TST-Q — mock MCP log

目标： 执行只到 mock。输入： skills/spec-organize/tests/mock-mcp/ 的 client/server。断言： call 打出 stdout log（tool/args/result）；无真实下单/订票。判定： Python（log 存在 + 无真实副作用）。

TST-R — reader 新鲜度

目标： reader 不落后于 source。输入： spec-driven-development-reader.html + 所有 source .md。断言： reader mtime ≥ 每个 source mtime；否则 fail。判定： Python。

TST-S — skill 正文四例

目标： 四个 skill 正文包含 PRD-Q 四例。输入： spec-pipeline / spec-organize / spec-review / spec-write 的 SKILL.md。断言： 每个 skill 至少提到 shed、北京旅游、数学题、股票；缺 fail。判定： Python（关键词）+ judge（是否只是点名）。

Evidence Appendix

ARD-A — Authority by concern replaces a single global source of truth

The previous rule was "code is the source of truth", stated in three places in doc-organize. It resolves every conflict in one direction and leaves a spec unable to protect intended behavior: under it, a spec that states a retry count of 3 while the code retries 5 is simply wrong, even when 3 was the requirement.

Considered and rejected:

  • *Keep "code is the source of truth"* — rejected because it makes the spec

unenforceable precisely where enforcement matters, and because a passing test would then also count as a requirement.

  • *Declare "spec is the source of truth"* — rejected for the mirror reason: a

spec cannot answer what the code currently does, and treating it as authoritative for implementation would force spec edits for every refactor.

  • *Single source with an exception list* — rejected as an unmaintainable middle

ground that still names one winner by default.

Adopted instead: authority by concern. Intended behavior belongs to the spec, current implementation to the code, contracts to the machine-readable artifact, database structure to migrations, and executable verification to the tests.

ARD-B — The standard lives in doc-organize, not a new skill

Placement, linting, and consolidation already belong to doc-organize, and its Sync mode is where drift is detected. A separate skill would have to duplicate the document standard to know what a spec is.

Considered and rejected: a new spec-driven-development skill with doc-organize keeping only a pointer. Rejected because the two would share the type list, the frontmatter contract, and the required sections, and the copy would drift.

ARD-C — Detail is carried in sibling files, not inline in SKILL.md

The material is seventeen sections. Inline it would have taken SKILL.md past 700 lines, and a skill that must be read in one pass cannot afford that.

Follows the existing pattern: domain-modeling/ADR-FORMAT.md and domain-modeling/CONTEXT-FORMAT.md. Sibling files travel with the directory, so the skill stays portable — it must not point at this repository's docs/, which does not exist in the projects the skill is deployed to.

ARD-D — The health field is named health, not status

state already tracks the authoring state (draft or final). A second field named status would be read as the same concept, and it accepted an overlapping vocabulary (draft, active, stale, deprecated) that made the overlap worse.

Considered and rejected: replacing state's vocabulary with draft | active | stale | deprecated. Rejected because it would invalidate every existing document to gain a distinction that a second field provides for free.

ARD-E — design and impl-plan cap at 1,000 lines; decision-history is exempt

The earlier guideline said feature specs run 500-1,500 lines, which contradicts a 1,000-line ceiling. The ceiling wins; the guideline is removed.

decision-history is exempt because it is append-only history. Trimming it would destroy the record that is its entire purpose. Exempting it also means the cap never creates pressure to delete a superseded decision.

ARD-F — A feature folder may hold more than one design or impl-plan

Supersedes the earlier rule "one file per type per feature" for these two types only, and removes the anti-pattern that forbade a second spec file.

prd, test-plan, decision-history, and how-to stay single-file: none of them grows without bound. design and impl-plan do, and capping them at 1,000 lines without allowing a second file would have made the cap unmeetable.

ARD-G — Spec parts take an aspect noun, plan parts take a number plus phase

payment-design-authorization.md        aspect noun, unordered
payment-impl-plan-01-schema.md       number plus phase, ordered

Considered and rejected: numbering both (payment-design-01.md). A number says nothing about the contents, and inserting a part forces a renumber across the set. A plan is genuinely ordered, so a number carries meaning there; a spec is cut by bounded context, so a noun carries meaning there.

ARD-H — Four content priority levels; L1 is never deleted

L1 decisive (behavior, contracts, invariants, constraints, error semantics, security rules, architecture boundaries, out of scope, assumptions, compatibility constraints, open questions), L2 rationale, L3 alternatives, L4 support. Trim L4, then L3, then compress L2. Never delete L1.

out of scope, assumptions, compatibility constraints, and open questions are filed at L1 rather than L2 because dropping any of them breaks the implementation in the same way as dropping a stated requirement.

A fact whose authoritative home is another document is L4 as a link, never a restated copy. This connects the level model to the duplication rule: restating a fact is a defect, not a level.

ARD-I — This feature carries two spec documents

Deliberate exception to decision ARD-F's one-spec-per-feature default, recorded here because the rule requires a logged reason rather than a silent breach.

This feature is named for the standard itself, so the standard's own spec belongs to it. wayfinder-import-design.md already occupied spec-driven-development/design/, and the wayfinder import is a distinct effort with its own lifecycle.

Considered and rejected:

  • *Rename the feature* — rejected because the initiative name is established in

the project's working context.

  • *Put the standard's spec in its own feature* — rejected because the standard

and the import are the same initiative; splitting them into two features would misrepresent the work.

  • *Fold the standard into wayfinder-import-design.md* — rejected as a

restatement: two unrelated documents in one file.

The two files are distinguished by name, following decision ARD-G's aspect rule: spec-driven-development-design.md for the standard, wayfinder-import-design.md for the import.

The PRD said six artifacts; pipeline-design.md and the document standard said five. The pipeline spec is right about stages: how-to is an output for the case where a human must operate the result, not a step every feature runs.

A large edit lands unreviewed and is hard to attribute when it breaks something. The limit is 10 lines or 200 characters; satisfying either is enough. A larger change is split into sequential edits. A restructure needs explicit human instruction, which is how this PRD's own revision was applied.

Pipeline

Spec-Driven Development — Pipeline

本篇定义 spec-pipeline 编排 skill：轻量 guidance + 接口。凡 写/改 feature spec 的工作 先进 spec-pipeline，由它按阶段 推荐并调用 其它 skill、维护 轻量 state、在提交前 询问 review、在迷路时 recap。

文档格式、路径、ID、体量见 sibling ../document-standard/design/document-standard-design.md（DSGN-A–M）。本篇 link，不 restate。

Problem Statement

Parent PRD 定义的四类上游问题见 ../../../prd/spec-driven-development-prd.md。本篇补充 pipeline 要解决的 流程 问题：

  • 大 feature / initiative 难拆成可执行的 smaller feature，新人不知道顺序。
  • 多个 skill 并存，调用方 不知道何时用哪个。
  • 长会话后 不知道进度（做到哪、还剩什么）。
  • 提交前 容易跳过 review。

Solution

spec-pipeline 为统一入口，驱动四阶段：

Create → Map → Converge ⇄ (PRD ↔ design ↔ decision-history) → Downstream (test-plan ∥ impl-plan)
  • Create： 立项与 context（feature create、粗 PRD、搜索 → CLAUDE.local）。
  • Map： 与人 interview；AI 判断拆分/decision/scratch；无 固定 MUST 产物模板；可选 可替换 map 工具（示例 wayfinder，非 SDD deliverable）。
  • Converge： 三角循环打磨；收敛后 才进入 Downstream。
  • Downstream： test-plan 与 impl-plan 并行，均自 design 篇 总结（对齐 parent PRD Solution）。

User Stories

  1. 拆分大需求： 作为不熟悉 spec 的人，我希望经 pipeline Map interview 后，能拆出 smaller feature 并进入 spec-driven 写齐文稿。
  2. 恢复上下文： 作为中断后继续的人，我希望 pipeline recap：已做什么、state 字段、待办、建议下一步。
  3. 提交前： 作为提交者，我希望 pipeline 在「该提交了」时 询问 是否先跑 spec-review。

Implementation Decisions

  • 编排 = spec-pipeline；标准 = spec-organize；写 = spec-write；审 = spec-review（提交前由 pipeline 询问，非 silent 强制）。
  • Map 以 interview 为主；AI 判断 是否记 decision、建议拆 feature、或仅 scratch task；人确认 后才创建 docs/features/<f>/ 路径。
  • Map 工具（示例 wayfinder）经 推荐表 调用，可替换；不在 SDD deliverable 清单。
  • State： feature create 完成、<f> 未确定前 — 进度只写在 CLAUDE.local.md（或项目 CLAUDE 层），不 创建 raw/state/*.md。<f> 确定后 — 权威 state 在 docs/features/<f>/raw/state/state-<YYYY-MM-DD>.md（document-standard DSGN-B/C）。
  • Recap 由 pipeline 生成给人看；不是 source of truth（SO T = state 文件 + committed 文稿）。
  • 后期 task 管理：plug-in 其它 skill；本篇 不 引入 BMAD/GSD 级重框架。
  • 协作：读上游 artifact，禁止 silent 改；冲突 Detect → Report → Ask（同 document-standard DSGN-G）。
  • 本篇设计条目 ID 前缀 **PIPE-*；不 用 DSGN-*** 作 pipeline 内锚点（DSGN 保留给 document-standard）。

Design

PIPE-A — spec-pipeline 职责（MUST）

来源：PRD-A（在既有 pipeline 上改进，不另造编排）。

  • PIPE-A1 任意「写/改 spec」任务 经 spec-pipeline 进入（除非 human 显式跳过并记入 state/recap）。
  • PIPE-A2 调用 spec-organize 执行标准、Lint、Organize（路径/格式以 organize 为准）。
  • PIPE-A3 调用 spec-write 执行文稿增删改（含 parent HLD §4 小步编辑 norm）。
  • PIPE-A4 在 提交/推送 committed 变更前，询问 是否 spec-review；用户拒绝则记录，不 silent 跳过审计痕迹。
  • PIPE-A5 用户请求或会话丢失时 recap：已做、当前 state、待做、建议下一步（list）。
  • PIPE-A6 维护/读取 PIPE-H 定义的 state；推荐 PIPE-G 表中的 skill。

PIPE-B — 四阶段总览

阶段 目的 典型失败
Create 建立 feature/initiative 与 context 无 PRD 锚点、context 只存在于聊天
Map 探已知/未知、判断是否拆分 silent 建目录、无 interview
Converge PRD/design/decision 循环至够稳 在 open decision 上写死 design
Downstream test-plan ∥ impl-plan 只写 test 无 regression，或 impl 无顺序

PIPE-C — Create

  1. feature create（walter-worker）建立或选定 <f> / initiative 根（peer vs nested 见 parent HLD §3.1）。
  2. 粗 PRD（示例：「推荐 iPhone 并协助购买」)— 可 draft，不要求一次写齐六要素。
  3. 搜索/调研 → 已知 context 写入 CLAUDE.local.md（或项目 CLAUDE 层）；不 替代 committed PRD。

PIPE-D — Map

  1. Interview 用户（及 context 包）；AI 归纳已知/未知。
  2. AI 判断（无固定 MUST 文件类型）：是否建议 新 feature、是否写 decision、是否在 scratch 留 task 线索、或 暂不拆 进入 Converge。
  3. Recap Map 结论：判断摘要、建议拆分、仍 open 项。
  4. 可选 调用 pluggable map skill（示例 wayfinder）；不得 替代 interview。
  5. 禁止 未经确认创建 docs/features/<f>/ 或移动 committed 树（Organize 模式负责路径）。
  6. 拆分标准（暂时）： AI 先给几个拆法推荐。一个人 20 小时以内能搞清楚的，算一个 feature spec；AI 估算超过 20 小时的，拆成 peer 或 sub-feature。小时估算和拆不拆的评判都由 AI 做。
  7. 子问题（PRD-L）： 每个子问题标成 AI 查、人决定、或 AI 查完后人决定。人没问到的盲区和风险，AI 必须提出。

DSGN-D — INDEX 与 book（派生层）

docs/features/ 里的 committed 文档是 source of truth。INDEX 与 book 都是 派生层，不用 DSGN-E frontmatter / Change Log，不写 新 decision：

INDEX book
回答的问题 在哪（路径、type、initiative 结构） 干了什么（短摘要，便于 AI/人决定要不要打开全文）

docs/INDEX.md — 干什么
目的 全库 feature spec 各篇的 地图：哪个 initiative 下有哪些 PRD、design、plan，路径是什么。
给谁用 人、agent、脚本 发现文档 时先查 INDEX，再打开 docs/features/... 里的正文。

INDEX 怎么维护

  • 生成物：整文件 regenerate（改 generator/template，不长期手改一行行条目）。
  • 何时 regenerate：任一 committed 文档 create / move / rename / delete 之后；与 book 一样，push 到 GitHub 前/时 应与 docs/features/ 变更 同批同步（见 book 应然）。
  • 收录范围：只列 committed 文档（含 sub-feature）；不列 raw/、.scratch/。
  • 结构：按 feature（initiative） 分块，块内按 type 顺序（prd → design → … → decision-history）；链接相对 docs/。
  • 质量（DSGN-M MUST）：disk 有文件但未 listed → orphan；listed 但文件不存在 → dead link。

docs/book/ — 干什么**

（与历史 doc-organize 一致：*Assembled output, built from documents that are already final。* — 此处 final 指 feature 侧已接受的 committed 正文，不是 book 自己定稿。）
目的 由 feature spec 各篇 组装 的 摘要层：用短说明写清每份 PRD/design/plan 覆盖什么、得出什么、该去哪读全文 — 主要给 AI 检索与选篇。
给谁用 Agent / 人 先扫 book 再打开 docs/features/...；不是在此写第一版 design 或新 decision。
不是什么 不是 source of truth；不是 design 全文拷贝；不能 与 feature 正文 手维护两份相同 fact。
与 INDEX INDEX = 目录；book = 内容摘要。二者互补，通常 一起 更新。

book 写什么（摘要契约）

  • 每条摘要 必须 链到对应 canonical 路径（docs/features/...）。
  • 写 scope + 主要结论/状态（例如：document-standard 的 design 篇定 DSGN-A 契约；pending review 项），不 展开 L1 全文。
  • 新增/变更 decision 只改 feature / decision-history，再 重生成 book 摘要，禁止只在 book 改口径。

book 什么时候更新（应然）

  • 凡 docs/features/ 下 committed 文档 有变更并 push 到 GitHub，同一 push（或紧邻的前序 commit）中应已 regenerate 对应的 book（及 INDEX）。

*实现*（pre-push hook、CI、bot、手动）属 impl；本 standard 要求 远端可见的 docs 与 book/INDEX 同步，避免 AI 在 GitHub 上读到新 spec 却仍是旧摘要。

  • 源文档 state: draft 时可暂不更新对应摘要；final 或已 merge 的 committed 变更 必须反映到 book。

其它

  • 路径：docs/book/；无 DSGN-E frontmatter；Lint 查 link 有效**、摘要指向的文件存在。
  • 可 额外 用于 MkDocs / Pages 发布；发布 nav 属 impl，不得与 feature 树、INDEX 矛盾。

其它豁免路径（同样不是 feature 文档，无 DSGN-E frontmatter；Lint 只查 link）：CONTEXT.md（domain glossary）、README.md（repo 导向）。

DSGN-F — 条目 ID（type 前缀 + 字母）

各 type 内可追溯条目用 {前缀}-{字母}，字母序同 Excel 列（A–Z → AA–AZ → BA–…）。可在已有条目之间 插入 新 ID（大方向顺序，见 DSGN-J）。

ID immutable（MUST）： 某 ID 一旦写入 feature spec（表、标题、正文、外链），该字符串 终身固定 — 禁止 改字母、改前缀、拼写「修正」、重编号、把 PRD-A 合并进 PRD-B。禁止复用 已出现过的 ID（即使 entry 被 strike / 整段作废）。口径变了 → 新 ID + 旧处 strike / link（DSGN-J）；不得 改旧 ID 本身。

Type 前缀 例

design DSGN DSGN-A, DSGN-B
decision-history ARD ARD-A, ARD-AA
impl-plan IMPL IMPL-A, IMPL-B
test-plan TST TST-A, TST-B

跨文档引用 写全 ID（如 PRD-A、ARD-F）。how-to 无强制 letter ID。

作用域（MUST）： ID 在 feature + type 内唯一；跨 feature 引用写 <feature>/<ID>（如 document-standard/PRD-K）。裸 ID 只在本 feature 内有意义。

HLD 例外： 父 HLD 的 System Context / Logical Architecture 等 架构章节 不要求 DSGN-* ID；只有可追溯的规则小节才要 ID。

凡有序号即 ID（MUST）： ADR、requirement、design 规则小节、impl task、test case、defer/open question 等 一切 可追溯条目 — 必须 用上表 {前缀}-{字母}。禁止 裸数字（0001）、PRD-1/DH-1/FR-3/OQ-1/D1 等作永久 ID。本 design 篇小节即 DSGN-A 起（见索引）。

检查： ids.py 按 type 强制标题模式（PRD-* / DSGN-* / IMPL-* / TST-* / ARD-*），缺 ID 或裸数字即 fail。

AI 单次 edit 粒度（≤10 行 / ≤200 字）属 SDD parent HLD §4，不在本 document-standard；impl 目标：spec-write 等书写 skill。

DSGN-G — Authority by Concern

不要 global single source of truth — 按 concern 各认一个 authoritative artifact；不一致时 Detect → Report → Ask（禁止 silent 改一侧；禁止默认 design 篇 > code）。

Concern Authoritative artifact
Intended behavior feature design 文档
API contract OpenAPI / protobuf / GraphQL / JSON Schema 等
Database structure migrations / schema
Current implementation code
Executable verification tests

design 篇 权威 intended behavior；code 权威当前实现与内部结构。Machine-readable contract 不要在 Markdown 里手抄全文 — link 或 generate。Tests 是 verification，不是 requirement 替身。final 后 maintain，不整篇 rewrite。

DSGN-H — Design 文档 Scope（type: design 正文）

写： behavior、contract、invariant、constraint、error、state transition、外部交互、架构边界（含 diagram 类）。 不写： class 结构、private method、framework 内部细节（见 DSGN-I trim 时也应 absent）。 测试句： 可改 implementation 而不改 externally observable behavior → 不应改 design 篇。

Agent 加载顺序： Global rules → Domain design → Architecture → Contract → Examples/tests → Code。窄问题却要整篇 design → re-cut boundary。

体量与 split：DSGN-B。篇内设计决策 / 小节锚点用 DSGN-A 等（DSGN-F）。

DSGN-I — Content Priority

Trim 顺序 L4 → L3 → 压 L2；L1 永不删。仍 > 硬 cap → DSGN-B split。

Level Trim
L1 behavior、contract、invariant、error、security、boundary、out of scope、assumption、compatibility、open question — never
L2 rationale — 压缩
L3 alternatives — 先删
L4 引用、raw output — 先删；重复 fact 只能是 link

DSGN-J — Decision History — 语义

文件角色： 决策 索引 + 正文（Decision Log / ### <ID> 小节，格式 DSGN-E）。不是 PRD / design 篇 的摘要。

书写顺序： 倒序 — 每加一条，写在 Decision Log 最上面（最新在上，越往下越早）。

Decision ID： 格式 ARD-{字母}（DSGN-F，分配后 不可改）。Log 表 / ### ARD-A — … 与 ID 一致。

推翻旧 decision： 旧 entry 不删行；正文 删除线；旁 link 到新 ID（如 → ARD-F）。新口径用 新 ARD ID 写满一条，倒序 插 Log 顶。旧 entry 仅 strike + 指链（DSGN-I 不 trim 被 strike 字句）。

拆 part（超 DSGN-B 硬 cap）： ID 全 feature 唯一；新 entry 写入 当前 part Log 顶部；旧 part 保留；part 间 link 即可。

什么时候加一条（agent 写 spec 时）： 细则表见 parent HLD §5。简记：

加 不加
别人定下来的口径（review、结对、stakeholder），团队要能看到 仅在你脑子里、还没写进 design 篇、也 没动代码 的试探
你的转向会 改已有代码或对外契约（breaking behavior、路径/rename、谁才是 authority） 只在 design 篇 改几句就能说清的推敲；「想过又改主意」不必每条都 log
rename / 撞名等流程要求记入的（DSGN-K） agent 默认不 自动批量 append；不确定问 human

DSGN-K — Paths and Names — 冲突处置

新 feature / 新文件名 必须 对照已有名称；命中任一 collision signal 即视为冲突：

Signal 例
normalize 后相同 Payment vs payment
token 子集 auth vs auth-service
单复数 / 常见缩写 doc vs docs
edit distance ≤ 2 payment-api vs payments-api

处置：同一 bounded context → merge 再按 aspect split design。不同 context 易混 → rename 双方并记入 decision-history。同 feature 内文件撞名 → 拉开 aspect 或 rename feature。Rename = decision，更新 inbound link，禁止 silent。

DSGN-L — Enforcement Modes

Mode 行为
Organize feature/type → collision → 路径/文件名 → frontmatter + sections → Change Log → INDEX
Lint walk docs/features/；MUST 机械 fix；semantic report
Consolidate propose → 批准；decision 全保留；raw/ legacy cite 或删

Review（spec-review） 同 Lint 的 detect（机械 MUST + semantic）；不 fix，输出带 severity 的修改建议

内容质量（设计是否成立）由 Review 的 semantic 部分处理，不属本 standard 的 MUST。

DSGN-M — Quality Gates

MUST： DSGN-A 全满足（含 DSGN-F ID 不可改、不可复用）；DSGN-G 冲突不 silent；DSGN-I 不删 L1；consolidation 不丢 decision；Commit = no 路径未 commit；INDEX 无 orphan/dead link；含 docs/features/ 变更的 push 时 INDEX/book 已与源同步；collision 已查。

NICE： heading 不跳级；link 有效；CONTEXT 术语一致；last_verified 新鲜；context boundary 合理。

Testing Decisions

验证见 parent ../../../test-plan/spec-driven-development-test-plan.md：被测对象是 spec-organize / spec-review，不是本篇；本篇全部 MUST / 禁止 由 TST-A 扫入 must_registry.yaml，机械项 Python 判、其余 LLM judge 判。

Out of Scope

  • 存量 tree 一次性 migrate（incremental 合规即可）。
  • CI / skill 如何实现 enforcement（文件数、prompt、hook）。

Document Standard — Spec Reader HTML（Design）

Aspect design： DSGN-N（spec reader / human HTML 汇编）。PRD：PRD-A–P 见 ../prd/document-standard-prd-spec-reader-html.md。与 DSGN-B 路径、DSGN-I 优先级、DSGN-F ID 引用一致。Implementation： skills/spec-html-standard/SPEC-HTML-STANDARD.md（标准文件，非 skill）；spec-pipeline 编排入口，加载该标准汇编 HTML。

Problem Statement

  1. Feature spec 多篇、多层，人类难以一次读全。
  2. 「人类可读 HTML」若写成 短摘要，review 与 onboarding 会 漏 MUST，与 document-standard「L1 永不删」冲突。
  3. 先前 v0 指引（spec-pipeline SPEC-READER.md）写「summarize and rephrase」易被理解成 大幅删减 — 废止该解读；以本篇 DSGN-N 为准。

Solution

定义 Spec Reader HTML 产物：单文件、Tab 化、富排版、保真优先 的 derived view；canonical 永远是 committed .md。
