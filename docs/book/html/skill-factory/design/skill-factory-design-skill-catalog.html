skill-factory — skill 目录、调用关系与共性问题

本篇是 skill-factory 设计 的一个分篇（part）。 13 个必备章节只在入口文件里，本篇只回答三个问题。 第一，工厂里一共有哪些 skill，各自从哪里来。 第二，这些 skill 之间谁调用谁，连成了哪几条流水线，哪些调用已经断了。 第三，给每个 skill 反推规格（reverse-spec，即从现有代码和聊天记录倒推出需求和设计）时，反复出现了哪些共性问题。 本篇是汇总，细节都在各 skill 自己的规格里，这里只链接，不重复。 skill 的组成见 为什么要做，一个 skill 怎么搭，验证和安装见 怎么验证 skill，怎么安装和升级。

证据从哪里来

仓库事实以 HEAD ca8efab（2026-11-24）为准，引用 commit 短哈希。 SKILL.md:行号 形式的引用都指 HEAD ca8efab 的文件。 各 skill 的问题引用它自己 design 里 Open Questions 表的编号，例如"auto-tdd 的 QUES-A"。 QUES 是 open question（未决问题）的编号前缀。 research 的规格还没提交，草稿在 raw/parked/research/ 下，只在本机。 raw/ 路径是有效证据，即使别人打不开（SPEC-STANDARD 的 ARD-BW）。 用户原话引用会话 id 前 8 位加日期，多数转引自各 skill 的 PRD。 找不到证据的地方写 UNKNOWN，不猜。 下文的"建议"都等用户决定，不是决策。

skill 目录

DSGN-AF 目录。 HEAD 一共有 26 份 SKILL.md：skills/ 下 17 份，personal-skills/ 下 9 份。 skills/spec-html-standard/ 只放三份标准文件，没有 SKILL.md，所以不算一个 skill。 "来源"一列里，"自写"指需求出自用户自己的会话；"导入"指从别人的仓库拿来。 导入的 7 个都来自 Matt Pocock 的 mattpocock/skills，frontmatter 里都写了 source_author: mattpocock 和 source_url。 SDD 指 spec-driven-development（从规格驱动开发）这个 feature。 5 个 SDD skill 归那个 feature 管，本篇只列出，不分析，见 spec-driven-development 设计。

调用关系

DSGN-AG 怎么数一条调用。 本篇把"一个 SKILL.md 让 agent 去用另一个 skill"记作一条调用边。 写法有三种：/名字 这样的斜杠命令，正文里点名"调用某 skill"，以及"配套 skill"这类列表。 只在 When NOT to Use 里说"改用某 skill"的，算作转介，不算调用。 被调用的 skill 在本仓库和 ~/.claude/skills/ 下都找不到，就记为断边。 被调用的名字后来改了，SKILL.md 没跟着改，也记为断边。 以上边是逐个 grep 26 份 SKILL.md 得到的（HEAD ca8efab）。

DSGN-AH 规划侧的调用。 wayfinder 是调用最多的 skill。 它把待定的问题写成一张张 brief（问题卡片），按类型分给别的 skill 解决（skills/wayfinder/SKILL.md:123-126）。 research 类 brief 交给 /research 子 agent 无人值守地解决。 grilling 类 brief 交给 /grilling 和 /domain-modeling 一起和用户对话。 prototype 类 brief 交给 prototype。 接口表里，访谈一栏的默认实现是 grill-with-docs 加 domain-modeling（SKILL.md:135）。 交付前审查时，代码文件交给 matt-code-review（SKILL.md:308）。 grill-with-docs 的正文只有一句：用 domain-modeling 跑一次 /grilling（skills/grill-with-docs/SKILL.md:31）。 这里有两条断边。 第一，/grilling 在本仓库和 ~/.claude/skills/ 下都不存在，wayfinder 和 grill-with-docs 都调用它（grill-with-docs 的 QUES-A，domain-modeling 的 QUES-C）。 第二，prototype 链接的 LOGIC.md 和 UI.md 从没导入（skills/prototype/SKILL.md:39-40，prototype 的 QUES-A）。 matt-code-review 只在 ~/.claude/skills/ 下有一份部署副本，本仓库和 walter-worker 的 skills/ 下都没有它的源，出处是 UNKNOWN。

DSGN-AI 交付侧的调用。 wayfinder 写明的交付顺序是 to-spec、spec-review、to-tickets、auto-tdd 四步（skills/wayfinder/SKILL.md:276）。 spec-review 是一道关口，通过了 to-tickets 才能跑（SKILL.md:254）。 在 SDD 仓库里，spec 不发成 issue，而是由 spec-write 写进 docs/features/（SKILL.md:270）。 implement 不在这条链上，没有任何 skill 调用它。 用户在导入 implement 一分钟后说"implement 我的替代是auto-tdd"（d8d2da7f，2026-08-02，见 implement 的 PRD）。 implement 自己调用 /tdd 和 /code-review（skills/implement/SKILL.md:30-34）。 /tdd 已在 commit 6086424 并入 auto-tdd，所以是断边（implement 的 QUES-B）。 /code-review 没说是哪一个（implement 的 QUES-C）。 implement 和 to-spec 都引用 doc-organize/ 下的文件（skills/implement/SKILL.md:40-41，skills/to-spec/SKILL.md:40-42）。 doc-organize 在 commit c44e983 改名为 spec-organize，这些引用就断了（implement 的 QUES-A，to-spec 的 QUES-A）。

流水线

DSGN-AK wayfinder 交付流水线。 这是本仓库最完整的一条流水线，从模糊的想法一直走到代码。 第一段是规划：wayfinder 建地图，把 brief 分给 research、grilling、prototype 去解决（DSGN-AH）。 第二段是写规格：普通仓库用 to-spec 发一个 issue，SDD 仓库用 spec-write 写进 docs/features/。 第三段是关口：spec-review 审过，才能拆工单。 第四段是交付：to-tickets 拆工单，auto-tdd 按工单写代码（DSGN-AI）。 这条链现在有三处走不通。 grilling 类 brief 是默认类型（skills/wayfinder/SKILL.md:125），但它要的 /grilling 不存在。 research 类 brief 期待一个无人值守、产出带出处 markdown 的子 agent，但 research 的两条分支都先问用户问题（research 草稿的 QUES-A）。 prototype 类 brief 走 UI 或逻辑分支时，要读的两份说明文件不存在。 另外，用户要求所有代码都要审查，但 wayfinder 让 prototype brief 跳过审查关口（prototype 的 QUES-B）。

DSGN-AL 视频流水线。 视频相关的 6 个 skill 都在 personal-skills/，它们没有一个总入口来串联。 create-video-workflow 把研究文档变成演示、视频或网站，分 7 个阶段。 transcribe-audio 说自己服务于 create-video-workflow 的第 1 阶段（personal-skills/transcribe-audio/SKILL.md:7）。 但 create-video-workflow 并不调用它，而是把纯音频素材记为缺口（personal-skills/create-video-workflow/SKILL.md:85，create-video-workflow 的 QUES-D）。 hvg 仓库里的那份 create-video-workflow 加过这一步路由，本仓库的副本没有跟上（transcribe-audio 的 QUES-C）。 youtube-summarize 自带一套 Whisper 转写和 easyocr 截图识别（personal-skills/youtube-summarize/SKILL.md:64-65）。 这和 transcribe-audio、pic-to-txt 的功能重复，但它不调用这两个 skill（transcribe-audio 的 QUES-B，youtube-summarize 的 QUES-D）。 youtube-research-pipeline 的第 0 步调用 pic-to-txt 的 ocr.py，但路径指向已不存在的目录（DSGN-AJ）。 它的第 1 步派 3 个并行子 agent 查资料，这些是它自己的子 agent，不是 research skill。 video-production-pip-style 是一份手工指南，在"配套资源"一节列了 youtube-research-pipeline、pic-to-txt 和 doc-organize（personal-skills/video-production-pip-style/SKILL.md:364-366）。 把 youtube-summarize 和 youtube-research-pipeline 合成一个 /youtube 的提议，2026-08-02 被推迟（youtube-summarize 的 QUES-B）。

DSGN-AM 自愈和 bug 循环。 自愈（self-heal）指 AI 记下用户对它的纠正，同类纠正重复出现后，自动写成预防规则。 这件事集中在 bug skill 的三条分支里（skills/bug/SKILL.md）。 Hunt 分支找根因并修好，第 5 阶段问用户要不要跑 Heal 分支（SKILL.md:94）。 Report 分支把 walter-worker 自身的问题写成 GitHub issue，然后也接 Heal 分支（SKILL.md:108）。 Heal 分支把纠正写进 .self-healing/traces/，同类纠正出现 2 次以上，就把规则注入项目 CLAUDE.md 的 SELF-ANALYZE 块（SKILL.md:116-139）。 research 在 When NOT to Use 里说，已经在实现阶段就改用 /bug hunt（skills/research/SKILL.md:43）。 auto-tdd 的完成标准要求修代码时，连同放过这个 bug 的 spec 和 skill 一起修（skills/auto-tdd/SKILL.md:123）。 这个循环现在不会自己转起来。 ~/.claude/hooks/on-self-heal.sh 文件存在，但没有在 ~/.claude/settings.json 里注册（本篇 2026-11-24 核对，bug 的 QUES-D）。 Report 分支写死了目标仓库 cicidi/walter-worker（SKILL.md:107，bug 的 QUES-C）。 全局 CLAUDE.md 里还有一个 walter-worker-fix skill 处理同一类问题，两者没有分工（bug 的 QUES-F）。

共性问题
