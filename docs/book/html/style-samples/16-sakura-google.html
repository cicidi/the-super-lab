Overview

五篇文档不是五个孤岛；它们共享同一份问题定义。

PRD · draft

本 PRD 定义 spec-driven development：用 PRD、decision-history、design、impl-plan、test-plan 五篇，把有门槛的问题分析清楚，并由 spec-write 与 spec-review 执行（ARD-AJ）。

01What

把问题、约束、验收写成可审查的文档。

02Why

让 AI 的推理有 context，而不是靠猜。

03Who

写 spec 的人、审 spec 的人、执行 skill。

04Not

不做重型流程，不为文档而文档。

Problem Statement

问题没有被定义清楚时，AI 的答案再流畅也只是猜。

unknown

今天，AI 模型的能力已经非常强大。它们可以阅读、搜索最新、最前沿的技术，帮助我们解决问题。

但是，问题是什么？

嘿，AI，我买 iPhone 18 Duo 还是 iPhone 18 基础版？

看似是一个简单的问题，但实际上，我们并没有告诉 AI 我们的真实需求。比如：我们买新的 iPhone 是用来做什么的？我们的 budget 是多少？我们之前是否一直使用 iPhone？我们喜欢 iPhone 的哪些优点，又有哪些缺点？

1. Problem 经常没有被定义清楚，更何谈解决

这些 context，AI 并不知道，因此 AI 的推荐肯定不会准确。这正是很多人抱怨 AI 不好用的原因。事实上，对于我们自己来说，这看似是一个清楚的问题，但实际上，可能不是 AI 不好用，而是人没有把 problem 定义好。

2. AI 真正赋予我们的 superpower，是帮助我们发现 unknown

在我们把问题问清楚以后，AI 也提供了一些思路，甚至 solution。但是，由于人的能力有限，我们可能根本没有见过某些解决方法或方案。我们利用已知的信息，找到我们不知道自己知道的信息，同时学习我们知道自己不知道的知识，最后把我们不知道、甚至不知道自己不知道的 blind spot 发掘出来。

Goals & Non-goals

目标决定写什么；非目标决定不写什么。

GOAL 01

把 problem 定义清楚

先回答 What / Why / Who / Not，再谈 solution。

GOAL 02

发现 unknown

用提问把 blind spot 摊开，而不是让模型猜。

GOAL 03

五篇可执行

PRD、decision-history、design、impl-plan、test-plan 互相咬合。

NON-GOAL

不替代人的判断

规范负责暴露问题，最终取舍仍然由人决定。

NON-GOAL

不追求一次写对

允许 review 回路反复修正，直到验收可测。

NON-GOAL

不做重型流程

文档为问题服务，不为流程本身服务。

Usage

先写 frontmatter，再让 skill 按类型执行；审查时只看 ID 与验收。

CLI / YAML
spec.prd.yaml 
feature: spec-driven-development
type: prd
state: draft
health: active
owner: cicidi
last_verified: 2026-11-04
terminal 
# 生成并校验 PRD
spec-write --feature spec-driven-development --type prd

# 逐条审查需求与验收
spec-review --feature spec-driven-development --strict

# 三个问题必须出现
grep -n "QUES-0[1-3]" docs/features/spec-driven-development/prd/*.md

Review Notes

三条在 review 时最常被问到的提醒。

提示

写 PRD 前先回答一个问题：这个问题不解决，会怎样？如果答不上来，说明问题还没有门槛。

警告

没有验收标准的 FR 不是需求，是愿望。愿望无法 review，也无法回归。
