PRD

Spec-Driven Development — PRD

Overview

这份 PRD 说明我们要做什么：一套「先写清楚 spec，再让 AI 去做」的方法，叫 spec-driven development（下文简称 SDD）。

SDD 用五篇文档把一个有门槛的问题分析清楚：PRD（要做什么）、decision-history（做过哪些决定）、design（怎么做）、impl-plan（按什么顺序做）、test-plan（怎么验证做对了）。写文档由 spec-write 这个 skill 负责，检查文档由 spec-review 负责（ARD-AJ）。

文中的缩写和术语，例如 skill、ARD、gold，在 parent design 附录：术语表 里有解释。

Problem Statement

今天，AI 模型的能力已经非常强大。它们可以阅读、搜索最新、最前沿的技术，帮助我们解决问题。

但是，问题是什么？

1. Problem 经常没有被定义清楚，更何谈解决

比如这样一个问题：

嘿，AI，我买 iPhone 18 Duo 还是 iPhone 18 基础版？

看似是一个简单的问题，但实际上，我们并没有告诉 AI 我们的真实需求。

比如：我们买新的 iPhone 是用来做什么的？我们的 budget 是多少？我们之前是否一直使用 iPhone？我们喜欢 iPhone 的哪些优点，又有哪些缺点？

这些 context，AI 并不知道，因此 AI 的推荐肯定不会准确。

这正是很多人抱怨 AI 不好用的原因。事实上，对于我们自己来说，这看似是一个清楚的问题，但实际上，可能不是 AI 不好用，而是人没有把 problem 定义好。

2. AI 真正赋予我们的 superpower，是帮助我们发现 unknown

在我们把问题问清楚以后，AI 也提供了一些思路，甚至 solution。

但是，由于人的能力有限，我们可能根本没有见过某些解决方法或方案。

我们利用已知的信息，找到我们不知道自己知道的信息，同时学习我们知道自己不知道的知识，最后把我们不知道、甚至不知道自己不知道的 blind spot 发掘出来。

这才是 AI 真正赋予我们超能力的地方。

3. Decision 不断变化，AI 需要理解、记录并同步这些变化

经常，我们做了一段时间，或者和 team 里的其他人讨论后，会发现一些 decision 一直在改变。

比如：我们买 iPhone 的 budget，和父母、妻子商量未果。我们之前说买 iPhone 的 budget 是 2,000 美金，现在突然变成了 1,000 美金，那么 AI 整个 decision 的方向就会发生彻底的转变。

紧接着，一系列新的问题又会被引入：去哪里买？是不是能够接受二手 iPhone 18 Duo？

当然，随之而来的，去哪里买、如何找 deal 等具体实现方式都会发生改变。

今天的例子比较简单，以后可能会有更复杂的例子：多个人做出多个 decision，到底谁是真理？而这个真理，可能还需要 impact、覆盖其他一些之前的 decision。

比如：爸爸的 budget 是 1,800 美金，妈妈说 1,500 美金；爸爸说下个月可以买，妈妈说这个月可以买。

到底谁是真理？根据这个真理，我们又要如何修改之前的 decision？

这里真正的问题是：当多个参与者做出不同的 decision 时，AI 如何理解这些 decision 之间的关系，判断哪些 decision 是有效的，并根据最新的 decision 更新整个 decision-making process？

4. 即使 problem、solution、update、sync 都做好了，人依旧是整个 AI 世界最大的 bottleneck

首先是阅读。

怎么让文件好读、好懂？文件怎么好查找？如何清晰地知道每个文件是做什么的？如何做好 file management？

大的项目不可能只有一个 spec，那么如何切分 spec？如何让不同的 spec 之间保持清晰的关系？以后 AI 和人又该怎么读、怎么查找？

当项目越来越大，文件越来越多，spec 越来越复杂时，我们如何让人和 AI 都能够快速理解整个项目，并准确找到自己需要的信息？

这些都是 AI 真正落地到实际工作中，需要解决的问题。

5. 有门槛的难题不只在软件里

盖一个 shed、去北京旅游、看懂一道著名数学题、不靠猜地分析一只股票——人往往从没做过，不知道怎么拆、盲区在哪、哪些要自己拍板。

AI 要把大问题拆成小的：能查的 AI 自己查（合规、财报、交通），要选的人来选（预算、偏好、风险），人想不到的 AI 主动问。spec 既是学习笔记，也是决策记录，最后交给 AI 执行。

Goals and Success Metrics

目标： 任何有门槛的难题，都能拆成三类小问题：AI 能查的、人要决定的、可以交给 AI 执行的。拆完写成一套本科生读得懂、前后一致、结论有依据的 spec。

验收方式： 看 test-plan 的测试结果，包括机械检查、对 iPhone 案例的评测分数、可读性测试（test-plan）。这些是评测指标，用来判断 skill 好不好用。

产品级成功指标： 例如「用了 SDD 的人，决策是否真的更好」。怎么量、基线是多少，目前还定不下来，延后处理（PRD-G，ARD-N）。

User Stories

  • 作为写 spec 的人，我希望 AI 先追问我，把我已知的、未知的和没想到的盲区都问出来。
  • 作为审 spec 的人，我希望格式错误和内容问题都能被找出来，而且每条修改建议都能直接照着做。
  • 作为执行的人，我希望 spec 能一路落到 design 和 impl-plan，执行时先用 mock 演练，每个结论都能查到来源。

Solution

我们不重新解释什么是 spec-driven。这里要做的是一组配合使用的 skill，让 AI 按固定的方法把一个具体问题分析清楚。

PRD、decision-history、design 三篇是反复打磨的循环，不是只写一遍的直线。三篇打磨到足够稳定之后，再从 design 分别总结出 impl-plan 和 test-plan。这两篇互不依赖，可以同时写。

  1. PRD：要做什么、解决什么问题；有哪些限制、偏好、时间要求、可用的资源和工具。design 或某个决定暴露出缺口时，回到 PRD 修改需求。
  2. Decision-history：根据 PRD 做出的决定。凡是影响方向的决定，先记进 decision-history。这一步大约一半靠 AI 整理、一半靠人拍板。新决定可能改变 PRD 的范围；design 里的取舍也可能需要补一条决定。
  3. Design：和 PRD、decision-history 一起迭代，写技术方案、接口约定、要用的工具等。写 design 时发现问题没想清楚、或决定不够，就回到第 1 步或第 2 步继续打磨。
  4. Impl-plan：从 design 总结出实现步骤，包括先做什么、后做什么、每个任务的细节和准备工作。不需要等 test-plan 写完。
  5. Test-plan：从 design 总结出验证方法，包括每个任务怎么算完成、可用性检查、防止改坏旧功能的回归检查。不需要等 impl-plan 写完。

Functional Requirements

PRD-A：写 spec 的流程沿用现有流程并加以改进，不另造一套。流程分哪几个阶段、每个阶段做什么，写在 pipeline design。

PRD-B：提供一组 skill。skill 本质上是写得好的 prompt，引导 AI 完成 spec 的四件事：书写、命名、检查、更新。

PRD-C：AI 每次改 docs/ 下的文档，必须同时满足两条：不超过 10 行，并且不超过 200 字符；新建一个文件不算在内（ARD-CE）。更大的改动拆成多次；确实需要一次大改（restructure）时，必须有人明确授权，并记一条 ARD（例如 ARD-BK）。

PRD-D：每篇文档有行数上限，最长不超过 1,000 行，因为太长的文档几乎没法维护。decision-history 例外，不设上限：它只增不减（ARD-E）。各类文档的具体上限见 document-standard 的 DSGN-B。

PRD-E：规定文档放在哪个目录、文件叫什么名字、目录之间是什么关系（parent、sub-feature、peer）。具体规则见 document-standard 的 DSGN-B。

PRD-F：多个人的决定互相冲突时，以 decision-history 里时间较晚的那条为准；看不出先后，就问用户。AI 不猜测谁说了算。

PRD-G（延后）：产品级成功指标和基线，暂时定不下来，见 ARD-N。test-plan 里的分数是评测指标，不是产品成功指标。

PRD-H：流程里的每一步，优先使用已经流行的 skill，不重新发明。

PRD-I：每项改动都要能验证。实在验证不了的，在 spec 里标为 Unverified 并写明原因；标了的项不作为 test-plan 的通过条件。

PRD-J：写或改 feature spec 时，由 spec-write 按标准判断要新建哪篇、或要改哪几篇；提交前，询问是否先跑 spec-review。写作进度记在 wayfinder 的地图目录里，目录建好前后的位置见 pipeline design 的 PIPE-H（ARD-CH）。

PRD-K：适用范围不限于软件，任何有门槛的难题都用同一套 spec。四个例子：盖 shed（合规、成本、施工）、北京旅游（行程、住宿、风险、预算）、看懂一道著名数学题（零基础一步步学）、分析一只股票（基本面、财报、新闻，每个结论有依据）。这四个例子不在本仓库建 gold（ARD-AD）。

PRD-L：每个子问题都标明由谁处理：AI 查、人决定、或 AI 查完后人决定。人没有问到的盲区和风险，AI 必须主动提出来。

PRD-M：文档要让人读懂，这是硬需求，而且是通过条件。交付前，由一个 LLM（大语言模型）扮演本科水平的程序员，只读这一篇文档和术语表，回答从文档里抽出的问题；答错太多，或者有文档里没解释、术语表里也没有的术语，就不算交付（ARD-BO）。具体门槛见 test-plan 的 TST-V。

PRD-N：正式 spec 里的每个结论，都要能追溯到查到的事实，例如法规条文、财报、新闻、定义，不靠猜。查不到的写 UNKNOWN。评测时，AI 回答问题只能用 context 包里给的信息。

PRD-O：执行阶段不真下单、不真订票。所有例子共用一个 mock MCP 服务器，提供几个固定的工具；客户端调用后打印出调用记录，就算交付成功。

PRD-P：最终交付物是 spec-write、spec-review，以及负责进度规则的 wayfinder 三个 skill（ARD-CH）。用它们写出来的 spec，要满足 PRD-K 到 PRD-O。

PRD-Q：书写、命名、检查、更新，以及 PRD-K 到 PRD-O，都是需求；spec-write 和 spec-review 能做的事不限于这几件。两个 skill 的正文里都要写出四个例子：盖 shed、北京旅游、数学题、股票。skill 好不好用，只看测试结果。

Out of Scope

  • 真实下单、订票、交易。执行只做到 mock MCP 的调用记录。
  • 多人决定的细致仲裁规则，例如两个决定时间相同怎么办。目前只按 decision-history 的先后，看不出就问用户。
  • 在本仓库为四个非软件例子建 gold。例子写进 skill 正文，gold 放在别处。
  • 把已有的不合规文档批量迁移到新标准。
  • skill 和 spec 的迁移策略。版本只做来源标记：每次 build 把 PRD 的 version 末位加 1 再印进 skill（ARD-CK）。

Resources Needed

  • spec-write、spec-review、wayfinder 三个 skill，前两个要读的三份标准文件（ARD-CH），和一份 test-plan。不需要数据库。外部服务：评测用的 deepseek-flash API，以及发布网站用的 GitHub Actions 和 GitHub Pages（ARD-CD）。
  • 评测需要 deepseek-flash 的 API，以及生成 gold 跑 3 次、复核跑 5 次的费用。跑分结果和报告不提交（ARD-CJ）。

进入下游前，PRD 要写清的五项（pipeline design 的 PIPE-E-B）：

项 本 PRD
限制 每次改动不超过 10 行并且不超过 200 字符（PRD-C）；文档行数有上限（PRD-D）
偏好 not apply
时间 not apply

Implementation Decisions

DSGN-A — AI 每次改文档的上限

来源：PRD-C。

适用于 AI 对 docs/ 下 markdown 文档的每一次修改：

规则 说明
单次上限 两条都要满足：不超过 10 行，并且不超过 200 字符；只管修改已有文件，新建文件不算（ARD-CE）
超出时 拆成多次改；或者由人明确授权一次大改（restructure），并记一条 ARD
和文档标准的关系 行数上限、路径、frontmatter 见 document-standard 的 DSGN-B 和 DSGN-E
怎么验证 测试无法检查单次改动的大小，所以这一条不作为 test-plan 的通过条件（PRD-I）

这条规则写在 spec-write 的正文里，靠 skill 执行，不靠测试。

DSGN-B — 什么时候写 decision-history

decision-history 只记已经对外生效、或者已经逼着现实改变的方向。它不是 design 写作过程中的思考日记。

应该记 不应该记
别人做的决定（评审、结对、利益相关方的意见），团队需要看到 还只在自己脑子里、没写进 design、也没改代码的试探
自己的重大转向，并且已经改了、或者必须改已有代码（接口、路径、改名、权威换边、不兼容的行为变化） 「想过又改主意」的每一步；design 里改一句话就能说清的事
流程要求记录的改名、撞名、推翻旧决定（见 document-standard 的 DSGN-J、DSGN-K） 只是补充 design 正文、还没定下来的理由

没提交的草稿和 raw/design/ 不能代替 decision-history。要把草稿里的结论正式写进文档时，按上表判断要不要记。AI 补写 feature spec 时，默认不自动往 decision-history 里加条目；拿不准就问人。

DSGN-C — 规范要同时写进 CLAUDE.md 和 skill

DSGN-A（改动上限）、DSGN-B（什么时候记决定）以及各篇文档的职责，要让 AI 在任何会话里都记得，不能只写在本仓库的 skill 正文里（PRD-H：复用已有的机制）。

渠道 作用
~/.claude/CLAUDE.md，以及项目里的 CLAUDE.md、CLAUDE.local.md 跨会话、跨 feature 的默认 AI 行为
spec-write、spec-review、wayfinder 三个 skill 具体任务的操作步骤；规则来自三份标准文件

项目里写哪个文件：有 CLAUDE.local.md 就写它，没有就写 CLAUDE.md，两个都没有就问用户要不要新建（ARD-CG）。

实现 SDD 或文档标准时，计划里必须同时包含 skill 的修改和 CLAUDE 层的条目，两边写的是同一套规范。规则的细节写在 sub-feature 的 design 里，本文只定「两个渠道都要写」这条原则。

Further Notes

DSGN-E — parent 和 sub-feature 的文档齐备要求

  • parent（docs/features/spec-driven-development/ 这一层，不含 features/ 下的 sub-feature）：spec-review 要确认五篇都在：prd、design、decision-history、impl-plan、test-plan。how-to 可选。缺任何一篇，记为严重度 3 及以上的问题。

Alternatives Considered

  • 一个 skill 同时负责写和审：放弃。自己审自己写的东西，容易看不出问题（ARD-AJ）。
  • 一篇大文档装下所有内容：放弃。很快会超过行数上限，而且「要什么」「为什么」「怎么做」混在一起，改一处要翻全篇。
  • 保留 spec-pipeline 作为统一入口：放弃。四个 skill 让使用者不知道该从哪个开始；写和审两个动作已经覆盖全部场景（ARD-AJ）。

Drawbacks

  • 五篇文档加上 design 的 13 个必需章节，对小问题来说太重。sub-feature 可以只写 design（DSGN-E），能缓解一部分。
  • decision-history 只增不减，越来越长。
  • wayfinder 按 SDD 改写后和上游 mattpocock/skills 分叉，上游更新要手工合并（ARD-CH）。
  • 审查和可读性判断都依赖 LLM，同样的输入两次结果可能不同。所以生成 gold 跑 3 次，复核跑 5 次（ARD-CJ）。

Risks and Mitigations

风险 后果 应对
规则越加越多 作者把句子压成关键词，文档变得像给机器读的 规则分 MUST 和 NICE，只有 MUST 算失败（ARD-BN）；可读性作为通过条件（ARD-BO）

检查脚本没跟上规则 机械检查报 0 个问题，但文档其实不合规 规则改动后，同一批更新检查脚本和 MUST 清单（TST-M）；当前欠账列在 impl-plan 的 IMPL-P

Reversibility

  • 所有文档都是 git 里的 markdown，任何修改都可以用 git 撤回。
  • 决定不删除。推翻一条决定，就新写一条 ARD，旧的划掉并链到新的，所以随时能看到当初为什么这样定。

Spec-Driven Development — Skill 契约

本篇是 整体设计 spec-driven-development-design.md 的一个分篇，只讲两个交付的 skill 各自做什么。术语见 术语表。

Problem Statement

交付物是 spec-write、spec-review，以及负责进度规则的 wayfinder（ARD-CH）。如果它们的职责只写在各自的 SKILL.md 里，改 skill 的人可以随手改掉职责边界，而没人察觉。所以需要一份独立的契约：说清每个 skill 什么时候用、要什么输入、产出什么、不能做什么。

Solution

本篇是三个交付 skill 行为的权威来源，SKILL.md 只是它的实现。两者不一致时，以本篇为准：先改本篇，再改 SKILL.md。具体的写作规则不在本篇重复，以三份标准文件 SPEC-STANDARD.md、SPEC-PRESENTATION.md、SPEC-HTML-STANDARD.md 为准（ARD-AJ、ARD-BX）。

Design

Skill 什么时候用 输入 产出 不能做的事
spec-write 新建或修改 spec 文档 用户的意图；三份标准文件 改好的文档；改完告诉用户网页没更新、问要不要重建，commit 前必须重建（ARD-CF） 动笔前没判断「新建哪篇、还是改哪几篇」；一次改动超过 10 行或超过 200 字符而没有授权（parent design 的 DSGN-A）；悄悄改动上游文档

User Stories

  • 作为调用 skill 的人，我想知道每个 skill 什么时候用、要给它什么、它会产出什么。
  • 作为审查的人，我希望写和审的职责不重叠，每条标准规则只在一个地方有正式说法。
  • 作为维护 skill 的人，我希望修改 SKILL.md 不会悄悄改变契约；契约要变，先改本篇。

Implementation Decisions

  • 以谁为准： 以本篇为准。SKILL.md 和本篇冲突时，先改本篇，再改 SKILL.md。这条沿用「按关注点分权威」的原则（document-standard 的 DSGN-G）。
  • 故意不定义： 失败处理、迁移、信息来源可信度分级、数据清理；版本只是来源标记，每次 build 末位加 1（ARD-CK，重述已划掉的 ARD-AF）。
  • 四个例子： spec-write、spec-review 的正文都要提到盖 shed、北京旅游、数学题、股票（PRD-Q）。它们只是说明用的例子，不是本仓库的 gold。
  • 暂时测不了的： 阶段编排、单次改动大小、不同模型之间的偏差，按 PRD-I 标为 Unverified。

Testing Decisions

  • TST-S：spec-write、spec-review 的 SKILL.md 都包含四个例子。
  • TST-O、TST-P：PRD 的每条需求都能在 design 里找到对应；归属、证据、UNKNOWN 写得对。
  • TST-Q：mock MCP 调用打印出记录，并且没有真实副作用。
  • TST-V：每篇文档本科生读得懂。
  • 暂时测不了：阶段编排（pipeline design 的 PIPE-A-D、PIPE-A-E、PIPE-H）、单次改动大小（PRD-C）、不同模型之间的偏差（ARD-AD）。

Out of Scope

  • 故意不定义的事项，见上面 Implementation Decisions。
  • 已有不合规文档的迁移。
  • 每个 skill 具体的 prompt 措辞，由 SKILL.md 自己决定。

Further Notes

  • 新增 skill 时，先在本篇的表里加一行，再写它的 SKILL.md。
  • 契约改了，要同步检查 document-standard 和 pipeline 里相关的 DSGN、PIPE 规则。

Alternatives Considered

  • 合成一个 skill： 放弃。写和审必须分开，自己审自己写的东西看不出问题（ARD-AJ）。
  • 把契约直接写进 SKILL.md： 放弃。那样 SKILL.md 就成了权威，契约没有独立的位置，改 skill 时也没有东西能拦住越界的修改。

Drawbacks

  • 多了一层：改 skill 的行为，要同时改本篇和 SKILL.md。

Risks and Mitigations

  • SKILL.md 和本篇慢慢不一致： 冲突时以本篇为准；spec-review 审 skill 时对照本篇。

Open Questions

本 feature 的未决问题统一记在 parent design 的 Open Questions。和本篇有关的是 QUES-A（交付的 skill 怎么带上标准文件）和 QUES-C（新工具要不要进契约表）。

Reversibility

  • 契约修改可以撤回：改回本篇和 SKILL.md 即可，没有数据要迁移。
  • 新增 skill 只要在表里加一行；去掉一个 skill，要同一批修改 pipeline design 和 test-plan。

Test Scope

要测的： 把 spec-write 和 spec-review 装进任意项目后的行为。输入有三类：本仓库的 docs/features/、外部仓库（路径在 eval.yaml 里指定）、人工做的小样例（fixture）。可读性也在测试范围内（TST-V，ARD-BO）。

  • 阶段编排（PRD-I，见 pipeline design 的 QUES-A）。
  • 单次改动的大小（PRD-C）。
  • 四个非软件例子的 gold（PRD-K）。gold 放在别处；例子写进 skill 正文，由 TST-S 检查。

Scoring

分数 1：MUST 合规。 得分是「通过的条数 / 总条数」，总条数是 must_registry.yaml 里的条目数。method: python 的由检查脚本判断，method: llm 的由判分模型判断，每条只有通过或不通过。

分数 2：和 gold 比。 对 annotations.yaml 里的每一条打分：

标注 产出里有类似的 产出里没有
GOOD +1 0
BAD −1（犯了这个错） 0

分数 2 =（加分合计 − 减分合计）× 10 ÷ 标注总数。满分 10，可以是负数。「类似」由判分模型判断。只在同一个 gold 版本内比较。

门槛： 分数 1 必须满分；分数 2 不能低于同一 gold 版本的上一次运行（ARD-R）。复核用同一个 deepseek-flash 独立裁决 5 次，至少 4 次通过才算通过；复核不能推翻 Python 检查的结果（ARD-CJ）。不同模型之间的偏差暂时测不了，标为 Unverified。

分数的用途： 分数 1 和分数 2 是评测指标，不是产品的成功指标（PRD-G、ARD-N）。

gold 增长： 运行中发现新的好例子或坏例子，追加到 annotations.yaml，gold 版本号加一，added_in 写上新版本。报告里必须写明 gold 版本（ARD-S）。

TST-F — spec-write 的异常输入

TST-O — PRD 到 design 的追溯

目标： PRD 的每条需求，在 design 里都有对应的规则。输入： parent PRD、document-standard 的 reader PRD，以及 parent design、pipeline design、document-standard design 和它的 reader 分篇。通过条件： 两份 PRD 的每个 PRD-* 都至少对应一个 DSGN-* 或 PIPE-*。两份 PRD 的编号会重复（都有 PRD-A），所以按 feature 分开比对：parent 的 PRD 对 parent design、pipeline design 和 document-standard design，reader PRD 对 reader design。parent 的 PRD-G 已延后（ARD-N），不要求对应；有没对应上的就失败。「对应」指编号出现在 DSGN-* 或 PIPE-* 规则小节的正文里；只在 Open Questions 或 Change Log 里提到不算。判定： Python（test_tst_o_trace.py）。

TST-P — 子问题归属、证据、UNKNOWN

目标： 有子问题的 design 都有「子问题归属」表，结论都能追溯。输入： 带归属表的 design；故意写了没有依据的结论的样例；UNKNOWN 的样例。通过条件： 缺表就失败；有结论没依据就失败；把 UNKNOWN 当事实写就失败。判定： Python 检查表的结构，判分模型判断依据的质量。

TST-Q — mock MCP 的调用记录

TST-V — 本科生读得懂

目标： 每篇已提交的文档，本科水平的程序员只读这一篇就能读懂（PRD-M，ARD-BO）。

输入： 一篇文档，加上 parent design 的术语表。被测的有两类：SDD 自己的每篇文档；TST-C、TST-E 里 spec-write 写出的每篇文档。

做法：

  1. 从这篇文档的编号条目（PRD-*、DSGN-*、PIPE-*、IMPL-*、TST-*、ARD-*）里，每条出一道题，最多抽 20 道。例如「PRD-F 规定，多人的决定冲突时怎么办」。
  2. 对照：不给文档，先问一遍。不看文档也能答对的题太容易，作废。
  3. 让判分模型扮演本科程序员，只读这一篇和术语表，回答剩下的题。
  4. 再让它列出这篇里第一次出现时没有解释、术语表里也没有的词。

通过条件： 剩下的题答对至少 80%，并且没解释的词是 0 个。跑 3 次，至少 2 次通过才算这篇通过。可读性判断的波动比 MUST 判断大，所以这里不要求 3 次都通过。

本文件记录这套方法里所有已经生效的决定。每条决定有一个编号，格式是 ARD- 加字母，例如 ARD-A、ARD-BK。编号一旦写下就不再改，也不再给别的决定用。

规则。 内容的增删改由 spec-write 做。格式类 MUST（例如标题写法、frontmatter 字段）可以由整理工具的 Lint 模式直接修。两者都受 ARD-BP 的改动上限约束。

放弃的方案。 Lint 只报告不改：每个小格式问题都要绕一次 spec-write，太慢。

ARD-BU — 人确认后才建 feature 目录

原因。 pipeline design 里，Create 阶段（PIPE-C、PIPE-G）说要用 feature create 命令建目录，但 PIPE-D 和 Implementation Decisions 说人在 Map 阶段确认后才建。Map 在 Create 之后，两者矛盾。

规则。 Create 阶段只把暂定的 feature 名字和进度记在 CLAUDE.local.md（ARD-BT）。人在 Map 阶段确认拆法和名字之后，才用 feature create 命令建 docs/features/<f>/。

放弃的方案。 Create 就建目录：名字还没定就建，事后改名会留下死链。

ARD-BT — 重申 ARD-U、ARD-V 仍然有效的部分

原因。 ARD-U 和 ARD-V 在日志里整行被划掉，但它们只有一部分被推翻：ARD-U 被推翻的是「spec-pipeline 是入口」，ARD-V 被推翻的是「为四个例子建 gold」。剩下的部分仍是现行规则（PRD-J、pipeline design 的 PIPE-D、PIPE-H、PRD-K），却挂在已划掉的决定上，读者会以为这些规则也作废了。

规则。 下面三条仍然有效，以本条为准：Map 阶段以访谈为主，产出由 AI 判断；进度在 feature 名字定之前记在 CLAUDE.local.md，定了以后记在 docs/features/<f>/raw/state/；非软件难题留在本 PRD，用同样五篇文档。

ARD-BS — 可以中英文混合；Problem Statement 保留原话

原因。 ARD-BK 要求正文统一为中文。审查时发现 PRD 的 Problem Statement 是作者原话，中英文混写，标题带 1 到 5 的编号。人决定保留原样：读着通顺比形式统一更重要。

规则。 正文可以中英文混合，只要读着通顺。英文术语第一次出现时要解释，或者收进术语表。Problem Statement 可以保留作者原话，包括原来的编号标题。推翻 ARD-BK 里「正文统一为中文」的说法。ARD-BK 其余部分仍然有效，在此重述：2026-11-20 这次整理是人明确授权的大改，可以大段重写；术语表放在 parent design 附录；单次改动上限在这一批暂停。

本条也给 ARD-AW 加了一个例外，ARD-AW 因此划掉，在此重述：必需章节（## 级）的标题用英文、不编号；其他章节只有写有序步骤时才编号；例外是 Problem Statement 下面作者原话的小标题可以保留编号。

ARD-BR — pipeline 子条款改用字母

原因。 document-standard 的 DSGN-F 规定编号后面只用字母，但 pipeline design 的子条款用了数字（PIPE-A1、PIPE-E1）。人选择改名，不开例外。

规则。 PIPE-A1 到 PIPE-A6 改为 PIPE-A-A 到 PIPE-A-F；PIPE-E1 到 PIPE-E3 改为 PIPE-E-A 到 PIPE-E-C；PIPE-F1、PIPE-F2 改为 PIPE-F-A、PIPE-F-B。新旧对照表在 pipeline design 的 Further Notes（ARD-AP）。

放弃的方案。 记一条例外，允许子条款用数字：改动最小，但标准里就多了一条特例。

ARD-BQ — 六种文档都可以拆分篇

原因。 ARD-F 只允许 design 和 impl-plan 拆分篇，理由是其他四种不会无限变长。但后来 document-standard 的 DSGN-B 给六种文档都定了分篇的命名规则，DSGN-J 也允许 decision-history 拆分篇，document-standard 还已经有一个 PRD 分篇（reader PRD）。规则和实际做法都已经超出了 ARD-F。

规则。 六种文档都可以拆分篇。有分篇时，必须有入口文件 <f>-<type>.md，入口文件链到各分篇。document-standard 因此补上入口文件 document-standard-prd.md。推翻 ARD-F。

放弃的方案。 维持 ARD-F、收紧 DSGN-B：reader PRD 会变成违规文件，又不能随意改名。允许只有分篇、没有入口：读者不知道从哪篇开始读。

ARD-BP — 改动上限两条都要满足

原因。 ARD-K 写的是「10 行或 200 字符，满足其一即可」。按字面理解，一行 5,000 个字符的改动也算合规，这违背了「小步改、每步能看清」的本意。

规则。 AI 每次改 docs/ 下的 markdown，必须同时满足两条：不超过 10 行，并且不超过 200 字符。更大的改动拆成多次；确实需要一次大改，要人明确授权并记一条 ARD。推翻 ARD-K 里「满足其一即可」的部分，ARD-K 其余内容由本条完整重述。

ARD-BO — 可读性是通过条件

原因。 PRD-M 把可读性定为硬需求，却又写「不作为通过条件」，等于没有要求。这套方法要解决的问题之一就是「人读不过来」（PRD Problem Statement 第 4 点），可读性必须能挡住交付。

怎么判。 一个 LLM 扮演本科程序员，只读被测的那一篇和 parent design 的术语表（本行在 2026-11-20 原地修订，加上术语表，和 PRD-M、TST-V 一致；ARD-AN 允许原地修订）。脚本从这篇的编号条目（PRD-*、DSGN-*、PIPE-*、IMPL-*、TST-*、ARD-*）各出一道题，例如「PRD-F 规定多人决定冲突时怎么办」。再出一组对照题：不给文档直接问，能答对的题说明太容易，作废。答对率不足，或者有第一次出现时没有解释、术语表里也没有的词，这篇就不通过。具体门槛写在 test-plan 的 TST-V。

放弃的方案。 只让 LLM 打一个「好不好读」的分：主观，同一篇文档两次打分可能差很多。用句长、词频这类可读性公式打分：看不出术语有没有解释。ISO 24495-1（简明语言标准）讲的是原则和真实读者测试，不是公式；TST-V 让模型扮演读者答题，借的正是这个思路。

影响。 修改 PRD-M；ARD-W 的「读懂才算通过」保留，并补上具体做法。

ARD-BN — 规则分 MUST 和 NICE 两级

原因。 2026-11-07 一天加了二十多条格式规则。作者为了逐条满足，只好把句子压成关键词和编号，文档越来越像给机器读的。规则越多，越没人读得完。

怎么分。 MUST 是违反后 spec 会写错、会丢信息、会互相矛盾的规则。NICE 是格式上的偏好，spec-review 可以提，但不算失败。下面八条降为 NICE：

决定 内容 为什么只是偏好
ARD-AL 的后半句 每节写明哪份文档对这些事实有权威 「一个事实只写一处」已经是 MUST，这句是额外的标注
ARD-AM 步骤编号是位置，不是永久编号 只影响引用方式
ARD-AN 就绪程度、原地修订、按负责人分组 都是允许怎么写，不是必须怎么写
ARD-AR 不变量写成表格 写成清楚的句子也不会错
ARD-AZ §N 链接落点、步骤范围不重叠 链接打不开已经由 ARD-AP 管
ARD-BA HTML 更新记录覆盖每个日期 HTML 是派生物
ARD-BB 问题清单的数量统计 数错一个数不影响规则本身
ARD-BE 图的规则 画法偏好

ARD-AX 和 ARD-AY 本来就是「允许」，不是要求，不受影响。其他规则保持 MUST。

放弃的方案。 全部保留、只改写法：规则数量不变，作者负担不变。全部删掉：会丢掉其中有用的写法建议。

ARD-BM — 删除线只用在 decision-history

原因。 2026-11-18 在 document-standard 的 DSGN-F 加了一条「改正文时不删旧句，划掉后在旁边写新句」。几轮下来，test-plan 的资产表一个格子里有三处删除线，读者分不清哪句是现行规则。这条规则还和 ARD-AS（删除线只留给 decision-history）直接矛盾。

规则。 正文只写现行规则。推翻旧说法时，在新句后面链到对应的 ARD。旧版本可以从 git 历史和 decision-history 里找到。错别字直接改。本决定重申 ARD-AS，撤销 2026-11-18 那条规则。

放弃的方案。 保留正文删除线：历史已经有 decision-history 和 git 两处记录，正文再记一次是重复，而且越积越难读。

ARD-BL — 打分用的 gold 是 iPhone 案例

原因。 评测的做法是：给 skill 同一份需求和背景资料，看它写出的 spec 和 gold 有多接近。ARD-BJ 把这套 SDD spec 定为 gold，但它没有对应的「输入需求」，skill 无从生成它，所以没法打分。如果拿 skill 去审 gold 本身，又成了自己考自己：改 gold 就能提高分数。

规则。 打分用的 gold 是 iPhone 购买案例 skills/spec-organize/tests/gold/v1/：有需求 requirement.md、背景资料 context.md、范例 exemplar/ 和标注 annotations.yaml。这套 SDD spec 是写法样板：spec-review 拿它当审查对象，找出它不满足自己标准的地方，但它不参与打分。推翻 ARD-BJ。

放弃的方案。 保留 ARD-BJ 并补写一份输入需求：需求是事后补的，等于按答案出题。四个非软件例子各建一个 gold：ARD-AD 已决定这四个例子不在本仓库建 gold。

ARD-BK — 本次整理是授权的大改

人在 2026-11-20 明确授权这一批整理：正文统一改成中文（必需章节标题和编号仍是英文，见 document-standard 的 DSGN-E；后来 ARD-BS 放宽为允许中英文混合）；可以大段重写，但要保留原意；缩写和术语集中解释在 parent design 附录。这一批暂停「每次不超过 10 行或 200 字符」的上限（ARD-K），这一批结束后恢复。做法和 ARD-AI 相同。

ARD-BJ — gold spec 就是这套 spec（已被 ARD-BL 推翻）

当时的想法是：这套 spec 本身就是写得最好的样板，评测通过就意味着写出了这样的 spec。后来发现它没有输入需求，无法用来打分，见 ARD-BL。

ARD-BI — 左侧栏的序号和层级

左侧栏按层级排列，序号可见：1 prd、2 decision-history、3 design、4 impl plan、5 test plan、6 how to。sub-feature 不放在 design 下面，而是单独一组，编号 10，每个 sub-feature 在这组下展开。design 的分篇和 reader 放在 3 design 下面。pipeline 在左侧目录里没有单独的页面，它的内容收在 reader 汇编页里。原因：读者先按顺序读 prd、决定、design，序号让顺序一眼可见。

ARD-BH — 交付物只有 spec-write 和 spec-review

对外交付的只有两个 skill：spec-write 负责写，spec-review 负责审。SPEC-STANDARD.md 和 SPEC-PRESENTATION.md 是这两个 skill 要读的文件，不单独算交付物。spec-organize 和 spec-pipeline 也不在交付物里。ARD-AJ 只说了标准写在哪里，没说它们算不算交付物；本条补上这一点。标准文件后来增加到三份，见 ARD-BX。原因：使用者只调用 skill；标准文件单独交付没有用处。

ARD-BG — 全站一个网站，左边是目录

docs/book/html/index.html 列出所有 feature。每篇 spec 的 HTML 是目录里的一行。打开一个 feature，左边是这个 feature 的目录，右边是正文。原因：读者要在多篇文档之间来回跳，一个网站比一堆独立的 HTML 文件好找。推翻 ARD-AH 的「reader 是唯一的 HTML 交付物」：现在 reader 是网站里的一页。ARD-AH 里「旧的摘要页删除」已经执行，仍然有效。

ARD-BF — spec 的 HTML 放在 book 下

docs/book/html/ 的目录结构和 docs/features/ 一样。parent 的汇编页是 docs/book/html/<parent>/<parent>-reader.html；其他 spec 的 HTML 用相同的相对路径，只把扩展名换成 .html。markdown 留在 docs/features/。原因：HTML 和 markdown 混在一起，容易被误当成权威文件。

ARD-BE — 图只画流程

一个流程一张图。图里的步骤数要和它所在章节写的步骤范围一致。状态用表格写，不用图。图不能出现文字里没写的事实。原因：图里多出来的事实没人维护，很快就和文字不一致。按 ARD-BN 降为 NICE。

ARD-BD — 外部 gold 只留清单

清单记录：源仓库路径、有问题的那个 commit、修好后的 commit、应该找出的问题、允许漏掉的问题。别人的 spec 原文不复制进本仓库。原因：那些 spec 不是公开的。

ARD-BC — 引用处的状态与问题清单一致

在正文里提到某个 QUES 时，旁边写的「未决」或「已决」必须和问题清单里一致。原因：清单里已经关闭的问题，正文还说它未决，读者会被误导。

ARD-BB — 问题清单的数量要对得上

清单里写「共 N 个问题」，N 必须等于实际行数；按状态统计的数量也一样。按 ARD-BN 降为 NICE。

ARD-BA — HTML 更新记录覆盖每个日期

手工维护的 reader 页面，它的更新记录要包含 markdown Change Log 里的每一个日期。按 ARD-BN 降为 NICE。

ARD-AZ — 章节链接和步骤范围

写成「§N」的链接要落在第 N 节，或它的上一级、下一级。同一文档里的步骤范围不能重叠。按 ARD-BN 降为 NICE。

ARD-AY — 问题清单可以代替子问题归属表

如果每个子问题都已经是问题清单里的一行，并且每行都写了负责人和依据，design 可以只放一个链接，不必再抄一张归属表。原因：同一件事记两处，迟早不一致。

ARD-AX — 可以加 Ready 列

Decision Log 可以加第四列 Ready，表示这条决定是否已经可以执行。仍然不能加 Status 列和 Supersedes 列：状态写在正文里，推翻关系用删除线加链接表示。

ARD-AW — 只有步骤类章节可以编号

必需章节的标题用标准规定的英文原文，不加编号。专门写一串有序步骤的章节可以编号。原因：检查脚本按标题原文找必需章节；编号会让标题对不上。

ARD-AV — 必需章节只写在入口文件

design 拆成多篇时，13 个必需章节只要求写在入口文件 <f>-design.md。其他分篇在开头链回入口，只写自己负责的那部分。原因：每个分篇都写 13 节，大部分会是空话。

ARD-AU — 翻译副本只放本地

<name>.<lang>.md 这样的翻译副本不提交。副本开头写明以 <name>.md 为准。副本里的标题可以翻译。原因：提交的翻译副本会和原文慢慢不一致，又没人负责同步。

ARD-AT — 完成标准、顺序、mock

每个 IMPL-* 写明完成标准。先做只读的部分，再做会写入的部分。对方的接口还没上线时，先写一个 mock 代替。原因：没有完成标准的任务不知道什么时候算做完；先写后读容易把数据写坏。

ARD-AS — 正文推翻旧说法时链到新 ARD

正文不再成立的句子直接改写，并链到推翻它的 ARD。删除线只留给 decision-history。错别字直接改。ARD-BM 重申了这条。

ARD-AR — 不变量写成表格

不变量是「任何时候都必须成立的事」。把它写成表格：哪些记录必须存在，或者哪些状态绝不能出现，各由谁来保证。原因：一句口号没法检查。按 ARD-BN 降为 NICE。

ARD-AQ — 引用代码时写明 commit

design 或 impl-plan 里写「某文件第几行」时，同时写明是哪个 commit 的。原因：代码会变，行号会移动；不写 commit，以后没人知道当时指的是哪一行。

ARD-AP — 保留旧锚点

编号迁移时，保留一张新旧编号对照表。标题改名时，把旧的锚点留在新标题上方。原因：其他文档里的旧链接不会因此失效。

ARD-AO — 每个 feature 一份问题清单

很多文档都提到同一批问题时，只在一处列出，其他文档链过去。每个条目编号是 QUES- 加字母，写明问题、目前答案、负责人。原因：同一个问题记在三处，关掉一处另外两处还开着。

ARD-AN — 就绪程度和原地修订

一条决定可以写「这边已经定了，在等另一个团队」。同一行的措辞可以原地修订。未决事项按负责人分组。按 ARD-BN 降为 NICE。

ARD-AM — 步骤编号只是位置

步骤编号表示它在流程里的位置，不是永久编号。插入一步时，这一节和引用它的地方一起重新编号。按 ARD-BN 降为 NICE。

ARD-AL — audience 字段

frontmatter 的 audience 可以是 internal 或 external。不写不算错，所以已有文档不受影响；写了其他值就算错。原来的后半句「每节写明哪份文档对这些事实有权威」按 ARD-BN 降为 NICE。

ARD-AK — markdown 是全文

脚本生成的 reader 每次从 markdown 重新生成。手工维护的 HTML 要在页面里写明源文件路径和源文件的 sha256；源文件变了而 HTML 没变，检查就会报「过期」。原因：HTML 是给人读的副本，不能比 markdown 旧。

ARD-AJ — 入口 skill 是 spec-write 和 spec-review

使用者从 spec-write 和 spec-review 进入。路径、权限、写什么、证据这些规则写在 skills/spec-organize/SPEC-STANDARD.md；文字、格式、表格这些表达规则写在 skills/spec-html-standard/SPEC-PRESENTATION.md。spec-organize 和 spec-pipeline 不再是入口。推翻 ARD-AB。原因：四个 skill 让使用者不知道该从哪个开始；写和审两个动作已经覆盖全部场景。

ARD-AI — 那一次合并是授权的大改

人明确授权了一次性合并 SDD 的 spec 文档。那一批允许超过 10 行或 200 字符的改动，之后恢复上限。

ARD-AH — reader 是唯一的 HTML 交付物（已被 ARD-BG 推翻）

spec-driven-development-reader.html 是给人读的交付物。旧的摘要页 spec-driven-development.html 删除，原来指向它的链接改指 reader。后来改成全站一个网站，reader 是其中一页，见 ARD-BG。

ARD-AG — 收敛由规则判断

pipeline design 的 PIPE-E-A 到 PIPE-E-C（收敛条件）自动检查。每个未决事项都要标明是否阻塞（写在问题清单的「阻塞」列）。只要还有阻塞的事项，就不能进入下游。原因：让 AI 自己判断「够稳了」，它总会说够稳了。

ARD-AF — 故意不定义的事项

失败处理、skill 和 spec 的版本管理、信息来源可信度分级、数据清理，都故意不定义。已有的不合规 feature 不迁移，只修 SDD 自己这套文档。原因：先把核心流程做对，这些事项等有真实需求再定。

ARD-AE — 非软件问题的对应关系、归属和证据

非软件问题也用同样五篇文档：调研笔记放 raw/research/，决定放 decision-history，方案和执行步骤放 design 和 impl-plan，验证放 test-plan。每个有子问题的 design 都有一张子问题归属表，每个子问题标明「AI 查」「人决定」或「AI 查完人决定」。每个结论都有来源；查不到的写 UNKNOWN。测不了的项写成 Unverified: <原因>（<什么条件下能测>）。

ARD-AD — 评测用 deepseek-flash 跑 3 次

目前只有 DeepSeek 的 API 可用，所以生成 gold 和判分都用 deepseek-flash 独立跑 3 次。不同模型之间的偏差暂时测不了，标为 Unverified。gold 由四部分组成：案例、版本、范例、标注。跑分结果 runs/ 和报告 reports/ 不提交。四个非软件例子（盖 shed、北京旅游、数学题、股票）写进 skill 正文作说明，不在本仓库建 gold。推翻 ARD-V 里建 gold 的部分。

ARD-AC — PRD 和文档标准的调整

PRD 的必需章节去掉「非功能需求」；parent PRD 补齐 Overview、Goals and Success Metrics、User Stories、Functional Requirements、Out of Scope。编号在「feature 加文档类型」内唯一，跨 feature 引用写成 <feature>/<编号>。HLD 的架构章节不要求 DSGN 编号。how-to 有定义，但暂不检查。

ARD-AB — 四个 skill（已被 ARD-AJ 推翻）

当时的交付物是四个 skill：spec-pipeline 负责编排，spec-organize 负责标准和检查，spec-review 负责找问题，spec-write 负责改文档。推翻了只列三个 skill 的 ARD-O。

ARD-AA — 多人决定以较晚的为准，否则问

PRD-F 关闭。两个决定冲突时，decision-history 里时间较晚的那条为准；看不出先后，就问用户。AI 不猜谁说了算。推翻 ARD-M。

ARD-Z — PRD 写清五项，再进入下游

取代 pipeline design 的 PIPE-E-B（当时编号 PIPE-E2）里原来没定义的「六项输入」。PRD 要写清限制、偏好、时间、资源、工具五项；不适用的写 not apply，不能留空。PRD、design、decision-history 三篇都存在后，才能开始写 impl-plan 和 test-plan。放弃的方案：用「building」这个词，以及让 PIPE-E-B 指向一个并没有这个定义的 PIPE-F。

ARD-Y — 按 20 小时估算来拆分

暂行规则（pipeline design 的 PIPE-D 第 6 步）。AI 先给出几种拆法。一个人 20 小时内能搞清楚的，算一个 feature spec；AI 估算超过 20 小时的，拆成 peer 或 sub-feature。估算和判断都由 AI 做。建目录仍要等人确认（PIPE-D 第 5 步）。

ARD-X — 执行只做到 mock 调用记录

不真订票，不真交易。mock MCP 客户端调用 mock MCP 服务器，打印出调用记录就算交付成功（PRD-O）。放弃的方案：真实执行，有不可撤回的副作用。

ARD-W — 可读性由本科程序员判断

另一个 LLM 扮演本科程序员。它读懂了才算通过，读不懂就不算交付（PRD-M）。调研时找到过 ISO 24495-1（简明语言标准），但没有拿它来打分。ARD-BO 补上了具体判法。

ARD-V — 难题用同样五篇文档（建 gold 的部分已被 ARD-AD 推翻）

盖 shed、北京旅游、一道著名数学题、分析一只股票，都留在本 PRD（PRD-K），用同样五篇文档。每个子问题写明由谁处理，每个结论引用查到的事实（PRD-L、PRD-N）。放弃的方案：为它们另开一个 feature。仍然有效的部分由 ARD-BT 重述。

ARD-U — spec-pipeline 编排和 Map、state 模型（已被 ARD-AJ 推翻）

当时 SDD 加了 spec-pipeline 作为入口 skill：它调用 spec-organize 和 spec-write，并在提交前提示跑 spec-review。Map 阶段靠和人访谈，产出（怎么拆、记什么决定、草稿）由 AI 判断，没有固定模板。进度先记在 CLAUDE.local，feature 建好后记到 docs/features/<f>/raw/state/。放弃的方案：Map 阶段强制产出固定文件，以及 BMAD 风格的仓库根目录状态树。spec-pipeline 作为入口已被 ARD-AJ 推翻；Create、Map、Converge、Downstream 四个阶段作为参考步骤保留在 pipeline design。仍然有效的部分（访谈、进度记录的位置）由 ARD-BT 重述。

ARD-T — wayfinder-import 不是 SDD 的 sub-feature

wayfinder 导入是另一项工作，属于 skill-factory，不属于 SDD 交付物。spec-driven-development/features/wayfinder-import/ 下的目录删除；需要的话在别处继续。ARD-I 的两份 spec 例外从此只是历史。

ARD-S — gold 可以增长，并有版本号

每次跑分发现的新好例子、新坏例子，追加到 annotations.yaml，同时 gold 版本号加一。分数只在同一个版本内比较。放弃的方案：gold 冻结不变，那样评审中发现的问题就积累不下来。

ARD-R — 两个分数和门槛

MUST 合规分是硬底线，必须满分。对标 gold 的分数按「(加分 − 减分) × 10 / 标注总数」计算，在同一 gold 版本内不能退步。放弃的方案：给对标分设一个固定及格线，因为 gold 升版后分母会变，固定线没有意义。

ARD-Q — 测试放在 skill 目录下

skill 会被装到任意项目里，测试也要跟着走。跨 skill 的检查器、gold、报告放在 spec-organize 下（当时它是主 skill）。放弃的方案：放在仓库根目录 tests/sdd/，那样测试不会跟着 skill 一起部署。

ARD-P — spec-review 也查机械规则

review 输出修改建议，不直接改。机械规则的违反也必须出现在建议里，否则使用者拿到的审查不完整。负责整理的工具可以直接修；review 只找问题、给建议。放弃的方案：review 只看语义，那样就没法用同一套 MUST 来给 review 打分。

ARD-O — skill 是 spec-organize（主）、spec-review、spec-write（已被 ARD-AB 推翻）

交付的 skill 统一用 spec- 前缀，因为它们服务于 spec-driven development，而不是一般的文档编辑。标准文件放在主 skill 里，叫 SPEC-STANDARD.md，延续 ARD-B 的做法。放弃的方案：单独建一个 spec-standard skill，三个使用方多一份要同步的副本。

ARD-N — 产品级成功指标延后

产品级成功指标怎么量、基线是多少，目前没有数据来定，延后到 PRD-G。test-plan 里的分数是评测指标，不是产品成功指标。

ARD-M — 多人决定以谁为准（已被 ARD-AA 推翻）

当时还没想清楚多人决定冲突时以谁为准，先延后到 PRD-F。后来由 ARD-AA 定下规则。

ARD-L — 盲区由现有 skill 发现

research skill 已经有「发现未知」的分支，grill-with-docs 已经会做追问式访谈。PRD-H 要求优先用现有工具。放弃的方案：专门新建一个 skill；在现有做法够用之前不做。以后可以换成新 skill，但「这一步必须跑」的要求不变。

ARD-K — AI 每次只改一小段（「满足其一即可」已被 ARD-BP 推翻）

一次大改动没人细看就进去了，出了问题也难找原因。当时的上限是 10 行或 200 字符，满足其中一条即可；ARD-BP 改为两条都要满足。更大的改动拆成多次。真要大改（restructure）需要人明确同意，ARD-AI 和 ARD-BK 就是这样的授权。放弃的方案：超出上限直接拒绝，会挡住正当的大改；只警告不拦，等于没有限制。

ARD-J — 五种必需文档加一种可选的 how-to

PRD 当时写的是六种必需文档，pipeline-design.md 和文档标准写的是五种。五种是对的：how-to 只在需要人去操作结果时才写，不是每个 feature 都要有。当时把这五种文档叫作「阶段」；现在「阶段」专指 pipeline design 里的 Create、Map、Converge、Downstream 四步，所以这里改称「文档」。放弃的方案：为了和 PRD 一致保留六种必需文档，那样会多出一种大多数 feature 用不到的文档。

ARD-I — 当时有两份 spec 文档（已成历史）

这是对 ARD-F 的「每种类型默认一份」的有意例外，按规则要写明原因，不能悄悄违反。当时这个 feature 以标准本身命名，所以标准的 spec 放在这里；而 wayfinder-import-design.md 已经占了 spec-driven-development/design/，它是另一项有自己生命周期的工作。两份文件按 ARD-G 用名称区分。放弃的方案：给 feature 改名（这个名字已在项目里用开了）；把标准单独放一个 feature（标准和导入当时属于同一项工作）；把两份合成一份（两件不相关的事写在一个文件里）。ARD-T 删除 wayfinder-import 后，这个例外不再存在。

ARD-H — 内容分四个优先级，L1 永远不删

L1 是决定性内容：行为、接口约定、不变量、约束、错误处理、安全规则、架构边界、不在范围内的事项、前提假设、兼容性约束、未决问题。L2 是理由，L3 是放弃的方案，L4 是参考资料。文档需要瘦身时，先删 L4，再删 L3，再压缩 L2，L1 永远不删。

「不在范围内」「前提假设」「兼容性约束」「未决问题」归在 L1 而不是 L2，因为丢掉其中任何一项，实现会和丢掉一条需求一样出错。如果一个事实的权威出处在别的文档，这里只能放链接（L4），不能复述一遍。

ARD-G — 分篇的命名

payment-design-authorization.md        design 分篇：名词，没有顺序
payment-impl-plan-01-schema.md         impl-plan 分篇：序号加阶段，有顺序

放弃的方案：两者都用序号（payment-design-01.md）。序号说明不了内容，插入一篇还要全部重新编号。impl-plan 本身有先后顺序，所以序号有意义；design 按业务边界拆，所以用名词。

ARD-F — 一个 feature 可以有多份 design 或 impl-plan（已被 ARD-BQ 推翻）

后来六种文档都允许拆分篇，见 ARD-BQ。当时的内容：取代原来「每个 feature 每种类型只有一份文件」的规则，只对这两种类型放开，并删掉禁止第二份 spec 的反例。prd、test-plan、decision-history、how-to 仍是一份：它们不会无限变长。design 和 impl-plan 会，既然限制了 1,000 行，就必须允许拆成多份。

ARD-E — 行数上限

旧的指引说 feature spec 一般 500 到 1,500 行，和 1,000 行上限矛盾。以上限为准，删掉旧指引。decision-history 不设上限：它只增不减，删减它就毁掉了它存在的意义；不设上限也就不会有删旧决定的压力。

ARD-D — 字段叫 health，不叫 status

state 字段已经表示写作状态（draft 或 final）。再加一个叫 status 的字段，读者会以为是同一件事，而且它的取值（draft、active、stale、deprecated）和 state 有重叠。放弃的方案：把 state 的取值改成 draft | active | stale | deprecated，那样所有已有文档都要改。

ARD-C — 细节放在 skill 目录的其他文件里

标准有十七节，全部写进 SKILL.md 会超过 700 行，而 skill 需要一次读完。沿用已有做法，例如 domain-modeling/ADR-FORMAT.md 和 domain-modeling/CONTEXT-FORMAT.md。这些文件和 skill 放在同一目录，跟着 skill 一起走，skill 才能装到别的项目；skill 不能指向本仓库的 docs/，因为别的项目里没有这个目录。

ARD-B — 标准放在已有的 skill 里

文档的放置、检查和合并本来就由 doc-organize（后改名 spec-organize）负责，它的 Sync 模式也负责发现不一致。新建一个 skill 就得把文档标准再抄一份。放弃的方案：新建 spec-driven-development skill，doc-organize 只留一个指针；两者会共用类型列表、frontmatter 约定和必需章节，副本迟早会不一致。

ARD-A — 按关注点分权威

原来的规则是「代码是唯一真相」，在 doc-organize 里写了三处。它把所有冲突都判给代码，spec 就保护不了「本来想要的行为」。比如 spec 规定重试 3 次，代码重试了 5 次：按旧规则 spec 是错的，即使 3 次才是需求。

放弃的方案：

  • 继续「代码是唯一真相」：spec 在最需要约束的地方失效，而且通过的测试会被当成需求。
  • 改成「spec 是唯一真相」：反过来也不行，spec 回答不了代码现在实际在做什么，每次重构都得改 spec。
  • 「唯一真相加例外清单」：很难维护，而且默认仍有一方说了算。

采用的做法：按关注点分。想要的行为以 spec 为准，当前实现以代码为准，接口约定以机器可读的定义文件为准，数据库结构以 migration 为准，可执行的验证以测试为准。

Pipeline

Spec-Driven Development — 写 spec 的阶段

本篇讲写一套 spec 要经过哪几个阶段、每个阶段做什么、用哪个 skill。它是参考步骤，不是一个要单独调用的 skill：写或改 spec 从 spec-write 开始，提交前由 spec-write 询问是否跑 spec-review（ARD-AJ）。

文档的格式、路径、编号、行数见 document-standard design，本篇只链过去，不重复。pipeline 没有自己的 PRD 和 test-plan，本篇提到的 PRD-*、TST-* 都指 parent 的 PRD 和 test-plan。术语见 parent design 的术语表。

Problem Statement

parent PRD 讲了上游的问题（见 PRD 的 Problem Statement）。本篇补充写 spec 这个流程本身的问题：

  • 大的需求很难拆成能执行的小 feature，新手不知道先做什么。
  • skill 很多，使用者不知道什么时候该用哪个。
  • 对话一长，就不知道做到哪了、还剩什么。
  • 提交前很容易跳过审查。

Solution

写 spec 分四个阶段，按顺序走：

  1. Create（立项）：给 feature 起一个暂定名，写一份粗略的 PRD，把调研到的背景写进 wayfinder 的地图目录 docs/state/wayfinder-<暂定名>/。feature 目录要等 Map 阶段人确认后才建。
  2. Map（摸底）：和人访谈，弄清已知、未知和盲区；由 AI 判断要不要拆分、要不要记决定、哪些只留草稿。可以用一个可替换的访谈辅助工具（例如 grill-with-docs）；进度记在 wayfinder 的地图里（PIPE-H）。
  3. Converge（收敛）：PRD、design、decision-history 三篇反复打磨，直到满足 PIPE-E 的收敛条件。
  4. Downstream（下游）：从 design 同时写出 test-plan 和 impl-plan，两篇互不依赖（和 parent PRD 的 Solution 一致）。

User Stories

  • 拆分大需求： 作为不熟悉 spec 的人，我希望经过 Map 阶段的访谈后，能把大需求拆成几个小 feature，再一个个写齐文档。
  • 恢复进度： 作为中途离开又回来的人，我希望 AI 给我一份进度回顾（recap）：做了什么、现在在哪个阶段、还剩什么、建议下一步做什么。
  • 提交前提醒： 作为提交改动的人，我希望在准备提交时被问一句：要不要先跑 spec-review。

Implementation Decisions

  • 分工： 标准写在三份标准文件 SPEC-STANDARD.md、SPEC-PRESENTATION.md、SPEC-HTML-STANDARD.md；写文档用 spec-write；审文档用 spec-review。进度规则由 wayfinder 执行。spec-pipeline 和 spec-organize 都不是入口（ARD-CH）。
  • Map 以访谈为主： AI 判断是否要记一条决定、是否建议拆出新 feature、是否只在草稿里留个线索。人确认之后，才创建 docs/features/<f>/ 目录（ARD-CH 重述 ARD-BU）。
  • 访谈辅助可替换： Map 阶段的访谈辅助工具通过 PIPE-G 的推荐表使用，随时可以换。wayfinder 另外负责进度规则，是交付物（ARD-CH）。
  • 进度记在哪： 进度记在 wayfinder 的地图目录里，规则见 PIPE-H（ARD-CH）。
  • 进度回顾不是正式记录： recap 是生成给人看的，不是真相来源。真相来源是进度文件加上已提交的文档。
  • 不引入重框架： 后期的任务管理接入别的 skill，本篇不引入 BMAD、GSD 这类完整的项目管理框架。
  • 协作： 读上游文档，不悄悄改。发现冲突时按「发现、报告、问人」处理（document-standard 的 DSGN-G）。
  • 编号： 本篇的规则编号用 PIPE- 前缀；DSGN 留给 document-standard。
  • 子问题归属表不适用： 本篇是纯流程的 design，PIPE-L 允许这样注明。还没定的事项和它们的负责人见 Open Questions。

Design

PIPE-A — 流程必须做到的事

来源：PRD-A（在现有流程上改进，不另造一套）；PRD-J（从 spec-write 开始，提交前询问是否审查，进度记在哪）。

  • PIPE-A-A：任何「写或改 spec」的任务，都从 spec-write 开始，先按 SPEC-STANDARD.md 判断要新建哪篇、还是改哪几篇（ARD-AJ）。
  • PIPE-A-B：路径和格式按文档标准检查。检查由检查脚本 run_spec_checks.py 或 spec-organize 的 Lint 模式执行。
  • PIPE-A-C：文档内容的增删改由 spec-write 做。格式类 MUST 的问题（例如标题写法、frontmatter 字段）可以由 spec-organize 的 Lint 模式直接修。两者都遵守 parent design 的 DSGN-A（每次改动的大小上限）（ARD-BV）。
  • PIPE-A-D：提交或推送已提交文档的改动之前，询问是否先跑 spec-review。用户说不跑，就把这个选择记下来，不能悄悄跳过。
  • PIPE-A-E：用户要求，或者对话中断后重新开始时，给出进度回顾：做了什么、现在的进度、还剩什么、建议下一步。
  • PIPE-A-F：维护和读取 PIPE-H 定义的进度记录；按 PIPE-G 的表推荐 skill。

PIPE-A-D、PIPE-A-E、PIPE-A-F 由 wayfinder 执行（ARD-CH）。

PIPE-B — 四个阶段总览

阶段 目的 常见的失败
Create 定暂定名，收集背景 粗略 PRD 和背景没写进地图，只存在聊天记录里
Map 弄清已知和未知，判断要不要拆 没访谈就建目录
Converge PRD、design、decision-history 打磨到足够稳定 还有没定的决定，design 就写死了
Downstream 同时写 test-plan 和 impl-plan test-plan 没有回归检查；impl-plan 没有先后顺序

PIPE-C — Create（立项）

  1. 给 feature 起一个暂定名，新建地图目录 docs/state/wayfinder-<暂定名>/，CLAUDE 层只记它的路径。这时还不建目录，目录在 Map 阶段人确认后才建（PIPE-D 第 5 步）。
  2. 写一份粗略的 PRD，例如「推荐一台 iPhone 并协助购买」。这时还没有目录，粗略 PRD 先写在地图的 map.md 里；不要求一次写齐 PIPE-E-B 的五项。
  3. 把搜索和调研得到的背景也写进地图。目录建好以后，粗略 PRD 要整理成已提交的 PRD，地图不能代替它。

PIPE-D — Map（摸底）

  1. 访谈用户（评测时用 context 包代替用户），由 AI 整理出已知和未知。
  2. AI 判断下一步，没有固定要产出的文件：是否建议拆出新 feature、哪些结论以后要记成决定、是否只在草稿里留个线索，还是先不拆，直接进入 Converge。要记的决定先列在地图文件里，第 5 步建好目录后再写进 decision-history。
  3. 给出 Map 的结论回顾：判断的要点、建议的拆法、还没定的事项。
  4. 可选：调用一个可替换的访谈辅助工具（例如 grill-with-docs），但它不能代替访谈。
  5. 人确认拆法和名字之后，才用 walter-worker 的 feature create 命令建 docs/features/<f>/ 目录；要不要放进 parent 的 features/ 下面，见 parent design 的「目录结构」一节。没有人确认，也不能移动已提交的文档（ARD-CH 重述 ARD-BU）。
  6. 拆分标准（暂行）：AI 先给出几种拆法。一个人 20 小时以内能搞清楚的，算一个 feature spec；AI 估算超过 20 小时的，拆成 peer feature 或 sub-feature。估算和判断都由 AI 做（ARD-Y）。
  7. 子问题（PRD-L）：每个子问题标明「AI 查」「人决定」或「AI 查完人决定」。人没问到的盲区和风险，AI 必须主动提出来。

PIPE-E — Converge（收敛）

PRD、design、decision-history 三篇反复打磨（见 parent PRD 的 Solution）。下面三个条件全部满足，才能进入 Downstream：

  • PIPE-E-A：没有阻塞的未决问题。每个未决问题都写在本 feature 的问题清单里，并在「阻塞」一列标明是或否。只要还有标「是」的问题没解决，就不能进入 Downstream；由 wayfinder 检查（ARD-CH）（ARD-AG）。
  • PIPE-E-B：PRD 写清了限制、偏好、时间、资源、工具五项；不适用的写 not apply，不能留空。design 和 decision-history 两篇都已存在（ARD-Z）。
  • PIPE-E-C：design 列出了它依赖的决定和还没定的事项，并写清了实现需要的接口和边界。实现任务的细节留到 Downstream 再定。

PIPE-F — Downstream（下游）

  • test-plan 和 impl-plan 同时开始写，互不依赖，都从 design 总结出来。
  • PIPE-F-A（test-plan）：每个任务都有完成检查和回归检查。回归检查用来确认改动没有弄坏原来能用的功能。
  • PIPE-F-B（impl-plan）：每个任务写明依赖谁、挡住了谁；被挡住的后做，没被挡住的先做。

PIPE-G — 每个阶段推荐的 skill

阶段 场景 推荐 是否必须
Map 结束、人确认后 建 feature 目录 walter-worker 的 feature create 必须
Create 补充背景 research（举例） 可选
Map 摸底、辅助拆分 可替换的访谈辅助工具（例如 grill-with-docs） 可选
Converge 写或改文档 spec-write 有改动时必须
Converge 检查路径和格式 run_spec_checks.py 或 spec-organize 的 Lint 新建、移动、合并文档后必须
任何阶段 提交前 spec-review 询问（PIPE-A-D）
Downstream 写 test-plan 和 impl-plan spec-write，加上路径和格式检查 必须

Map 阶段的访谈辅助工具随时可以换；wayfinder 负责进度规则，是交付物（ARD-CH）。

PIPE-H — 进度记录

来源：PRD-J、ARD-CH。进度记录就是 wayfinder 的地图目录：map.md 加 issues/ 下每个 brief 一个文件。每个 feature 一个，任务再小也建，都不提交。

时段 记在哪 记什么
feature 名字还没定 docs/state/wayfinder-<暂定名>/ 阶段、粗略需求、Map 笔记、未定事项
feature 名字已定 docs/features/<f>/raw/state/wayfinder/（目录建好后整个移过来） map.md 开头写 phase（Create、Map、Converge、Downstream 之一）、feature、last_action；未关闭的 brief 就是未完成事项
  • 进度回顾读取进度记录和已提交的文档，发给用户看；回顾本身默认不提交。
  • 有方向性的结论，要正式写进 decision-history、PRD 或 design，不能长期只留在进度记录里。

PIPE-I — 协作、来源和齐备

  • 读上游文档，不悄悄改；有分歧就报告并问人（document-standard 的 DSGN-G）。
  • 多人的决定冲突时，以 decision-history 里时间较晚的为准；看不出先后就问用户；AI 不猜（PRD-F）。
  • 决定变了，要点名哪些下游文档需要复查：PRD、design、impl-plan、test-plan。
  • parent 和 sub-feature 的齐备要求见 parent design 的 DSGN-E：parent 五篇都要有，sub-feature 不要求。这件事由 spec-review 检查，本篇只转交，不重复规则。

PIPE-J — 本篇管什么、不管什么

本篇管 本篇不管
阶段、入口、skill 推荐、进度记录、进度回顾、提交前询问 frontmatter、路径、编号的细则（见 document-standard）
收敛条件、下游两篇同时写 辅助工具和 research 等 skill 的正文
轻量的进度记录 完整的任务管理框架（BMAD、GSD 这类）

PIPE-K — 非软件问题对应到五篇文档

依据 PRD-K、PRD-Q：非软件的难题也用同样五篇文档，不新增文档类型。

内容 放在哪
调研、学习笔记、原始资料 raw/research/<主题>.md（不提交，不算权威）
决定 decision-history（ARD-*）
方案、执行步骤 design；需要排先后顺序的执行步骤放 impl-plan
验证 test-plan

raw/ 里的结论要正式写进文档时，在文档里用一句话写出结论，并链到 raw/ 文件作依据，不把草稿整段搬进来（ARD-BW）。

执行只做到 mock（PRD-O）：所有例子共用一个 mock MCP 服务器，打印出调用记录就算成功，不真下单、不真订票（ARD-X）。四个例子（盖 shed、北京旅游、数学题、股票）写进 skill 正文，不在本仓库建 gold。

PIPE-L — 子问题归属和证据

来源：PRD-L（子问题归属）、PRD-N（结论要有依据，查不到写 UNKNOWN）。

有子问题的 feature，它的 design 必须有一张「子问题归属」表。纯标准或纯流程的 design 可以注明不适用。

子问题 归属 依据
<问题> AI 查、人决定 或 AI 查完人决定 raw/ 路径（其他读者打不开也可以，ARD-BW）、网址或 ARD-* 编号
  • 归属只能是这三种之一。人没问到的盲区和风险，AI 必须主动加行。
  • 依据必须能追溯；查不到写 UNKNOWN，不能写推测。
  • spec-review 检查两种问题：有结论却没有依据；该写 UNKNOWN 的地方写成了事实。
  • 允许：如果每个子问题都已经是问题清单里的一行，并且每行都有负责人和依据，design 可以只放一个链接，不再抄一张表（ARD-AY）。

  • PRD-N：正式结论链到事实；评测时答案只能来自 context 包。
  • PRD-O：所有例子共用一个 mock MCP 服务器，打印出调用记录就算通过。

Document Standard — 文档标准

本篇规定 docs/features/ 下的 feature 文档怎么写：有哪几种文档、放在哪、叫什么名字、最长多少行、开头写什么、必须有哪些章节、编号怎么起、出现矛盾以谁为准。本篇不规定 skill 怎么拆文件、怎么加载这些规则，那属于实现。

相关文档：

  • 写 spec 分几个阶段，见 pipeline design。
  • 怎么测试，见 parent 的 test-plan。被测的是 spec-write、spec-review 和 wayfinder 三个 skill；本篇的每条 MUST 都收进 MUST 清单，由测试逐条检查。
  • 术语和缩写，见 parent design 的术语表。

本篇的规则小节用 DSGN 编号，只在 document-standard 这个 feature 内有效：

编号 讲什么
DSGN-A 文档契约总览，包含下面的 DSGN-B 到 DSGN-F
DSGN-B 文档类型、目录、文件名、行数上限、怎么拆分
DSGN-C 哪些文件不能提交
DSGN-D INDEX 和 book 这两层派生内容
DSGN-E frontmatter、必需章节、Decision Log 和 Change Log 的格式
DSGN-F 编号规则，以及怎么改已有正文
DSGN-G 冲突时以谁为准（按关注点分权威）
DSGN-H design 文档写什么、不写什么
DSGN-I 内容的四个优先级（L1 到 L4）
DSGN-J decision-history 怎么写
DSGN-K 名字撞车时怎么处理
DSGN-L 检查和整理文档的几种模式
DSGN-M 质量门槛：哪些是 MUST，哪些是 NICE
DSGN-N 给人读的 reader HTML，见分篇

Problem Statement

feature 文档一多，如果没有统一标准，会出现四类问题：

  • 两份文档说法不一致时，不知道以哪份为准，AI 就会悄悄改掉其中一份。
  • 文档放得到处都是，找不到。
  • 分不清一份文档是「过时了」还是「写错了」。
  • 同一个事实写在好几处，改了一处，其他几处还是旧的。

Solution

用一份契约规定所有文档共同遵守的格式，再用几条补充规则处理语义和流程上的问题：

  • 契约（DSGN-A，包含 DSGN-B 到 DSGN-F）：类型、路径、行数、不能提交的文件、INDEX 和 book、frontmatter、章节、编号。大多数 MUST 规则在这里，脚本可以自动检查。
  • 补充规则（DSGN-G 到 DSGN-L）：冲突以谁为准、design 写什么、内容优先级、决定怎么记、撞名怎么办、检查模式。这些多数要靠 spec-review 判断。
  • 质量门槛（DSGN-M）：把上面的规则分成 MUST 和 NICE。

User Stories

  • 作为写 spec 的人，我想知道文档放在哪、叫什么、最长多少行、哪份说了算。
  • 作为审 spec 的人，我希望格式规则能由脚本检查；内容上的问题只报告，不被悄悄改掉。
  • 作为 AI，我希望 frontmatter、编号、Change Log 的规则写得明确，不用猜。

Implementation Decisions

  • 本篇的规则会摘要写进 SPEC-STANDARD.md 和 SPEC-PRESENTATION.md；reader design 的规则摘要写进 SPEC-HTML-STANDARD.md。spec-write 和 spec-review 读的是这三份摘要（ARD-CH 重述 ARD-BX）。摘要和本篇不一致时，先改本篇，再改摘要。
  • 格式类的 MUST 由检查脚本执行；内容类的问题由 spec-review 报告。
  • how-to 暂不做机械检查；其他五种文档按 DSGN-E 检查。
  • 已有的不合规文档不迁移，只报告（ARD-CK，重述 ARD-AF）。
  • 本篇是一份纯标准，「子问题归属表」不适用（pipeline design 的 PIPE-L 允许这样注明）。还没定的事项和它们的负责人见 Open Questions。

Design

DSGN-A — Document Contract

文档契约由下面五条组成：DSGN-B 规定类型和路径，DSGN-C 规定哪些不能提交，DSGN-D 规定 INDEX 和 book，DSGN-E 规定格式，DSGN-F 规定编号。

DSGN-B — 文档类型、目录、文件名、行数上限、拆分

来源：parent PRD 的 PRD-D（行数上限）和 PRD-E（目录、文件名、目录之间的关系）。

<f> 表示 feature 的名字，用小写字母和连字符（例如 spec-driven-development），并且要和文件名里的 feature 部分一致。

feature 有两种放法：

放法 根目录 frontmatter 里的 feature 写什么
普通 feature docs/features/<f>/ <f>
sub-feature docs/features/<parent>/features/<sub>/ <sub>，也就是 sub-feature 自己的名字

sub-feature 的例子（parent 是 spec-driven-development，sub-feature 是 document-standard）：

  • 入口 design：.../document-standard/design/document-standard-design.md
  • design 分篇：.../document-standard/design/document-standard-design-<名词>.md
  • 调研笔记：.../document-standard/raw/research/<主题>.md
  • 进度快照：.../document-standard/raw/state/state-<YYYY-MM-DD>.md
  • 同级的另一个 sub-feature：.../pipeline/design/pipeline-design.md

文件名规则（MUST）。 提交的文档必须放在对应类型的目录里，文件名以 <f>-<type> 开头。有两种例外：raw/ 下的文件；被某篇文档引用的辅助文件，它放在 docs/features/<f>/<type>/<来源名>.md，行数上限和它所在的类型相同。不允许单独建一个 reference/ 类型；外部资料放在辅助文件里，或者放进 raw/。

六种类型，每种放在哪、叫什么：

类型 写什么 目录 入口文件名 分篇文件名
prd 做什么、为什么 docs/features/<f>/prd/ <f>-prd.md <f>-prd-<名词>.md
design 怎么做 docs/features/<f>/design/ <f>-design.md <f>-design-<名词>.md
impl-plan 任务和先后顺序 docs/features/<f>/impl-plan/ <f>-impl-plan.md <f>-impl-plan-<两位序号>-<阶段>.md
test-plan 怎么验证 docs/features/<f>/test-plan/ <f>-test-plan.md <f>-test-plan-<范围>.md
decision-history 所有决定 docs/features/<f>/decision-history/ <f>-decision-history.md <f>-decision-history-<两位序号>-<时期>.md
how-to 怎么使用、怎么运维 docs/features/<f>/how-to/ <f>-how-to.md <f>-how-to-<场景>.md

这六种都要提交到 git。六种都可以拆分篇；有分篇时，必须有入口文件 <f>-<type>.md，入口文件链到各分篇（MUST，ARD-BQ）。分篇的命名规则：prd、design、test-plan、how-to 用名词，说明这篇讲哪个方面；impl-plan 和 decision-history 用「序号加阶段或时期」，因为它们有先后顺序（ARD-G）。

行数（MUST）。 parent PRD 的 PRD-D 规定，除 decision-history 外，任何文档不超过 1,000 行。各类型的具体数字：

类型 建议行数 上限（MUST）
prd 150–400 800
design 200–500；整体架构类 500–900 1,000
impl-plan 100–500 1,000
test-plan 200–600 800
decision-history 不设 不设（ARD-E）
how-to 100–350 600
raw/ 下的文件 最好不超过 2,000 不设

上限包括 frontmatter 和 Change Log。超过上限就算失败，处理方法是：

  1. 先按 DSGN-I 删减：从 L4 开始删，L1 永远不删。为了凑行数删掉 L1，本身就是错误。decision-history 不删条目，只能拆分篇。
  2. 删减后仍然超过，就拆成分篇。按业务边界、领域、负责人、生命周期或时间段来拆，不要按行数机械地切。
  3. 入口文件必须链到各分篇（ARD-BQ）。拆分时如果名字撞车，见 DSGN-K。

raw/ 目录。 raw/ 放本地草稿，在 .gitignore 里用 docs/features/**/raw/ 排除；两个星号表示任意层级，sub-feature 下的 raw/ 也被排除。这里的文件不需要 frontmatter、Change Log，也不进 INDEX。草稿里的结论要正式写进文档时，在正式文档里写结论并链到草稿。草稿可以作为依据，即使其他读者打不开（ARD-BW）；但它不是权威出处，权威的是写进正式文档的那句结论。

子目录 放什么 文件名
raw/research/ 调研的原始输出 <主题>.md
raw/review/ AI 临时做的审查记录 <YYYY-MM-DD>-<审查者>-<对象>.md
raw/design/ 还没写进正式 design 的草稿 <YYYY-MM-DD>-<对象>.md
raw/evidence/ 证据、工具输出 <YYYY-MM-DD>-<简称>.md
raw/discussion/ 讨论记录（可选） <主题>.md
raw/state/ 进度快照，用来在长对话被压缩后恢复上下文 state-<YYYY-MM-DD>.md（最多 400 行）；SDD 的进度用 raw/state/wayfinder/ 地图目录（parent ARD-CH）

旧项目里直接放在 feature 根目录的 state/、research/、discussion/，挪进 raw/。工单草稿放在 .scratch/<feature>/，同样不提交。

DSGN-C — 不能提交的文件
路径 说明
docs/features/<f>/raw/** 整个草稿目录，包括 raw/state/
docs/state/ 名字没定时的 wayfinder 地图目录（parent ARD-CH）
.scratch/<feature>/ 工单等临时文件。它不在 docs/features/ 下，但同样不能提交

这些路径必须写进 .gitignore 或用等效的办法排除。误提交算违反 DSGN-M 的 MUST。这些文件不需要 frontmatter、Change Log，也不进 INDEX。

本地翻译副本（MUST）。 <name>.<lang>.md 这样的翻译副本只放在本地，不提交。副本开头写明以 <name>.md 为准；副本里的标题可以翻译（ARD-AU）。

DSGN-D — INDEX 和 book

docs/features/ 里已提交的文档是唯一的真相来源。INDEX 和 book 都是从它们派生出来的，不用 DSGN-E 的 frontmatter 和 Change Log，也不能在里面写新的决定。

INDEX book
回答什么问题 文档在哪：路径、类型、feature 结构 文档讲了什么：短摘要，帮人和 AI 决定要不要打开原文
粒度 一行一个链接加标题，可以带一句说明 每篇或每组文档一段摘要，链回原文

docs/INDEX.md 是什么。 它是所有 feature 文档的地图：每个 feature 下有哪些 PRD、design、计划，各在什么路径。人、AI、脚本找文档时，先查 INDEX，再打开 docs/features/ 里的原文。INDEX 不是 design，在 INDEX 里改标题或链接不等于改需求，INDEX 里也不写设计结论。

INDEX 怎么维护：

  • 整个文件由脚本重新生成。要改内容就改生成脚本或模板，不要长期手工一行行改。
  • 任何已提交的文档新建、移动、改名、删除之后，都要重新生成 INDEX，并且和那次文档改动一起推送。
  • 只列已提交的文档，包括 sub-feature 的文档；不列 raw/ 和 .scratch/。
  • 按 feature 分块，块内按类型排序：prd、design、impl-plan、test-plan、decision-history。链接写成相对 docs/ 的路径。
  • 质量要求（MUST）：磁盘上有、INDEX 里没列的，叫孤立文档；INDEX 里列了、磁盘上没有的，叫死链。两种都不允许。

docs/book/ 是什么。 它是从 feature 文档组装出来的摘要层，用短说明写清每份 PRD、design、计划覆盖什么、结论是什么、去哪里读全文，主要帮 AI 检索和挑选要读的文档。人和 AI 先扫 book，再打开原文。book 不是真相来源，不是全文拷贝，也不能和原文各自手工维护同一个事实。

book 写什么：

  • 每条摘要都链到对应的原文路径。
  • 写这篇的范围和主要结论或状态，不展开 L1 的全文。
  • 新增或修改决定时，只改 feature 文档和 decision-history，然后重新生成 book；不能只在 book 里改说法。

book 什么时候更新：

  • docs/features/ 下已提交的文档有改动并推送到 GitHub 时，同一次推送里（或紧挨着的前一个 commit）应该已经重新生成了对应的 book 和 INDEX。具体用 pre-push hook、CI 还是手动，属于实现。本标准只要求远端能看到的文档和 book、INDEX 保持同步，避免 AI 在 GitHub 上读到新 spec，摘要却还是旧的。
  • 原文还是 state: draft 时，可以暂不更新摘要；final 或已合并的改动必须反映到 book。

其他：

  • book 在 docs/book/ 下，不用 DSGN-E 的 frontmatter。检查只看链接是否有效、摘要指向的文件是否存在。
  • HTML 页面在 docs/book/html/，目录结构和 docs/features/ 一样。HTML 也不是真相来源（ARD-BF）。
  • book 可以另外用来发布 MkDocs 或 GitHub Pages 网站。网站的导航怎么排属于实现，但不能和 feature 目录、INDEX 矛盾。

另外两个不算 feature 文档的文件，同样不用 frontmatter，检查只看链接：CONTEXT.md（领域术语表）和 README.md（仓库说明）。

DSGN-E — 格式

frontmatter（MUST）。 每篇已提交的文档开头都有：

---
feature: <feature-name>
type: prd | design | impl-plan | test-plan | decision-history | how-to
state: draft | final
final_date: YYYY-MM-DD   # state 是 final 时必填
---

可选字段：spec_id、version、health（active、stale 或 deprecated）、owner、last_verified、audience（internal 或 external，ARD-AL）。表示文档健康状况的字段叫 health，不叫 status（ARD-D）。

必需章节（MUST）。 每种文档必须有下面这些 ## 章节。标题用英文原文，不翻译、不编号、不改名、不删；可以另外加章节。比如把 Overview 写成 ## 1. 概述 就违反规则。其他章节只有写有序步骤时才编号；例外是 Problem Statement 下面作者原话的小标题可以保留编号（ARD-BS）。

类型 必需章节
prd Overview, Goals and Success Metrics, User Stories, Functional Requirements, Out of Scope, Resources Needed
design Problem Statement, Solution, User Stories, Implementation Decisions, Design, Testing Decisions, Out of Scope, Further Notes, Alternatives Considered, Drawbacks, Risks and Mitigations, Open Questions, Reversibility
impl-plan Global Constraints, Acceptance Criteria，以及每个任务一节 ## IMPL-*
test-plan Test Cases, Test Execution Order, Expected Pass Threshold
decision-history Decision Log, Evidence Appendix
how-to Overview, Prerequisites, Steps, Verification
  • how-to 暂不做机械检查，其他五种按本表检查。
  • design 拆成多篇时，13 个必需章节只要求写在入口文件；分篇在开头链回入口，只写自己那部分（ARD-AV）。
  • 某个必需章节对这篇确实不适用，就保留标题，正文写一句「不适用」并说明原因，或者链到写着这件事的地方。

几个章节的意思。 这几个章节借鉴自 Kubernetes 的设计提案模板（KEP）和 Rust 的 RFC 模板：

章节 写什么
Alternatives Considered 考虑过但放弃的方案，以及放弃的原因
Drawbacks 选定的方案本身有什么缺点
Risks and Mitigations 用起来可能出什么问题，怎么应对。和 Drawbacks 分开写
Open Questions 还没解决的问题，每个都有负责人
Reversibility 怎么撤回、怎么回到原来的状态（对应 KEP 的升级降级）
Acceptance Criteria 做到什么程度算完成（对应 KEP 的 Graduation Criteria）
Resources Needed 需要哪些资源（对应 KEP 的 Infrastructure Needed）

KEP 里的版本偏移、发布签核、运维就绪问卷不采用：它们是为集群运维设计的，不适合非软件问题（parent PRD 的 PRD-Q 要求方法通用）。

impl-plan 正文（MUST，由 spec-write 执行）。 每个 IMPL-* 写明三件事：依赖哪个任务、挡住了哪个任务、完成标准。依赖和挡住要两头对得上：A 写了挡住 B，B 就要写依赖 A。最后的执行顺序把被挡住的任务排在后面，例如先改数据库，再改用到它的接口。优先级高又没被挡住的先做；互不相挡的可以同时做。先做只读的部分，再做会写入的部分；对方的接口还没上线时，写明用什么 mock 代替（ARD-AT）。

引用代码（MUST）。 写「某文件第几行」时，同时写明是哪个 commit（ARD-AQ）。

未决问题清单（MUST）。 每个 feature 只有一份未决问题清单，一般是 design 的 ## Open Questions；其他文档链过去，不抄一份。每个条目编号是 QUES- 加字母，写明问题、目前答案、负责人，以及是否阻塞（ARD-AO、ARD-AG）。在别处提到某个问题时，写的「未决」或「已决」要和清单一致（ARD-BC）。

可读性（MUST）。 来源：parent PRD 的 PRD-M。一个本科水平的程序员，只读这一篇和术语表，就要能读懂（ARD-BO，由 parent test-plan 的 TST-V 检查）。具体要求：

  • 写完整的句子。关键词串、A → B → 失败 这样的箭头链、塞满缩写的表格格子，都不算句子。
  • 每个术语和缩写，第一次出现时解释，或者链到术语表。整套 spec 只有一份术语表，在 parent design 的附录；新术语加到那里。
  • 正文可以中英文混合，只要读着通顺；英文术语同样要解释或收进术语表。Problem Statement 可以保留作者原话（ARD-BS）。
  • 必需章节的标题和编号用英文。

插图（MUST）。 图里不写正文没有的事实，也不和正文矛盾；L1 内容不能只出现在图里。spec-review 发现时报严重度 3，并写出 SVG 文件名（ARD-CA）。

Decision Log（MUST）。 表头是 ID | Date | Decision，可以加第四列 Ready；不能有 Status 列和 Supersedes 列（ARD-AX）。最新的决定写在表的最上面。

Change Log（MUST）。 每篇文档的最后一节，只往末尾追加，不改旧行。

其他： 夹在 <!-- PROTECTED --> 和 <!-- END PROTECTED --> 两行注释之间的段落是受保护的，任何工具在任何模式下都不能改。文档新建、删除、移动后，重新生成 INDEX。

DSGN-F — 编号，以及怎么改已有正文

需要被引用的条目都用「前缀加字母」编号，字母按 Excel 列号的顺序：A 到 Z，接着 AA 到 AZ，再 BA……可以在已有条目之间插入新编号。

文档类型 前缀 例子
prd PRD PRD-A、PRD-AA
design DSGN（pipeline design 用 PIPE） DSGN-A、PIPE-B
decision-history ARD ARD-A、ARD-AA
impl-plan IMPL IMPL-A
test-plan TST TST-A
未决问题 QUES QUES-A

编号永不改（MUST）。 一个编号一旦写进文档（表格、标题、正文、外部链接），就永远不变：不改字母、不改前缀、不「修正拼写」、不重新编号、不把一个条目并进另一个。用过的编号即使条目已作废，也不再给别的条目用。说法变了，就起一个新编号，旧的按 DSGN-J 处理。

迁移时留对照（MUST）。 如果确实必须改编号（例如修正不合规的编号，要记一条 ARD），保留一张新旧编号对照表。标题改名时，把旧锚点留在新标题上方，旧链接才不会失效（ARD-AP）。

凡是要被引用的都要编号（MUST）。 需求、design 的规则小节、实现任务、测试用例、延后或未决的问题，都必须用上表的格式。不能用纯数字（0001），也不能用 PRD-1、FR-3、OQ-1、QUES-1、D1 这类数字编号。一个规则小节下面的子条款，可以在后面再加一个字母，例如 DSGN-N-A，只在本篇内使用。

编号的范围（MUST）。 编号在「同一个 feature 的同一种文档」里唯一。引用别的 feature 的编号时写成 <feature>/<编号>，例如 document-standard/DSGN-B，或者在句子里写明是哪个 feature。不带 feature 的编号只在本 feature 内有意义。

整体设计的例外。 parent 的整体设计（HLD）里讲架构的章节不需要编号，只有可以被引用的规则小节才要编号（ARD-AC）。

检查方法。 ids.py 检查文档里有没有 PRD-1 这类数字编号，有就报错。

改已有正文（MUST，由 spec-write 执行）。 正文只写现行规则：不再成立的句子直接改写，在新句后面链到推翻旧说法的 ARD。删除线只用在 decision-history，正文的旧版本从 git 历史里找。错别字直接改（ARD-BM、ARD-AS）。

AI 每次改动的大小上限（不超过 10 行，并且不超过 200 字符）不归本篇管，见 parent design 的 DSGN-A。

DSGN-G — 冲突时以谁为准

不设一个「全局唯一的真相来源」，而是按关注点分：每类事实认一份文档为准。两份文档不一致时，按「发现、报告、问人」处理：不能悄悄改掉其中一份，也不能默认 design 一定比代码对。

关注点 以谁为准
想要的行为 feature 的 design 文档
接口约定 OpenAPI、protobuf、GraphQL、JSON Schema 等机器可读的定义文件
数据库结构 migration 或 schema 文件
当前实现 代码
可执行的验证 测试

design 管「想要怎样」，代码管「现在怎样」和内部结构。机器可读的接口定义不要整段抄进 markdown，链过去或者自动生成。测试是验证手段，不能代替需求。文档变成 final 后只做维护性修改，不整篇重写；人明确授权并记成 ARD 的大改除外（例如 2026-11-20 的整理，见 parent decision-history 的 ARD-BS，它重述了 ARD-BK）。

DSGN-H — design 写什么、不写什么

写： 系统的行为、接口约定、不变量、约束、错误怎么处理、状态怎么变化、和外部怎么交互、架构边界（包括画图）。

不写： 类的层级结构、私有方法、框架内部的细节。按 DSGN-I 删减时，这些本来就不该出现。

判断方法： 如果实现可以改、而外部看到的行为不变，那这部分就不该写进 design。

AI 读文档的顺序： 全局规则、领域 design、架构、接口约定、例子和测试、代码。如果回答一个很窄的问题也要读完整篇 design，说明 design 的边界划得不对，应该重新拆分。

行数和拆分见 DSGN-B，编号见 DSGN-F。

DSGN-I — 内容的四个优先级

文档需要变短时，按 L4、L3、L2 的顺序删减或压缩，L1 永远不删。删减后仍然超过上限，就按 DSGN-B 拆分篇（ARD-H）。

级别 包括什么 删减时
L1 决定性内容 行为、接口约定、不变量、错误处理、安全规则、边界、不在范围内的事项、前提假设、兼容性约束、未决问题 永远不删
L2 理由 为什么这样设计 可以压缩
L3 放弃的方案 为什么不选另一种做法 先删
L4 参考资料 引用、原始输出、例子 先删；已经在别处写过的事实，只能放链接

DSGN-J — decision-history 怎么写

它是什么。 decision-history 是所有决定的索引加正文：Decision Log 一行一条，Evidence Appendix 每条一节（格式见 DSGN-E）。它不是 PRD 或 design 的摘要。

顺序。 新决定写在 Decision Log 的最上面，越往下越早。

每条都有一节说明（MUST）。 每条 ARD 在 Evidence Appendix 里有一节，写明原因；当时考虑过别的做法，就写出放弃了哪些、为什么。

编号。 ARD- 加字母（DSGN-F），分配后不能改。表格里的编号和 ### ARD-A — … 小节标题里的编号一致。

推翻旧决定。 旧行不删，用删除线划掉，后面链到新决定，例如：被划掉的旧说法，后面跟一个指向新决定的链接。新说法用一个新编号完整写一条，放在 Log 最上面。按 DSGN-I 删减时，不删被划掉的文字。只推翻旧决定的一部分时，也划掉整行，并在新决定里重述仍然有效的部分（例如 ARD-BT）。这是整套 spec 里唯一使用删除线的地方（ARD-BM）。

拆分篇。 decision-history 不设行数上限，但也可以拆分篇。拆了之后编号在整个 feature 内唯一；新决定写在当前那篇的 Log 最上面；旧篇保留，篇与篇之间用链接连起来。

什么时候加一条。 规则只写在一处：parent design 的 DSGN-B。另外，改名、撞名这类流程要求记录的事（DSGN-K）也要加一条。

DSGN-K — 名字撞车时怎么处理

新建 feature 或文件时，必须和已有的名字比一比。符合下面任何一条，就算撞车：

情况 例子
大小写、符号统一后相同 Payment 和 payment
一个名字包含另一个 auth 和 auth-service
单复数或常见缩写 doc 和 docs
只差两个字符以内 payment-api 和 payments-api

怎么处理：

  • 属于同一块业务：合并成一个 feature，再按方面拆 design 分篇。
  • 不同业务但容易混淆：两边都改名，并在 decision-history 里记一条。
  • 同一个 feature 内的文件撞名：给分篇换一个更准确的名词，或者给 feature 改名。

改名本身就是一个决定：要更新所有指向它的链接，不能悄悄改。

DSGN-L — 检查和整理文档的几种模式

模式 由谁执行 做什么
Organize spec-organize 按顺序处理：确定 feature 和类型、检查撞名、路径和文件名、frontmatter 和章节、Change Log、INDEX
Lint spec-organize 扫描 docs/features/；格式类的 MUST 直接修；内容上的问题只报告
Consolidate spec-organize 先提出合并方案，人批准后再合并；所有决定都保留；raw/ 里的旧内容要么被引用，要么删除
Sync spec-organize 找出文档和代码不一致的地方，按 DSGN-G 判断以谁为准；内容冲突只报告
Review spec-review 和 Lint 一样找问题（格式 MUST 加内容问题），但不改，只输出带严重度的修改建议

设计本身是否合理，由 Review 的内容审查负责，不属于本标准的 MUST。

DSGN-M — 质量门槛

MUST，做不到就算失败：

  • DSGN-A 契约全部满足，包括编号永不改、永不复用（DSGN-F）。
  • 冲突不能悄悄处理（DSGN-G）。
  • 不删 L1（DSGN-I）。
  • 合并文档时不丢任何决定。
  • 不能提交的路径没有被提交（DSGN-C）。
  • INDEX 没有孤立文档和死链；文档里的链接和锚点都能打开（ARD-AP）。指向 raw/ 的链接不算死链（ARD-BW）。
  • 推送 docs/features/ 的改动时，INDEX 和 book 已经同步。
  • 新名字已经检查过撞车（DSGN-K）。
  • 正文改动遵守 DSGN-F 的「改已有正文」规则。
  • 结论有依据，查不到写 UNKNOWN（pipeline design 的 PIPE-L）。
  • DSGN-E 里标了 MUST 的四条都满足：impl-plan 的任务写明依赖、挡住和完成标准；引用代码写明 commit；每个 feature 只有一份未决问题清单；文档能让本科程序员读懂。
  • 本地翻译副本不提交（DSGN-C）；改编号时留对照表和旧锚点（DSGN-F）；每条 ARD 都有说明（DSGN-J）。
  • 图不写正文没有的事实，也不和正文矛盾（DSGN-E 的「插图」）。

NICE，做不到只提醒（ARD-BN；下面的 ARD 都在 parent 的 decision-history 里）：

  • 标题层级不跳级；术语和 CONTEXT.md 一致；last_verified 不要太旧；文档边界划得合理。
  • 每节写明哪份文档对这些事实有权威（ARD-AL 的后半句）。
  • 步骤编号只表示位置（ARD-AM）。
  • 决定的就绪程度可以写在条目里，同一行可以原地修订，未决事项按负责人分组（ARD-AN）。
  • 不变量写成表格，不写成口号（ARD-AR）。
  • 写成「§N」的链接落在第 N 节或它的上下级；同一篇里的步骤范围不重叠（ARD-AZ）。
  • 手工维护的 HTML 更新记录，覆盖 markdown Change Log 里的每个日期（ARD-BA）。
  • 问题清单里写的总数和各状态的数量，等于实际行数（ARD-BB）。
  • 图只画文字说不清的流程，一个流程只画一张图（ARD-BE）。

Alternatives Considered

  • 只用一种 spec 类型装下所有内容： 放弃。文档会越来越大，也没法按关注点分开写（DSGN-B）。
  • 按 initiative 而不是按 feature 组织目录： 放弃。和已有的 docs/features/ 目录结构冲突。
  • frontmatter 用 status 而不是 health： 放弃（ARD-D）。
  • 所有规则都是 MUST： 放弃。纯格式规则太多，作者只好把文档写得像给机器读的（ARD-BN）。

  • 文档类型和必需章节偏多，小 feature 也要写全。sub-feature 可以不写全五篇（parent design 的 DSGN-E），能缓解一些。

Document Standard — 给人读的 HTML 页面（Design）

本篇是 document-standard-design.md 的分篇，规则编号 DSGN-N。需求见 reader PRD（PRD-A 到 PRD-P）。路径规则和 DSGN-B 一致，内容优先级和 DSGN-I 一致，编号和 DSGN-F 一致。术语见 parent design 的术语表。

生成网页时要遵守的规则摘要在 SPEC-HTML-STANDARD.md 和 SPEC-PRESENTATION.md，它们是 spec-write、spec-review 要读的三份标准文件中的两份（ARD-CH 重述 ARD-BX）。markdown 是全文，HTML 只是方便阅读的视图。spec-write 只改 markdown；spec-review 检查 HTML 有没有丢内容（ARD-AJ）。

Problem Statement

  1. feature spec 有很多篇、好几层，人很难一次读完。
  2. 如果「好读的 HTML」被写成短摘要，审查和新人上手时就会漏掉 MUST 规则，这违反了 document-standard 的「L1 永远不删」。
  3. 早期 spec-pipeline 里的 SPEC-READER.md 写过「概括并改写」，容易被理解成可以大幅删减。这种理解作废，以本篇的 DSGN-N 为准。

Solution

规定一种叫「spec reader」的 HTML 产物：静态网页，排版好读，内容不丢。它从已提交的 markdown 派生出来，正式版本永远是 markdown。

DSGN-N-H — 单篇页面

来源：reader PRD 的 PRD-F、PRD-J。

  • markdown 是源头，HTML 是派生物。
  • markdown 里用 <!-- html-skip --> 包住的内容可以不显示，但不能用它包住 L1 内容。
  • decision-history 里被划掉的句子在 HTML 里也保留。页面上有一个按钮，可以切换「显示删除线」和「隐藏删除线」。
  • 脚本生成的页面每次从 markdown 重新生成，不带 spec-paired 标记。手工维护的页面要带三个标记：spec-paired=hand-maintained、spec-source（源 markdown 的路径）、spec-source-sha256（源文件的哈希）。源文件变了而页面没变，哈希就对不上，检查会报「过期」（ARD-AK）。
  • 手工维护的页面如果有更新记录，要覆盖 markdown Change Log 里的每个日期（ARD-BA，NICE）。
DSGN-N-B — 内容不丢（MUST）

来源：reader PRD 的 PRD-A、PRD-G、PRD-J、PRD-K。

把 DSGN-I 的四个优先级对应到 HTML：

级别 在 HTML 里怎么处理
L1 全部显示：MUST 和禁止事项、需求表的每一行、测试用例、实现任务、Decision Log 的每一行（带编号）、接口表的数据行、Out of Scope、前提假设、边界、安全规则、错误处理。不能用一段话代替整张表或整节
L2 事实保留；可以写得更短，或者放进提示框，但不能删掉理由里的结论
L3 放弃的方案等，可以压成要点，加一句「详见原文」
L4 可以不显示正文，但必须在页脚或链接里指向 markdown

编号必须可见（MUST）。 HTML 里要原样显示编号，例如 PRD-A、DSGN-B、ARD-C、IMPL-C、TST-A，方便和审查结果、MUST 清单对照。

不允许（MUST NOT）：

  • 只留「问题」「方案」各一段，删掉 Design 下面各个 DSGN 小节的正文。
  • 用「见原文」代替一整页。（一节里面的 L3、L4 可以指向原文。）
  • 做成 markdown 预览：整页 <pre>，或者没排版的 markdown 原文。

允许：

  • 把 markdown 表格改成 HTML 表格。列可以合并显示，但行一行都不能少。
  • 把长段落分段，加提示框，加小流程图，前提是 L1 的内容一条都不少。
  • 一种文档有多个分篇时，按分篇分开显示。
DSGN-N-C — 汇编页的结构

来源：reader PRD 的 PRD-C、PRD-D。

parent 的汇编页（reader）把 parent 和各个 sub-feature 的文档放在一页里，方便从头读到尾。它是全站的一页，在左侧目录的「3 design」下面（ARD-BI）。

  • 页面顶部（MUST）： 说明这是方便阅读的汇编页，要改内容去改 .md；写明 parent 的名字。
  • parent 部分： 每种存在的文档一部分：PRD、Design、Impl plan、Test plan、Decision history；how-to 可选。
  • sub-feature 部分： 每个 docs/features/<parent>/features/<sub>/ 一部分，至少包含它的 design 入口和 design 分篇。
  • 每部分底部（MUST）： 写 Canonical: 加原文相对仓库根目录的路径；有多个分篇时，全部列出。

早期的汇编页用多个 Tab 切换，现在改成全站目录加汇编页（ARD-BG）。

DSGN-N-I — 全站目录

来源：reader PRD 的 PRD-C。

全项目只有一个网站，入口是 docs/book/html/index.html。每篇 spec 的 HTML 是目录里的一行。先在目录里选 feature；进入后，左边是这个 feature 的目录，右边是正文（ARD-BG）。每一页都能从入口点到；网站由 GitHub Pages 从 master 发布（ARD-CD）。

DSGN-N-K — 正文里的链接

来源：reader PRD 的 PRD-D、PRD-H。

  • 正文里出现的编号（PRD-、DSGN-、ARD-、IMPL-、TST-、PIPE-、QUES-）要链到它的定义。编号前面写明了出处（例如「parent design 的 DSGN-A」或 <feature>/<编号>），就链到那个 feature。没写出处，才先找本 feature；本 feature 里没有，再链到 parent。
  • 指向 docs/features/ 下 .md 的链接，改成指向 docs/book/html/ 下同路径的 HTML。没有单独页面的文档（例如 pipeline design，见 DSGN-N-L），链到汇编页里对应的那一节。
  • 指向其他已存在文件的链接，直接链到那个文件。
DSGN-N-L — 左侧目录的序号和层级

来源：reader PRD 的 PRD-C。

左侧目录显示层级和序号：1 prd、2 decision-history、3 design、4 impl plan、5 test plan、6 how to、10 sub-feature。design 的分篇和汇编页放在 3 下面。sub-feature 单独成一组，在 10 下面逐个展开。pipeline 在左侧目录里没有单独的页面，它的内容收在汇编页里（ARD-BI）。

DSGN-N-D — 视觉和技术要求

来源：reader PRD 的 PRD-B、PRD-H、PRD-L、PRD-O、PRD-P。

  • 全站用同一套样式：页面布局、编号标签、卡片、提示框（NICE，ARD-BY）。
  • 浏览器直接打开文件即可阅读正文与已提交的 SVG 插图，不需要服务器（MUST，PRD-O、ARD-CB）；字体与 Mermaid 可联网。
  • 插图用 diagram-design 画，SVG 与 citing md 同目录，生成时内嵌；全站配色与 diagram-design 默认一致（ARD-CA）。
  • 允许内嵌 Mermaid 流程图（Mermaid 是一种用文字描述、由浏览器画成图的格式）；没有先例时用文字画的流程图。
  • 页面里不能有密钥，也不能有 raw/ 里给机器用的评测原文；需要的话只放路径（MUST）。
  • 不能在运行时读取 .md 文件来显示主要内容；只有调试时可以（MUST）。
  • 页面标题、节、小节、条目的字号、粗细、样式各不相同；段落前面不加 a、b、c 或 1、2、3 这类序号（MUST）。
DSGN-N-E — 谁负责什么

来源：reader PRD 的 PRD-I、PRD-M、PRD-N。

spec-write 只改 markdown 与同目录插图 SVG；改完后告诉用户网页没更新、问要不要重建，commit 前必须重建（PRD-M、parent ARD-CF）

DSGN-N-F — 什么时候重新生成

来源：reader PRD 的 PRD-M。

  • parent 或任何 sub-feature 的已提交文档有实质修改（尤其是 L1、L2）之后，重新生成（NICE；网页过期由 parent test-plan 的 TST-R 检查）。

Document Standard — 给人读的 HTML 页面（PRD）

本篇是 document-standard 的一个分篇 PRD（入口是 document-standard-prd.md），讲「给人读的 HTML 页面」要什么、不要什么。具体规则写在 reader design（DSGN-N）。生成 HTML 时要遵守的规则摘要在 skills/spec-html-standard/SPEC-HTML-STANDARD.md，它只是一份规则文件，不是 skill。术语见 parent design 的术语表。

Overview

spec 的正式版本是已提交的 markdown。但一个 parent feature 往往有很多篇、好几层文档：parent 自己的五篇，加上 features/<sub>/ 下各个 sub-feature 的文档。人需要一个能一次浏览全部内容的网页，而且不能为了好读就丢掉 spec 里的 MUST 规则、表格的行、编号和 L1 内容。

早期手工写的汇编页删得太多，很多章节只剩几句话，和「spec 要让人读懂」的目标相反。本篇规定要什么、不要什么，细则见 DSGN-N。

Goals and Success Metrics

ID 目标 怎么算达到
PRD-A 内容不丢 读者在 HTML 里看到的 L1 内容和 markdown 一样多：MUST 和禁止事项、表格的每一行、带编号的条目、Out of Scope、关键的流程图。不能做成高管摘要
PRD-B 是排好版的网页，不是 markdown 预览 有卡片、提示框、表格，可以有流程图。不能只是把 markdown 原文塞进 <pre>，也不能运行时读取 .md 文件来显示
PRD-C parent 和 sub-feature 都覆盖 parent 的五篇文档，每篇存在的都有一页；每个 features/<sub>/ 至少收录它的 design，有其他已提交的文档也一并收录。页面都能从左侧目录找到；pipeline 例外，它没有单独的页面，内容收在汇编页里（ARD-BG、ARD-BI）
PRD-D 能追溯到原文 每一页（或每个大的部分）底部写明 Canonical: <markdown 路径>；页面顶部说明：要改 spec 先改 markdown，再重新生成 HTML
PRD-E 位置和命名固定 parent 的汇编页是 docs/book/html/<parent>/<parent>-reader.html；其他页面按它在 docs/features/ 下的相对路径放在 docs/book/html/，扩展名换成 .html（ARD-BF）
PRD-F 能逐步改进 最早可以手工维护；之后改用脚本从 markdown 生成。改用脚本以后，本篇和 DSGN-N 仍然是要遵守的规则

User Stories

  • PRD-G：作为审查的人，我希望在网页里看到完整的 MUST 表和每个 TST、IMPL 条目，不用来回打开十几个 markdown 文件。
  • PRD-H：作为 feature 的负责人，我希望网页排版更好读（标题层级清楚、有表格和提示框），但不丢 design 里的 DSGN、PIPE 这些编号和它们的内容。
  • PRD-I：作为 AI，我希望有一份 PRD、一份 design 和一份 SPEC-HTML-STANDARD.md 告诉我怎么生成网页，而不是只有一句「重写一下」。

Functional Requirements

ID 需求
PRD-J 生成 HTML 必须遵守 DSGN-N 的保真规则，和 document-standard 的 DSGN-I 一致：L1 不删；L2 可以写得更短，但不能删掉事实；L3、L4 可以概括，但必须链到原文
PRD-K 不能把整篇 design 或 PRD 压成一段概述。如果一种文档拆成了多个分篇，网页必须按分篇分开展示，每个分篇的 L1 都保留
PRD-L 全站视觉风格统一：衬线字体的标题、等宽字体的编号标签、浅色的提示框。这一条是 NICE：做不到只提醒，不算失败（ARD-BY）
PRD-M spec-write 改完 markdown 后，应该提示重新生成网页；用户要求时也重新生成。生成时必须按 skills/spec-html-standard/SPEC-HTML-STANDARD.md 做（没有单独的 reader skill）
PRD-N 如果发现 HTML 和 markdown 说法不一致，或者 HTML 暴露出 spec 本身的错误：先报告并问人，先改 markdown，再重新生成 HTML（和 DSGN-G 的原则一样）

Non-Functional Requirements

  • PRD-O：纯静态网页，阅读时不需要服务器，用浏览器直接打开文件就能看；发布时由 CI 生成（parent 的 ARD-CD），不依赖 MkDocs（一种把 markdown 生成网站的工具）的服务。
  • PRD-P：页面里不能有密钥，也不能有 raw/ 里给机器用的评测原文；需要的话只放路径链接。

Out of Scope

  • 替代 book 摘要或 MkDocs 的导航。网页放在 docs/book/html/（ARD-BF）。
  • 每次 git commit 自动同步网页。目前不要求 git hook（提交时自动运行的脚本）。
  • 拿网页当检查的依据。判断对错仍以 SPEC-STANDARD.md 和已提交的 markdown 为准。

Resources Needed

  • 一个生成静态 HTML 的脚本，加一个本地静态文件服务器（可选）。不需要后端，也不需要数据库。
