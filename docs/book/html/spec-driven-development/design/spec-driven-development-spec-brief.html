Problem Statement

Today's AI is strong, yet it disappoints because four problems sit upstream of any solution:

  1. The problem is often never defined. "iPhone 18 Duo or base?" omits use, budget, history, and preferences — so the answer cannot be accurate.
  2. AI's real value is discovering the unknown. What we know, what we know we do not know, what we do not know we know, and the blind spots we do not know we do not know.
  3. Decisions change and conflict. A budget moves from $2,000 to $1,000 and the whole direction changes; multiple participants can assert different decisions, so authority and propagation must be explicit.
  4. The human and the document are the bottleneck. Files must be readable, findable, clearly scoped; large projects need specs split by boundary and linked so people and agents can find the right one.

This standard addresses the documentation side: one authoritative artifact per concern, changes recorded instead of overwritten, and rules for splitting and naming documents. Defining the problem, discovering unknowns, and negotiating between participants belong to the skills before and around the documents — wayfinder, research, and grilling.

Solution

Spec-driven development is a set of skills that work together, not one skill. Their shared goal is to analyze the concrete problem until the work is clear, then carry that clarity through five artifacts:

  1. PRD — what we are building, the problem it solves, limitations, preferences, timeline, resources, tools.
  2. Decision history — every product-direction decision recorded before it is acted on; append-only; 50/50 AI-draft / human-confirm.
  3. Spec — the chosen technical approach, contracts, tools, interfaces, boundaries; HLD + LLD material.
  4. Impl plan — what comes first, what later, task details and preparation.
  5. Test plan — done and usable now, plus a regression guard for future changes.

The skills never silently rewrite an earlier artifact. If a decision and a requirement conflict, the human resolves it and states which one is right; the skill records the ruling. The shared document contract — authority by concern, content priority, health, naming, and the four enforcement modes — is specified in the spec's D1–D9.

Implementation Decisions

  • The rules live in doc-organize rather than a new skill, because placement, linting, and consolidation already belong there.
  • Detail is carried in sibling reference files rather than inline in SKILL.md, so SKILL.md stays loadable in one pass.
  • state keeps draft / final; health is a separate optional field, so no migration is required.
  • No rule is enforced by a timestamp edit. last_verified moves only when a real verification happened.
  • This spec is self-contained by design; the skill is implementation and operational text.
  • Rule IDs and traceability replace verbatim copies of agent-facing text. Prose is paraphrased; exact identifiers, enum values, paths, commands, and tables are verbatim.

Testing Decisions

Verified by reading the modified skill end to end against the seventeen source rules, and by confirming no remaining instance of the replaced rule (grep -i "code is the source of truth" returns nothing). The self-contained redesign is checked against the traceability table: every rule group resolves to an existing implementing file, and every rule ID appears in the spec. The pipeline spec is 409 lines and the document standard is 910 lines; both are under the 1,000-line cap.

Out of Scope

  • Migrating existing documents to the new optional metadata fields.
  • Bringing docs/features/ into compliance with the existing standard.
  • Automating drift detection in CI.

Further Notes

Known non-compliance in the tree, observed while writing this document and not addressed here:

  • The wayfinder-import spec and its siblings do not follow <feature>-<type>.md.
  • docs/features/skill-factory/ has a design/ directory and fourteen separate decision-history files.
  • This feature carries three spec documents (pipeline, document standard, wayfinder import). Decision 0006 allows more than one spec; decision 0009 records the reason.
