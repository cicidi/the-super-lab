Three layers, often confused

Layer 1 · Method

wayfinder + to-spec + to-tickets

Decide → write → ticket. These skills define how work is shaped: a map of decisions, one spec, many tracer-bullet tickets.

Layer 2 · Discipline

doc-organize + doc-review + implement

These define how artifacts stay honest: authority by concern, review gates, TDD at agreed seams, conflict reporting.

Layer 3 · Runtime

walter-worker / coworker

This is not the workflow tool. It installs skills into harnesses, injects feature context into CLAUDE.local.md, and records sessions.

Page 01 · Workflow

Pipeline at a glance

The intended chain from a loose idea to committed code. Three gates sit inside it: a delivery review per task brief, a document review before tickets, and a work-completion review after implementation.

As-is vs target

This page maps the skills installed today: wayfinder → to-spec → doc-review → to-tickets → implement. The spec's Solution now describes a different target framing — five cooperating artifacts: PRD → decision history → spec → impl plan → test plan. The redesign has to reconcile the two; this page does not claim they are the same.

Three gates, three scopes

Gate 1

Delivery review

When: closing a task brief that produced files.
Tool: doc-review for .md, matt-code-review for code.
Skips: research, grilling, prototype briefs.

Gate 2

Document review

When: after to-spec, before to-tickets.
Scope: spec + all closed briefs + CONTEXT.md + ADRs.
Checks: consistency, completeness, no contradictions, mkdocs-ready.

Work completion

When: implementation finished.

Page 02 · Decision layer

wayfinder

Planning for work too large for one agent session. It charts a shared map of decision briefs on the tracker, then resolves them one at a time until the route to the destination is clear. It produces decisions, not deliverables.

source mattpocockimported 2026-08-02status adapted

Design in one sentence

The map is an index, not a store. Each decision lives in exactly one brief. The map gists it and links to it; it never restates the detail. A session claims one brief, resolves it, records the answer, and graduates newly-specifiable fog into fresh briefs.

The map

One issue, labelled wayfinder:map. Its body has five fixed sections:

SectionHoldsRule
DestinationWhat reaching the end looks like — a spec, a decision, or a change.One or two lines; every session re-orients to it.
NotesDomain, skills to consult, standing preferences.May override "plan, don't do" by carrying execution into the map.
Decisions so farOne line per closed brief + link.Index only; detail stays in the brief.
Not yet specifiedFog of war: in-scope questions not yet sharp enough to brief.Never pre-sliced into brief-sized pieces.
Out of scopeWork consciously ruled beyond the destination.Closed, never graduates.

Briefs

A brief is a child issue of the map. Its body is the question, sized to one ~100K-token agent session. The answer is not in the body; it is recorded on resolution.

TypeModeUsed whenResolved by
researchAFKA fact outside the working directory blocks a decision./research subagent; findings on a throwaway branch.
prototypeHITL"How should it look / behave?" needs a concrete artifact./prototype; asset linked, not pasted.
grillingHITLThe default: a decision needs a live human exchange./grilling + /domain-modeling, one question at a time.
taskHITL or AFKManual work must happen before a decision can be made.Do the work; record facts later briefs depend on.

HITL is not optional

A HITL brief only resolves through a live exchange with the human. An agent that answers its own grilling questions has broken the design (wayfinder/SKILL.md:99).

Mechanics

Claim

Assignment is the lock

A session claims a brief by assigning it to the dev before any work. An open, unassigned brief is unclaimed. This is how parallel sessions skip each other.

Frontier

Open + unblocked + unclaimed

Blocking uses the tracker's native dependency relationship so the frontier renders in the tracker UI. A brief is unblocked when every blocker is closed.

Fog

Brief vs not-yet-specified

Brief when the question is already sharp, even if blocked. Leave it in fog when you cannot yet phrase it precisely. Resolution graduates fog into new briefs.

Scope

Out of scope is not fog

Fog gathers toward the destination. Work beyond it is out of scope: close any existing brief and record one line in Out of scope. It never graduates.

Two invocation modes

Mode A

Chart the map

  1. Name the destination via grilling + domain-modeling.
  2. Map the frontier breadth-first.
  3. If no fog appears, stop — no map is needed.
  4. Create the map issue.
  5. Create the briefs you can specify; wire blocking in a second pass.
  6. Fire research subagents in parallel.
  7. Stop — charting resolves nothing.
Mode B

Work the map

  1. Load the map at low resolution.
  2. Pick a brief (user-named or first frontier); claim it.
  3. Resolve it with the named skills.
  4. Run the delivery review gate if it is a task brief with deliverables.
  5. Post the answer, close the brief, append to Decisions so far.
  6. Add newly surfaced briefs; graduate fog.
  7. Stop after one brief, except research.

Page 03 · Writing layer

to-spec

Turns the current conversation and codebase understanding into a spec (PRD) and publishes it to the tracker. It does not interview — it synthesizes what is already known.

source mattpocockoutput spec issuelabel ready-for-agent

Contract

Input
Conversation context, closed wayfinder briefs, repo state, domain glossary and ADRs.
Output
A spec (PRD) published to the tracker and labelled ready-for-agent.
Does
Synthesizes decisions; sketches test seams; writes the template; publishes.
Does not
Interview the user; invent decisions; include file paths or code snippets.
Depends on
doc-organize for placement, frontmatter and required sections; AUTHORITY-BY-CONCERN.md and CONTENT-PRIORITY.md for content.

Process

1

Explore

Read the repo; use the domain glossary; respect ADRs.

→
2

Sketch seams

Prefer existing seams; use the highest seam; aim for one. Confirm with the user.

→
3

Write

Fill the section template, tagged L1–L4.

→
4

Publish

Tracker issue + ready-for-agent; no extra triage.

The template and its content levels

SectionLevelWhat goes in it
Problem StatementL1The problem from the user's perspective. Never trimmed — without it the direction cannot be checked.
SolutionL1The solution from the user's perspective.
User StoriesL1A long numbered list: As an actor, I want a feature, so that benefit.
Implementation DecisionsL1 decision / L2 rationaleModules, interfaces, schema changes, API contracts, interactions. No file paths or snippets.
Alternatives ConsideredL3, optionalLive options that lost, each with the reason. Omit if none was seriously considered.
Testing DecisionsL1 constraint / L2 specifics"Test external behavior, not implementation" plus modules and prior art.
Out of ScopeL1Non-goals; never trimmed.
Further NotesL4Background, references, open threads; links, never restatements.

The one exception to "no code"

If a prototype produced a snippet that encodes a decision more precisely than prose — a state machine, reducer, schema, or type shape — inline that snippet in the relevant decision and note it came from a prototype. Trim to the decision-rich parts, not a working demo.

Design consequences

  • After to-spec, the spec is the authoritative artifact for intended behavior. Code is authoritative for current implementation. A later disagreement is a conflict to report, not a silent rewrite.
  • The spec is sized by content: the 1,000-line cap and split-by-bounded-context rule from doc-organize apply.
  • "No interview" is deliberate: the grilling already happened in wayfinder or grill-with-docs. If the conversation is still fuzzy, to-spec is the wrong tool.

Page 04 · Verification layer

doc-review

Two-branch review skill. Design review stress-tests a spec before implementation; work completion review verifies finished work against acceptance criteria. Every design finding gets a 1–5 severity; only 3+ is discussed.

branches 2levels 1–5max debate 3 rounds

Branch A · Design review

Step 1

Severity gate

5 CriticalWould break the system or force major rework
4 ImportantSignificant design flaw or missing requirement
3 Worth discussingReal concern, not blocking
2 MinorNice-to-have, stylistic
1 NitpickTypo, wording

Only 3+ is debated. 1–2 are recorded as skipped.

Step 2

Choose intensity

Quick scan — a single gap report with all 3+ findings.

Full adversarial — two independent reviewers, then debate disagreements; at least one web search per major claim; 3 rounds max per issue; a judge rules on available evidence.

If every finding is level 2 or below, the document passes and no changes are needed.

Branch B · Work completion review

PHASE 1

Collector

Read PRD/design/plan; derive acceptance criteria with source + MUST/SHOULD/NICE; write a test plan and regression guard.

→
PHASE 2

Reviewer

Run the suite; Playwright for E2E; curl for APIs; manual code paths; check diff coverage; scan for secrets/debug code.

→
PHASE 3

Sign-off

ACCEPTED with evidence (file:line + test result) or REJECTED with action items.

Role in the SDD chain

PositionUses which branchPass condition
After wayfinder, before to-spec → ticketsDesign reviewNo 3+ findings, or all accepted findings fixed.
Closing a task brief with .md deliverablesDesign review (delivery gate)Review passes before the brief closes.
After implementationWork completion reviewEvery MUST criterion has PASS + evidence.

It reports; it does not rewrite

doc-review judges a spec against doc-organize: missing L1 content, implementation detail that should not be there, and claims about current implementation the code does not support. It reports findings — it never silently rewrites the spec or the code.

Anti-patterns the skill explicitly blocks

  • Bikeshedding — debating level 2 findings.
  • No evidence — arguments without citations or search results.
  • Reading instead of testing — code-reading is not verification.
  • Vague sign-off — "looks good" is not acceptance; SIGNED needs file:line and a test result.
  • Endless debate — 3 rounds, then the judge rules.

Page 05 · Decomposition layer

to-tickets

Breaks a plan, spec, or conversation into tracer-bullet tickets: each cuts a narrow but complete vertical slice through every layer and declares the tickets that block it.

output ticketsshape vertical slicelabel ready-for-agent

Rules for a slice

  • Cuts a narrow but complete path through schema, API, UI, and tests — vertical, not a horizontal layer slice.
  • A completed slice is demoable or verifiable on its own.
  • Each slice fits in a single fresh context window.
  • Prefactoring that makes the change easier is done first: "make the change easy, then make the easy change."

Blocking edges

Each ticket declares the tickets that must complete before it can start. A ticket with no blockers can start immediately. Work the frontier: any ticket whose blockers are done.

The one exception: wide refactors

A mechanical change whose blast radius fans across the codebase — rename a column, retype a shared symbol — cannot land green as one slice. Sequence it as expand → migrate in batches → contract. Each batch is a ticket blocked by the expand; the contract is blocked by every migrate batch. If batches cannot stay green alone, they share an integration branch and all block a final integrate-and-verify ticket.

Process

1

Gather

Use the conversation; fetch a referenced spec/issue in full.

→
2

Explore

Optional codebase pass; find prefactors.

→
3

Draft

Vertical slices with blocking edges.

→
4

Quiz

Granularity, edges, merge/split; iterate to approval.

→
5

Publish

Local files or tracker, blockers first.

Publishing matrix

TrackerWhereBlocking shape
Local markdown.scratch/<feature-slug>/issues/<NN>-<slug>.md, numbered from 01 in dependency order"Blocked by" lists the numbers/titles
GitHub / Linear / otherOne issue per ticket, blockers firstNative blocking / sub-issue relation, else a "Blocked by" section

Ticket content

Deliver

What to build

The end-to-end behavior this ticket makes work, from the user's perspective — not a layer-by-layer implementation list.

Accept

Acceptance criteria

A checklist of externally observable conditions. Specific file paths and code snippets are avoided; they go stale.

What it deliberately does not do

It does not close or modify the parent issue. It does not re-open decisions — if decisions are still being made, the work belongs to wayfinder first.

Page 06 · Build layer

implement / auto-tdd

The build stage is where specs become code. Today there are two skills that can own it, plus a code-review skill at the end — and the pipeline names them inconsistently.

implement 47 linesauto-tdd 138 linesreview matt-code-review

implement

Trigger
Spec and tickets are ready; acceptance criteria and testing seams are agreed.
Does
TDD at pre-agreed seams; typecheck regularly; run single test files regularly; full suite once at the end; /code-review; commit to the current branch.
Refuses
Working when the spec is fuzzy or decisions are unmade — that is wayfinder or grill-with-docs first.
Spec handling
Classify the change before touching the spec. Refactor/rename/optimization/framework migration do not require a spec edit; externally observable behavior does. Conflicts are reported, not silently resolved.

auto-tdd

Basic

Red–green–refactor

Classic TDD through public interfaces: plan and approve; write one tracer-bullet test (RED); minimal code (GREEN); then one behavior at a time. Tests verify behavior, not implementation details.

Auto

Multi-agent continuous loop

A self-correcting loop with an arbitration judge and a quality judge. It does not stop until all tiers pass. Used when correctness matters and the work is complex.

matt-code-review

Two independent axes over the diff between HEAD and a fixed point:

AxisChecksWhy separate
StandardsCoding conventions + Fowler smell baseline.Wrong style is a different question from wrong behavior.
SpecFaithfulness to the originating issue / PRD / spec.Both run as parallel sub-agents so contexts do not pollute each other; findings are reported side by side, never merged.

Three names for one stage

wayfinder says to-tickets → auto-tdd; the installed implement skill says it drives TDD and closes with /code-review; the wayfinder-import spec lists implement as "future import, out of scope". The redesign needs one canonical build-stage contract (and a decision on which review skill owns the final gate).

Where the quality evidence comes from

  • implement guarantees typecheck + tests; it delegates review to /code-review.
  • auto-tdd guarantees its own loop and judges; it does not mention spec-drift classification.
  • matt-code-review guarantees two-axis diff review; it needs a fixed reference point.
  • doc-review Branch B guarantees acceptance against criteria with executed evidence.

Page 07 · Standard

doc-organize

The documentation standard and its four enforcement modes: Organize, Lint, Consolidate, Sync. Every other skill in the chain defers to it for placement, frontmatter, required sections, and conflict authority.

modes 4types 6 + statecap 1,000 lines

What it owns

Authority

One owner per concern

Spec owns intended behavior; code owns current implementation; contracts, migrations, tests own their facts.

Content

L1–L4 priority

L1 is never deleted. Trim L4, then L3, compress L2, split if still over the cap.

Structure

Type, path, sections

Six committed types plus gitignored state; fixed required sections per type; Change Log last.

The standard at a glance

RuleValue
Pathdocs/features/<feature>/<type>/<feature>-<type>.md
Typesprd, spec, impl-plan, test-plan, decision-history, how-to; state is local/gitignored
Frontmatterfeature, type, state, final_date; optional spec_id, version, health, owner, last_verified
Required spec sectionsProblem Statement, Solution, User Stories, Implementation Decisions, Design, Testing Decisions, Out of Scope, Further Notes
Size capspec and impl-plan under 1,000 lines; decision-history exempt

Recent change: the spec is now self-contained

The SDD spec was split on 2026-10-30 into a pipeline design and a document standard. The pipeline spec (296 lines) defines the five artifacts and their cooperation; its Problem Statement and Solution now live in the parent PRD. The document-standard spec (910 lines) defines authority, content priority, health, naming, document types, and enforcement. Both specs stay under the 1,000-line cap, and the document standard remains the operational contract implemented by the doc-organize skill.

Page 09 · Runtime

walter-worker: deploy, inject, record

walter-worker is a Claude Code context and memory manager. It installs skills into harnesses, injects feature context into CLAUDE.local.md, and records sessions. It does not run the SDD workflow and does not dispatch skills at runtime.

CLI coworkersource of truth the-super-labruntime harness

What it is / is not

Is

Context, memory, analytics

Manages the global → project → local CLAUDE.md layers; records sessions, tool calls, file I/O, skill usage, tokens and cost; builds cross-session memory; ships slash commands for project/feature/memory/dashboard.

Is not

A workflow executor

It does not decide when to call wayfinder, to-spec, or to-tickets. Those are invoked by the agent in the harness. The one exception is auto-worker, which spawns a headless Claude session with a prompt.

The one runtime exception: auto-worker

AutoWorkerAgent spawns claude -p <prompt> --output-format json as a fresh headless session, with the auto-worker skill loaded as context. It is used for the QA loop: find-issues ( inspector) → auto-worker (fixer) → verify → repeat. This is the only place walter-worker itself starts an agent.

Deployment drift is a real failure mode

The script copies skills but does not prune removed or renamed skills from ~/.claude/skills or ~/.cursor/rules. Only OpenCode dangling symlinks are pruned. A rename leaves the old skill installed, so two copies with similar names are discoverable — which is exactly the name-collision problem doc-organize/NAMING.md warns about.

Questions to answer before rewriting

  • Entry criteria: What exactly makes work "large enough for wayfinder"? One session? One context window? Decision count?
  • Build contract: Does implement replace auto-tdd, wrap it, or become its basic mode? Who owns the final review gate?
  • Tracker: Is GitHub Issues canonical, local markdown canonical, or is the tracker an explicit per-project config the skills must read?
  • Gate enforcement: Is a gate a skill invocation the agent must run, a checklist in the skill, or an external CI hook? What happens when it is skipped?
  • Artifact authority: After the self-contained spec rewrite, is the spec always the design source and the skill always implementation? What is duplicated, and how is drift checked?
  • walter-worker's boundary: Does it stay a deployment/context layer, or should it own orchestration? If it owns orchestration, which skill dispatch API does it use?
  • Skill ownership: Which skills belong to the-super-lab, which to walter-worker's bundle, and which are imported upstream? What is the update path?
  • Deployment hygiene: Should install prune removed/renamed skills in all four destinations? How are collisions detected before they reach the agent?
  • Document layout: Does MkDocs-ready move into doc-organize as a standard rule, or stay a wayfinder discipline?
  • Vocabulary: Freeze feature, brief, spec, ticket, map, destination — and retire the synonyms.
