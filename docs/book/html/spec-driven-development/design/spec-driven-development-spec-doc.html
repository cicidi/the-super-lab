Problem Statement

Today's AI models are strong. They can read, search, and reason about the latest technology, and they can help us solve real problems. So why does AI still disappoint so often? Four problems sit upstream of any solution.

1. The problem is often never defined

A question like "Should I buy the iPhone 18 Duo or the base iPhone 18?" looks simple, but it leaves out everything that determines the answer: what the phone is for, the budget, whether the buyer has always used an iPhone, which qualities they value, and which they dislike. The AI does not have that context, so its recommendation cannot be accurate. The common complaint that "AI is not useful" is often not a failure of the model — it is a failure to define the problem.

2. AI's real superpower is discovering the unknown

Once the problem is stated, AI can propose approaches and even a solution. But a person can only recognize solutions they have seen before. AI's greater value is to move us through four kinds of knowledge:

  • what we know we know,
  • what we know we do not know,
  • what we do not know we know,
  • what we do not know we do not know — the blind spots.

Surfacing the last category changes the outcome; it is not merely a faster answer.

3. Decisions change, and the change must be understood, recorded, and synced

Decisions rarely hold still. A budget agreed at $2,000 becomes $1,000 after a conversation with family, and the whole direction changes: where to buy, whether a used iPhone 18 Duo is acceptable, how to find a deal. Engineering has the same problem: a decision made last week is overturned by a new constraint or by another person.

Multiple participants make it harder. If one person budgets $1,800 and another $1,500, or one wants to buy this month and another next month, which decision is authoritative? How does that decision override the earlier ones it conflicts with? The hard problem is not recording decisions. It is representing their relationships, deciding which one is currently valid, and propagating a change through every decision that depended on it.

4. The human is still the bottleneck — and so is the document

Even with the problem defined, the unknowns surfaced, and the decisions synced, people still have to read. Is a document easy to read and easy to find? Is it clear what each file is for? How is the documentation managed?

A large project cannot have one spec. How should specs be split? How should the parts relate to each other? How will people and agents read and search them later? As the project and its spec tree grow, both need to find the right information quickly without loading everything.

What this standard addresses

This standard cannot solve all four problems. It addresses the ones that documentation can. Documentation and code drift apart because the obvious rule — "keep them in sync" — is not actionable: it does not say which artifact wins, when a document must change, or what to do when two artifacts disagree.

The previous rule was one-directional

The previous doc-organize rule said "code is the source of truth", which silently resolves every conflict in one direction and makes a spec unable to protect intended behavior.

The standard gives each concern one authoritative artifact, records changes instead of overwriting them, and sets rules for splitting and naming documents so people and agents can find the right one. The problems of defining the problem, discovering unknowns, and negotiating between participants belong to the skills that run before and around the documents — wayfinder, research, and grilling.

Solution

Spec-driven development is a set of skills that work together, not one skill. Their shared goal is to analyze the concrete problem until the work is clear, then carry that clarity through five artifacts:

#ArtifactQuestion it answersOutput
1PRDWhat are we building, what problem does it solve, and what are the limits, preferences, timeline, resources, and tools?The requirement that will impact every decision.
2Decision historyWhich product-direction decisions have been made, and which one is current?An append-only log; a superseded decision stays and a new entry supersedes it.
3SpecWhat is the chosen technical approach, contract, and tooling?The design, carrying HLD and LLD material; the split is out of scope for now.
4Impl planWhat comes first, what comes later, and what preparation does each task need?An ordered task plan.
5Test planIs the task done and usable now, and will a future change be caught before it becomes a regression?Verification plus a regression guard.

Decision history is recorded before it is acted on

Any future decision that touches product direction is written to the decision history first. Judging what counts as product direction is hard, so the target is a 50/50 split: AI drafts the update automatically; the human confirms or instructs the AI to record it.

How the skills cooperate

The skills never silently rewrite an earlier artifact. If a decision and a requirement conflict, the human resolves it and states which one is right; the skill records the ruling. The shared document contract — authority by concern, content priority, health, naming, and the four enforcement modes — is specified in D1–D9.

Design

This section is the design of the standard itself. Rule IDs are stable and grouped by concern: AUTH, SCOPE, HEALTH, PRIO, NAME, STD, MODE, GATE. The traceability table at the end maps each group to its implementing file.

Adoption footprint in doc-organize

Four surfaces changed: ## Authority by Concern and three sibling sections were added to SKILL.md; Lint gained stale-verification, excessive-implementation-detail, and reference-drift checks; Sync resolves by concern instead of defaulting to code; Quality Gates gained the change checklist.

D1 · Authority by Concern

Why: with one global source of truth, every conflict resolves in one direction and one class of fact is always silently overwritten. Intended behavior and current implementation are different concerns and need different owners.

AUTH-1One owner per concern

No single artifact is the source of truth for everything. Each concern has exactly one authoritative artifact.

ConcernAuthoritative artifactAnswers
Intended behaviorthe feature's specWhat the system SHOULD do
API contractOpenAPI, protobuf, GraphQL, JSON Schema, event schema, AsyncAPI — when presentThe contract's exact shape
Database structuremigrations and schema definitionsWhat the database actually is
Current implementationthe codeWhat the system CURRENTLY does
Executable verificationthe testsDoes the implementation satisfy the expected behavior

AUTH-2What the spec owns

The spec is authoritative for intended behavior: requirements, business rules, invariants, architectural constraints, externally observable behavior, security and authorization rules, reliability guarantees, and performance targets that were explicitly specified.

AUTH-3What the code owns

The code is authoritative for current implementation: class, module and package structure, internal algorithms and data structures, framework usage, implementation-specific optimizations, and the code paths actually taken.

AUTH-4Read the owner

Before reading anything, answer: what concern am I trying to establish? Then read the artifact that owns it. Do not read the code to learn intended behavior, and do not read the spec to learn the current call graph. Do not restate a machine-readable contract or a database schema in a Markdown spec — read the artifact it already lives in, and link to it.

AUTH-5Conflicts

When two authoritative artifacts disagree about the same concern, do not silently overwrite either one. Work through, in order:

  1. What is the intended behavior?
  2. Is there a recent requirement or change that speaks to it?
  3. Is there an explicit product or business decision?
  4. Was the code changed deliberately?
  5. Are the tests merely recording the current implementation?
  6. Is there a production-behavior or compatibility requirement?
  7. Which artifact is authoritative for this concern?

If the answer is not determinable, STOP

Explain the conflict, show the evidence on each side, and ask. Never silently pick a side, and never rewrite the spec or the code to match the other before the intended behavior is established. On a production system, existing behavior is never broken automatically because the spec reads as more authoritative.

AUTH-6A passing test is not a requirement

Tests are executable verification, not a substitute for requirements. They answer "does the current implementation satisfy the expected behavior?". A test that passes today may only be recording what the code already does.

D2 · Spec Scope and Size

Why: a spec that mirrors the code becomes a second codebase. It bloats, drifts, and must be edited by every refactor even when no behavior changed.

SCOPE-1What a spec describes

Describe: what and why, contract, invariants, constraints, expected behavior, error semantics, state transitions, external interactions, and architecture boundaries.

Do not describe: class hierarchy, private methods, temporary variables, internal helper functions, framework-specific implementation, or internal algorithms that are free to be refactored.

SCOPE-2The change test

If the implementation can change while externally observable behavior does not, the spec SHOULD NOT change.

Authorization must reject an expired payment method.

Not:

PaymentAuthorizationService.validateExpiration() calls
ExpirationValidator.validate(), which reads PaymentMethod.expiresAt.

SCOPE-3Size guidelines

DocumentTypical range
Feature / change spec500-1,500 lines
Architecture / design spec1,000-3,000 lines
A single implementation task100-500 lines
Spec context one agent task needsroughly 5-10k tokens

These are guidelines, not hard limits. The enforceable limit is separate: a spec or impl-plan file stays under 1,000 lines.

SCOPE-4Split on a boundary

Split on a bounded context, domain boundary, ownership boundary, independent lifecycle, independent change frequency, or agent-context requirement. Never split mechanically to satisfy a line count. A spec describing several independent domains, lifecycles, or behavior models should be split.

SCOPE-5Loading order

An agent should not load the whole documentation hierarchy. Load in this order and stop as soon as the task is answerable:

  1. Global rules
  2. The relevant domain spec
  3. The relevant architecture
  4. The relevant contract
  5. The relevant examples and tests
  6. The code

If an agent routinely needs most of a spec to answer a narrow question, the spec boundary is wrong. Re-cut it rather than raising the context budget.

D3 · Spec Health

Why: a spec that is never verified decays invisibly. Without metadata and drift checks, nobody can tell an old spec from a wrong one.

HEALTH-1Metadata

Beyond the four required fields, an important spec may carry:

spec_id: payment.authorization
version: 3
health: active
owner: payments-team
last_verified: 2026-09-25
FieldMeaning
stateAuthoring state: draft or final
healthactive, stale, or deprecated
ownerWho answers for the document's accuracy
last_verifiedWhen someone last confirmed the spec still matches intended and current behavior

HEALTH-2Verified is not updated

last_updated is when the file was edited. last_verified is when someone confirmed it is still true. Health tracks last_verified, not last_updated. Never edit a file only to move a timestamp.

HEALTH-3The field is health, not status

state already tracks the authoring state (draft or final). A second field named for "state" would be read as the same thing.

HEALTH-4Optional fields

All five optional fields may be omitted. A document without them is still valid; it simply carries no health signal, and Lint reports that as NICE, not MUST.

HEALTH-5Stale

stale means the spec has not been recently verified. It does NOT mean the spec is wrong. Roughly 90 days is a reasonable review signal and never a hard rule: a stable spec that rarely changes should not be edited to satisfy a clock.

HEALTH-6Drift detection

Check for, by CI, lint, agent review, or periodic audit:

  • spec and code contradict each other
  • the spec references an API or component that no longer exists
  • the code implements important behavior the spec does not mention
  • important behavior changed without the spec being reviewed
  • the spec carries excessive implementation detail
  • the spec has grown past a useful context boundary
  • the same fact is maintained in two places
  • last_verified is stale

HEALTH-7Detect, report, ask

Not every drift is mechanically resolvable. For semantic ambiguity the order is:

Detect -> Report -> Ask

Never Detect -> Guess -> Rewrite.

HEALTH-8Change checklist

Run this when an implementation change is complete:

  • Relevant spec identified
  • Authoritative source identified for each affected concern
  • Determined whether intended behavior changed
  • If behavior changed, the spec is updated
  • If the change is implementation-only, no spec edit was made
  • Code does not contradict intended behavior
  • Tests verify the important spec requirements
  • Machine-readable contracts remain consistent
  • No duplicate source of truth introduced
  • last_verified updated only where a real verification happened
  • Unresolved spec/code conflicts reported, not silently resolved

HEALTH-9Duplication

Do not maintain the same fact by hand in a spec, a README, a wiki, an issue tracker, API documentation, and code comments. Pick one authoritative source, generate the others, delete the duplicate, or give each document a distinct purpose. The goal is not that every document agrees; it is that no fact is maintained twice.

D4 · Content Priority

Why: without a trim order, people delete requirements to fit a size cap and call it optimization.

PRIO-1Four levels

LevelHoldsTestOn trim
L1 DecisiveWhat the system must do and must not doRemove it and a reader implements something differentNever deleted
L2 RationaleWhy this design, with evidenceRemove it and the rule still holds, but nobody knows whyCompressed
L3 AlternativesWhy not the other approachRemove it and the rule still holds, but the road not taken is lostDeleted first
L4 SupportReferences, research, examples, raw outputRemove it and nothing about the behavior is lostDeleted first

PRIO-2What sits at L1

  • intended behavior, requirements, business rules
  • contracts and the shape of inputs and outputs
  • invariants and constraints
  • error semantics
  • state transitions and external interactions
  • security, authorization, and permission rules
  • architecture boundaries — module edges and dependency direction
  • performance guarantees that were explicitly specified
  • out of scope and non-goals
  • assumptions
  • compatibility and migration constraints
  • open questions, marked as unresolved

The last four are easy to misfile as L2. They are L1: an implementation built on a dropped assumption, or one that breaks a dropped compatibility constraint, is wrong in the same way as one that ignores a stated requirement.

PRIO-3What sits at L2

  • the rationale for a decision
  • benchmark or profile output that justifies a stated guarantee
  • the incident or regression number that motivated a rule
  • a link to the discussion that produced the decision

PRIO-4What sits at L3

  • rejected alternatives, with the reason each was rejected
  • trade-off comparisons between the options that were live
  • "X was considered and dropped because Y"

PRIO-5What sits at L4

  • raw research notes and product comparisons
  • mockups and screenshots
  • illustrative example payloads and sample data
  • long logs and unprocessed benchmark output
  • meeting notes
  • a copy of a glossary that already exists in CONTEXT.md
  • tutorial-style explanation of background material

PRIO-6A duplicated fact is L4

A fact has exactly one authoritative home. If the same fact already appears in another document — a contract, a glossary, a decision-history, a README — then the second appearance is not a restatement. It is a link, and a link is L4.

Restating a fact is a defect

It creates a second place to update and a second place to be wrong. The link survives trimming as long as something depends on following it. What never survives is the copy.

PRIO-7Belongs at no level

These do not belong in a spec at any level. They are not L4 — they are absent:

  • class hierarchy
  • private methods
  • temporary variables
  • internal helper functions
  • pseudocode
  • framework-specific implementation detail
  • internal algorithms that are free to be refactored

PRIO-8Trimming procedure

  1. Replace every restated fact with a link to the document that owns it.
  2. Delete the remaining L4 content. Move research and long logs to the feature's gitignored scratch rather than deleting them outright, and keep a link if the spec cites them.
  3. Delete L3 content, unless a rejected alternative is the only thing preventing the decision from being relitigated.
  4. Compress L2 — keep the reason, drop the narration.
  5. Never delete L1.
  6. If the document is still over 1,000 lines, the boundary is wrong. Split it on a bounded context and name the parts by the rules in D5.

Deleting L1 to fit a size cap is a defect

It is not an optimization. Trim L4, then L3, compress L2, and split if the document is still too long.

D5 · Paths, Names, and Splitting

Why: a file must be identifiable outside its directory, and confusable names make readers and agents open the wrong document.

NAME-1The path

docs/features/<feature>/<type>/<feature>-<type>.md

One file per type per feature by default. prd, test-plan, decision-history, and how-to stay single-file. spec and impl-plan may be split, because they are the two types that grow without bound.

  • <feature> is kebab-case, lowercase, no spaces or special characters
  • The filename repeats the feature and the type, so a file is identifiable outside its directory
  • A supporting file that a document cites sits in that document's folder: docs/features/<feature>/design/<source-name>.md
  • A feature has at most one decision-history, and it is exempt from the 1,000-line cap: it is append-only history, and history is never trimmed

NAME-2Splitting

Split when one file would cross 1,000 lines. Split on a boundary — a bounded context, domain, ownership edge, or lifecycle — never to reach a line count.

docs/features/payment/design/payment-design-authorization.md
docs/features/payment/design/payment-design-settlement.md
docs/features/payment/impl-plan/payment-impl-plan-01-schema.md
docs/features/payment/impl-plan/payment-impl-plan-02-api.md
  • A spec part takes a bounded-context noun. Never a number: a number says nothing about the contents, and inserting a part forces a renumber across the set.
  • An impl-plan part takes a zero-padded sequence plus a phase name. A plan is ordered, so the number carries meaning there.
  • A <feature>-design.md may stay as an entry file holding global L1 constraints and links to the parts. Do not keep one as an empty shell.

NAME-3Name collisions

Check a new feature or file name against what already exists, every time a document is placed — in Organize before creating, and in Lint across the tree. Any one of these is a collision:

SignalExample
Identical after normalizationPayment vs payment
One name's tokens are a subset of the other'sauth within auth-service
Singular, plural, or a common abbreviation of the same worddoc/docs, auth/authentication
Edit distance at most 2 on the hyphenated namepayment-api vs payments-api

NAME-4Resolving a collision

Resolve by intent, not by picking a winner:

  • Same bounded context — merge into one feature folder, then split its spec by aspect.
  • Different contexts with confusable names — rename both so each is distinguishable (a bare auth becomes payment-auth and user-auth), and record the rename in the affected feature's decision-history.
  • A file collision inside one feature — make the aspect names distinct; if they cannot be, the feature name is too generic.

A rename is a decision. Log it rather than performing it silently, because every inbound link and every reader's memory of the old name has to be updated.

D6 · The Document Standard

Why: a fixed structure makes documents predictable for readers and mechanically checkable for lint.

STD-1Document types

Six committed types, one local type. Every document belongs to exactly one.

TypeHoldsCommitted
prdWhat to build and why — product-level requirementsyes
specHow it is built — technical detail, interfaces, design decisionsyes
impl-planThe task breakdown that implements the specyes
test-planHow the implementation is verifiedyes
decision-historyEvery decision ever made for the feature, in orderyes
how-toOperational instructions for using the resultyes
stateWorking progress, for compaction recoveryno — gitignored

Architecture and design content belongs in a ## Design section of spec, not in a separate design type. External material that a document cites belongs beside that document, not in a separate reference type.

STD-2Exempt from the standard

The standard governs documents under docs/features/. These are not typed documents and carry no frontmatter, type, or Change Log:

PathWhy exempt
docs/INDEX.mdGenerated index, rewritten wholesale each time
docs/book/**Assembled output, built from documents that are already final
CONTEXT.mdDomain glossary, owned by domain-modeling
README.mdRepository orientation, not a feature document

Lint reports these only if their links break or they list a file that no longer exists. Do not add frontmatter to them.

STD-3Frontmatter

Every document carries these four fields:

---
feature: <feature-name>
type: prd | design | impl-plan | test-plan | decision-history | how-to
state: draft | final
final_date: YYYY-MM-DD
---

final_date is required when state is final. A document becomes final when its content is settled; after that it is maintained rather than rewritten, and authority follows the concern table rather than defaulting to the code.

An important spec may additionally carry spec_id, version, health, owner, and last_verified. All five are optional — see D3.

STD-4Required sections

Each type has a fixed section set. Sections may be added, never renamed or dropped.

TypeRequired sections
prdOverview, Goals and Success Metrics, User Stories, Functional Requirements, Non-Functional Requirements, Out of Scope
specProblem Statement, Solution, User Stories, Implementation Decisions, Design, Testing Decisions, Out of Scope, Further Notes
impl-planGlobal Constraints, then numbered Tasks
test-planTest Cases, Test Execution Order, Expected Pass Threshold
decision-historyDecision Log, Evidence Appendix
how-toOverview, Prerequisites, Steps, Verification

prd carries product intent. spec carries technical intent and the Design section replacing the old separate design document. Implementation Decisions records architecture-level choices and their rationale — not class structure, private methods, or internal algorithms.

A spec may also carry an optional Alternatives Considered section holding the rejected approaches and why each lost. It is L3 and the first section deleted when the document runs long; omit it when no alternative was seriously considered.

STD-5Decision history

The decision-history file is a tracking history, not a curated summary. It keeps every decision ever made for the feature, including ones later superseded and ones that turned out wrong. Nothing is deleted.

| # | Date | Decision | Status | Supersedes |
|---|------|----------|--------|------------|
| 0001 | 2026-07-14 | Adopt kebab-case for feature directories | accepted | — |
| 0002 | 2026-07-22 | Store state per feature, not per project | superseded by 0007 | — |

Status uses the vocabulary proposed, accepted, deprecated, or superseded by <NNNN>. A superseded decision stays in the log and keeps its evidence entry. When a decision is overwritten, add a new numbered entry that supersedes the old one rather than editing the old one.

The Evidence Appendix holds one numbered entry per decision, preserving the original rationale and supporting content:

### 0001 — Adopt kebab-case for feature directories

Status: accepted

Rationale as originally recorded, including any alternatives that were
considered and why they were rejected. Support content belongs here:
benchmark output, links to the discussion that produced the decision.

STD-6Change Log

Every document ends with a Change Log, as its final section. It is appended to, never prepended, and existing entries are never removed.

## Change Log

| Date | Change |
|------|--------|
| 2026-08-02 | Initial creation |
| 2026-08-14 | Moved from docs/initiatives/ to docs/features/ |

STD-7Scratch

Research, discussion, and adversarial-review artifacts are working material, not documents. They live under the feature but are gitignored and never committed:

docs/features/<feature>/research/<topic>.md
docs/features/<feature>/discussion/<topic>.md
docs/features/<feature>/state/state-<YYYY-MM-DD>.md

Add these to .gitignore:

docs/features/*/research/
docs/features/*/discussion/
docs/features/*/state/

Not to be confused with .scratch/:

TreeHoldsWritten by
docs/features/<feature>/Reasoning material — research, discussion, adversarial review, progress statedoc-organize and the reasoning skills
.scratch/<feature-slug>/Ephemeral build artifacts — tickets and issueswayfinder and to-tickets

Reasoning is worth keeping on disk next to the feature it belongs to. Tickets are throwaway work items and stay outside the docs tree. doc-organize does not manage .scratch/, and Lint does not report it.

STD-8INDEX.md

Regenerate after every create, move, rename, or delete. Walk the docs tree and read each file's frontmatter, first heading, and first paragraph. A file that is not listed is an orphan; a listed file that does not exist is a dead link.

STD-9PROTECTED blocks

Content between <!-- PROTECTED --> and <!-- END PROTECTED --> is never modified by any mode. The <!-- PROTECTED START --> / <!-- PROTECTED END --> spelling is also recognised, but prefer the shorter form, which is what the rest of the tooling uses.

D7 · Enforcement Modes

Why: a standard that is only prose is advisory. The skill turns it into four repeatable modes with mechanical fixes where they are safe.

MODE-1Determine the mode

Infer from what the user asked. Ask one question only when genuinely ambiguous.

SignalMode
"where should this go", a new documentA — Organize
"check the docs", "is this valid", reviewing a fileB — Lint
"too many files", "merge these", "consolidate"C — Consolidate
"docs disagree", "spec is stale", "out of sync"D — Sync

"Review the file and fix the format" is B — Lint. "Review the file" meaning whether its content is any good is doc-review, not this skill.

MODE-2Mode A: Organize

  1. Identify the feature. If it is not obvious from context, ask.
  2. Identify the type from the six committed types. If the content spans types — product intent and technical detail together — split it: intent goes to prd, technical detail to spec.
  3. Check the feature name and the intended filename against what already exists (D5 lists the collision signals). Merge, rename, or confirm with the user before going further.
  4. Compute the path: docs/features/<feature>/<type>/<feature>-<type>.md.
  5. If that file already exists, do not create a second one — unless the type is spec or impl-plan and the existing file is at the 1,000-line cap. Prefer merging into the existing file in the right section and appending a Change Log entry. Split only when the cap forces it, and name the parts by D5.
  6. Write the frontmatter and required sections for the type.
  7. Append the Change Log entry.
  8. Regenerate INDEX.md.

MODE-3Mode B: Lint

Audit the docs tree against the standard. Applies mechanical fixes; reports the rest.

  • Wrong root — a doc tree under docs/initiatives/ or docs/<feature>/, outside docs/features/
  • Wrong type directory — a directory not in the six types: design/, plan/, raw/, reference/, mockups/, work-review/, issues-found/, devil-advocate/, wrong-history/
  • Wrong filename — not <feature>-<type>.md
  • Missing or invalid frontmatter — any of the four fields absent, or state outside draft|final, or final without final_date
  • Missing required sections for the type
  • Change Log missing, misplaced (not last), or containing a non-table section after it
  • Heading skips — an ## under no #, an #### under an ##
  • Dead links — a relative link whose target does not exist
  • Orphan or dangling INDEX.md entries
  • docs/adr/ — legacy layout; fold into the feature's decision-history
  • Stale verification — last_verified older than roughly 90 days; report only, never edit a file to move a timestamp
  • Excessive implementation detail — a spec describing class structure, private methods, or internal algorithms rather than behavior
  • Reference drift — a spec citing an API, component, or file that no longer exists; report it, do not guess the replacement
  • Oversized document — a spec or impl-plan over 1,000 lines; report it for splitting. decision-history is exempt
  • Name collision — two features or two files whose names trip a collision signal
  • Restated fact — the same fact written out in two documents; the second occurrence should be a link

Apply the mechanical fixes directly: rename to the standard filename, move to the standard directory, add missing frontmatter, move Change Log to the end. Report what needs a human decision — content that must be split across types, or a section that has no counterpart in the standard. Regenerate INDEX.md and append a Change Log entry to every file touched.

MODE-4Mode C: Consolidate

Reduce many files to one per type per feature. This mode deletes and merges, so it proposes and waits — it never applies without approval.

  • Multiple prd, spec, impl-plan, test-plan, or how-to files for the same feature become one file per type.
  • Multiple decision records become one decision-history, with the Decision Log in chronological order and every original preserved in the Evidence Appendix. Nothing is dropped, including superseded and incorrect decisions.
  • research/, discussion/, devil-advocate/, and raw/ content moves to gitignored scratch, or is deleted if it has no continuing value. Cite what it supported before removing it.
  • A reference/ file is a supporting file, not scratch. Move it into the folder of the document it supports — a source cited by the spec goes to spec/ — and keep it committed so the citation stays verifiable.

Present every move, merge, and deletion with its target. On approval, apply it, regenerate INDEX.md, and append Change Log entries. If a decision is being overwritten by consolidation, add a superseding entry rather than editing the original.

MODE-5Mode D: Sync

Reconcile documents with each other and with the code. Check for drift:

  • Tone and terminology — the same concept named differently in two places, or a glossary term from CONTEXT.md not used
  • Decision conflict — two documents asserting different decisions
  • Spec drift — a document and the code disagreeing about the same concern, or a document describing behavior the code no longer has
  • Reference drift — a document citing an API, component, or file that no longer exists
  • Duplicated facts — the same fact maintained by hand in two places

Resolve by authority:

  • Change Log first. If one document records a later change than another, the later one wins — a document-to-document question.
  • Intended behavior — the spec is authoritative. If the code contradicts the intended behavior, the code is what changes.
  • Current implementation — the code is authoritative. If the spec describes an implementation difference, the spec is what changes.
  • Contract or schema — the machine-readable artifact is authoritative. Never hand-edit a spec to mirror it.
  • Report what cannot be resolved. Which decision or which behavior is correct is a human decision. Detect, explain, show the evidence from both sides, and ask.

Auto-fix formatting, tone, terminology, links, and heading hierarchy directly. Never rewrite a decision silently. Append a Change Log entry to every file changed.

D8 · Quality Gates

Why: the gates are the checklist that makes the standard enforceable rather than aspirational.

GATE-1MUST

  • Every document is under docs/features/ with a type from the six
  • Filename is <feature>-<type>.md and matches its directory
  • Frontmatter carries all four fields; final has final_date
  • Required sections for the type are present and correctly named
  • Change Log present, last in the file, appended to only
  • PROTECTED blocks intact
  • INDEX.md regenerated after any create, move, rename, or delete
  • Consolidation preserved every decision, including superseded ones
  • Scratch content is gitignored and not committed
  • No content lost — every unique section from a merged file has a home
  • Spec changes trace to a change in intended behavior, not to a code change
  • Authority for each affected concern identified before resolving a conflict
  • No spec/code conflict resolved silently
  • No fact maintained by hand in two places
  • spec and impl-plan under 1,000 lines, or split on a bounded context
  • Feature and file names checked for collisions before creation
  • No L1 content dropped to meet the size cap

GATE-2NICE

  • Heading hierarchy has no skipped levels
  • All relative links resolve
  • Terminology matches CONTEXT.md
  • last_verified present and current on important specs
  • Spec stays within a useful context boundary

GATE-3Anti-patterns

  • Creating a second file for a type that already exists. A feature has one spec until it crosses the 1,000-line cap.
  • Splitting a spec to dodge the cap without a boundary.
  • Numbering spec parts. Plans are numbered because a plan is ordered; specs are named by their aspect.
  • Deleting L1 content to fit the cap.
  • Restating a fact that already has a home. The second occurrence is a link.
  • Letting two features carry confusable names.
  • Deleting a superseded decision.
  • Committing scratch.
  • Silently resolving a decision conflict.
  • Rewriting a final document.
  • Consolidating without approval.
  • Treating a content review as a lint.
  • Treating code as the source of truth for everything.
  • Treating the spec as the source of truth for everything.
  • Editing a spec to prove it is in sync.
  • Maintaining the same fact in two places by hand.
  • Splitting a spec to satisfy a line count.
