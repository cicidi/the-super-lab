Overview

本 PRD 定义 spec-driven development：用 PRD、decision-history、design 篇、impl-plan、test-plan 五篇，把有门槛的问题分析清楚，并由 spec-write 与 spec-review 执行（ARD-AJ）。

Problem Statement

今天，AI 模型的能力已经非常强大。它们可以阅读、搜索最新、最前沿的技术，帮助我们解决问题。

但是，问题是什么？

1. Problem 经常没有被定义清楚，更何谈解决

比如这样一个问题：

嘿，AI，我买 iPhone 18 Duo 还是 iPhone 18 基础版？

看似是一个简单的问题，但实际上，我们并没有告诉 AI 我们的真实需求。

比如：我们买新的 iPhone 是用来做什么的？我们的 budget 是多少？我们之前是否一直使用 iPhone？我们喜欢 iPhone 的哪些优点，又有哪些缺点？

这些 context，AI 并不知道，因此 AI 的推荐肯定不会准确。

这正是很多人抱怨 AI 不好用的原因。事实上，对于我们自己来说，这看似是一个清楚的问题，但实际上，可能不是 AI 不好用，而是人没有把 problem 定义好。

2. AI 真正赋予我们的 superpower，是帮助我们发现 unknown

在我们把问题问清楚以后，AI 也提供了一些思路，甚至 solution。

但是，由于人的能力有限，我们可能根本没有见过某些解决方法或方案。

我们利用已知的信息，找到我们不知道自己知道的信息，同时学习我们知道自己不知道的知识，最后把我们不知道、甚至不知道自己不知道的 blind spot 发掘出来。

这才是 AI 真正赋予我们超能力的地方。

3. Decision 不断变化，AI 需要理解、记录并同步这些变化

经常，我们做了一段时间，或者和 team 里的其他人讨论后，会发现一些 decision 一直在改变。

比如：我们买 iPhone 的 budget，和父母、妻子商量未果。我们之前说买 iPhone 的 budget 是 2,000 美金，现在突然变成了 1,000 美金，那么 AI 整个 decision 的方向就会发生彻底的转变。

紧接着，一系列新的问题又会被引入：去哪里买？是不是能够接受二手 iPhone 18 Duo？

当然，随之而来的，去哪里买、如何找 deal 等具体实现方式都会发生改变。

今天的例子比较简单，以后可能会有更复杂的例子：多个人做出多个 decision，到底谁是真理？而这个真理，可能还需要 impact、覆盖其他一些之前的 decision。

比如：爸爸的 budget 是 1,800 美金，妈妈说 1,500 美金；爸爸说下个月可以买，妈妈说这个月可以买。

到底谁是真理？根据这个真理，我们又要如何修改之前的 decision？

这里真正的问题是：当多个参与者做出不同的 decision 时，AI 如何理解这些 decision 之间的关系，判断哪些 decision 是有效的，并根据最新的 decision 更新整个 decision-making process？

4. 即使 problem、solution、update、sync 都做好了，人依旧是整个 AI 世界最大的 bottleneck

首先是阅读。

怎么让文件好读、好懂？文件怎么好查找？如何清晰地知道每个文件是做什么的？如何做好 file management？

大的项目不可能只有一个 spec，那么如何切分 spec？如何让不同的 spec 之间保持清晰的关系？以后 AI 和人又该怎么读、怎么查找？

当项目越来越大，文件越来越多，spec 越来越复杂时，我们如何让人和 AI 都能够快速理解整个项目，并准确找到自己需要的信息？

这些都是 AI 真正落地到实际工作中，需要解决的问题。

5. 有门槛的难题不只在软件里

盖一个 shed、去北京旅游、看懂一道著名数学题、不靠猜地分析一只股票——人往往从没做过，不知道怎么拆、盲区在哪、哪些要自己拍板。

AI 要把大问题拆成小的：能查的 AI 自己查（合规、财报、交通），要选的人来选（预算、偏好、风险），人想不到的 AI 主动问。spec 既是学习笔记，也是决策记录，最后交给 AI 执行。

Goals and Success Metrics

  • 目标：任何有门槛的难题都能拆成可查、可决策、可执行的小问题。
  • 验收：spec-write 与 spec-review 的测试结果（test-plan）；这不是产品 success metric。
  • PRD-G 的产品级 success metric 与 baseline 仍 deferred（ARD-N）。

User Stories

  • 作为写 spec 的人，我希望先被 interview，把已知/未知/盲区问出来。
  • 作为 reviewer，我希望机械 MUST 和语义缺陷都能检出，且建议可执行。
  • 作为执行者，我希望 spec 能落到 design/impl-plan，并有 mock 执行与可追溯证据。

Solution

Spec-driven development

我们不重复什么是 spec-driven。这里要做的是开发一些 skill；这些 skill 会在一起工作，而不是单个 skill。这些 skill 的目标是：通过一组 skill，把具体问题分析清楚。

PRD、decision history、design 篇 是互相打磨的循环，不是只走一遍的直线；循环收敛到「够稳」后，impl plan 与 test plan 各自独立：都从 design 篇 总结出来，彼此不串行依赖。

  1. PRD — 我们到底要做什么、解决什么；当前的 limitation 是什么；preference 是什么；timeline、各种 resource、tool 都有什么。design 篇 或 decision 暴露缺口时，回到 PRD 改 requirement。
  2. Decision history — 基于 PRD 作出 decision；任何跟产品方向相关的 decision 先 update decision history（约 50% AI、50% 人）。新 decision 可能改 PRD 范围；spec 里的 trade-off 也可能要求补 decision。
  3. Design 篇 — 与 PRD、decision 并行迭代：写设计（技术方案、contract、tool 等；HLD/LLD 不在此展开）。设计问清 problem、或发现 decision 不够，回到 1/2 继续磨。
  4. Impl plan — 从 design 篇 总结实现：先做什么、后做什么；各个 task 的细节、准备工作等（不依赖 test plan 先写完）。
  5. Test plan — 从 design 篇 总结验证：任务完成标准、可用性检查、regression guard（不依赖 impl plan 先写完）。

Functional Requirements

PRD-A — 做一个 pipeline，基于现在现有的 pipeline 做一些改进。

PRD-B — 做一些 skill；这些 skill 其实就是优质 prompt，或其他 popular 的 prompt，引导 AI 怎么工作：完成 spec 的书写、命名、校验、更新。

PRD-C — 每次改动不超过 10 行 或 200 字符；超出拆多次，restructure 需 human 授权。

PRD-D — 文档大小限制在 1000 行；太大几乎没法 maintain。

PRD-E — 文档的文件组织架构、folder 关系。

Additional constraints:

PRD-F — 多人 decision 冲突时，以 decision history 里时间较晚的那条为准。看不出先后就问用户。AI 不猜测谁为准。

PRD-G — （open）产品级 success metric 与 baseline — deferred，见 ARD-N。test-plan 的分数是 eval 指标，不是产品 success metric。

PRD-H — Spec-driven development 的 workflow 尽量使用 popular skill，不要自己重新发明。

PRD-I — 修改需要验证；没有能验证的，都需要在 spec 里面标注上。标明后不作为 test plan 的通过条件。

PRD-J — 写和改 feature spec 时，spec-write 按标准判断新建或修改哪几篇；提交前 spec-review 询问。State：feature 确定前 CLAUDE.local，之后 docs/features/<f>/raw/state/（ARD-AJ）。

PRD-K — 范围不限软件：任何有门槛的难题走同一套 spec。例子四个：盖 shed（合规、成本、施工）、北京旅游（行程、住宿、风险、预算）、看懂著名数学题（零基础逐步学）、分析股票（基本面、财报、新闻，有理有据）。这轮不在本仓库建 gold，放到别处。

PRD-L — 每个子问题标明归属：AI 查、人决定、或 AI 查完后人决定。人没问到的盲区和风险，AI 必须主动提出。

PRD-M — 把人讲明白是硬需求。交付前由一个 LLM 打分：它假设自己是一个本科水平的程序员真人，只按能不能看懂来判；看不懂不算交付。测试验不了，不作为通过条件。

PRD-N — 正式 spec 的结论必须能追溯到查到的事实（合规条文、财报、新闻、定义），不靠猜；查不到的标成未知。评测时答案只能来自 context 包。

PRD-O — 执行不真下单、不订票。一个共用 mock MCP server，若干固定工具；client call 打出 log 即算交付成功。

PRD-P — ~~最终交付是 spec-write、spec-review，以及 SPEC-STANDARD.md 与 SPEC-PRESENTATION.md（ARD-AJ）。~~ 最终交付只有 spec-write 与 spec-review（→ ARD-BH）。写出的 spec 满足 PRD-K 到 PRD-O。

PRD-Q — 书写、命名、校验、更新，以及 PRD-K 到 PRD-O，都是需求。spec-write 与 spec-review 不限于这几件事。两份 skill 正文写出四个例子：盖 shed、北京旅游、数学题、股票。好不好用只看测试。

Out of Scope

  • 真实下单、订票、交易；执行只到 mock MCP log。
  • 多人 decision 的仲裁细则；按 decision-history 时间，仍看不出则问用户。
  • 本仓库不建非软件四例的 gold；例子写进 skill 正文，gold 放到别处。
  • 存量不合规文档的批量迁移。
  • skill / spec 的版本与迁移策略。

Resources Needed

  • spec-write、spec-review、两份标准 + 一份 test plan;无外部服务、无数据库。
  • 评测需 deepseek-flash API 与 3 次 run 的预算;runs/reports 不入库(ARD-AD)。

Implementation Decisions

4. AI 文档编辑约束（SDD 全 pipeline）

来源： parent PRD Requirements §3。

适用范围： agent 对 docs/ 内 Markdown（feature spec 各篇）的单次编辑。

规则 说明
单次上限 ≤ 10 行 或 ≤ 200 字符（满足其一）
超出时 拆多次；或 human 授权 restructure
与 document-standard cap、路径、frontmatter 见 document-standard design 篇
验证 测试验不了单次编辑大小。不作为 test plan 的通过条件

Implementation： spec-write 已有正文。人不读 skill 正文。本条上限看 skill 执行，不靠测试。

5. Decision history — 何时写（agent / 写 spec 时注意）

原则： decision-history 记 已对外生效或已强迫改 reality 的方向，不是 design 脑内迭代的日记。

应该写 不应写
他人 的 decision（review、配对、stakeholder 口径）需团队可见 仍在本人脑中、未 写入 design 篇 且 未 改 existing code 的探索性微调
本人 重大转向且 已改或必须改 existing code（contract、路径、rename、authority 换边、breaking behavior） 为「想过又改主意」每条 append；design 篇里改一句能表达的不单独开 entry
Pipeline 要求的 rename / collision / supersede 等（见 document-standard DSGN-J–DSGN-K） 仅 enrich design 篇 正文、尚未收敛的 rationale

未 commit 的 scratch 与 raw/design/ 不 替代 decision-history；升格 committed fact 时按上表判断。Agents 补写 feature spec 时 默认不 自动堆 decision-history；有疑问时 human 定夺。

§4（小步编辑）、§5（decision-history 取舍）、feature spec 各篇职责等，须在 harness 全局 留下印象，不能只在 repo 内 skill 正文里写一遍（PRD-H：复用既有 skill，不另造）。

入口文件：spec-driven-development-design.md。

Problem Statement

spec-write 与 spec-review 的输入、输出和边界由本篇承载。标准在 SPEC-STANDARD.md 与 SPEC-PRESENTATION.md（ARD-AJ）。SKILL.md 不是权威。

Solution

本篇定义 spec-write 与 spec-review 的行为契约；SKILL.md 只是实现。规则细节以 SPEC-STANDARD.md 与 SPEC-PRESENTATION.md 为准（ARD-AJ）。

User Stories

  • 作为调用方，我希望知道每个 skill 在什么阶段被调用、需要给什么、会产出什么。
  • 作为 reviewer，我希望 write 与 review 的责任不重叠，标准条款有唯一文档地址。
  • 作为维护者，我希望改 SKILL.md 时不改变契约；契约变了要先改本篇。

Implementation Decisions

  • Authority： 契约以本篇为准；SKILL.md 与正文冲突时，先改契约再改正文（DSGN-G）。
  • 不定义： 失败策略、版本/迁移、来源可信度分级、数据清理（ARD-AF）。
  • 四例： spec-write 与 spec-review 正文都要点名 shed、北京旅游、数学题、股票（PRD-Q）；它们是说明性例子，不是本仓库 gold。
  • Unverified： pipeline 编排、单次编辑大小、可读性打分、跨模型偏差按 PRD-I 标 Unverified。

Design

Skill 阶段 输入 输出 边界
spec-write 新建或修改 用户意图、SPEC-STANDARD、SPEC-PRESENTATION 改后的文稿 先判断新建还是改哪些文；≤10 行/200 字符；不 silent 改上游
spec-review 提交前 / 设计审查 diff 或树、两份标准 建议表；每次一个选择 不 fix、不改写；问完可有一个附加题

共享能力落点：

  • 子问题归属表（PRD-L / PIPE-L）写在每个 feature 的 design 篇。
  • 证据与 UNKNOWN（PRD-N）由 spec-write 写、spec-review 查。
  • mock MCP client/server（PRD-O）仍放在 skills/spec-organize/tests/mock-mcp/。
  • 四个例子（PRD-Q）写进 spec-write 与 spec-review 的 SKILL.md；由 TST-S 检查。

Testing Decisions

  • TST-S： spec-write 与 spec-review 的 SKILL.md 都包含四例。
  • TST-O / TST-P： PRD → design 追溯；归属/证据/UNKNOWN。
  • TST-Q： mock MCP call 打出 log，且无真实副作用。
  • Unverified： spec-pipeline 编排（PIPE-A4/A5/H）、单次编辑大小（PRD-C）、可读性打分（PRD-M）、跨模型偏差（ARD-AD）。

Out of Scope

  • 失败策略、版本/迁移、来源可信度分级、数据清理（ARD-AF）。
  • 存量不合规文档的迁移。
  • 各 skill 的具体 prompt 文案；由 SKILL.md 实现。

Further Notes

  • 新增 skill 时先补本表，再写 SKILL.md。
  • 契约变更需同步 document-standard / pipeline 的对应 DSGN-* / PIPE-*。

Reversibility

  • 契约变更可回退:改本篇 + SKILL.md,无数据迁移。
  • 新增 skill 只需追加一行;移除 skill 须同批改 pipeline 与 test plan。

Alternatives Considered

  • 合成单一 skill → 拒:write 与 review 必须分开。ARD-AJ 将入口收成这两个 skill。
  • 契约直接写进 SKILL.md → 拒:正文变权威,契约失去独立地址(ARD-AB / DSGN-G)。

Drawbacks

  • 多一层间接:改行为要同时动契约与正文。

Risks and Mitigations

  • 风险:正文与契约漂移 → 冲突时契约优先,spec-review 检查引用。

Open Questions

  • 新 skill(如可替换的 map 工具)是否要进契约表。

Evidence Appendix

ARD-A — Authority by concern replaces a single global source of truth

The previous rule was "code is the source of truth", stated in three places in doc-organize. It resolves every conflict in one direction and leaves a spec unable to protect intended behavior: under it, a spec that states a retry count of 3 while the code retries 5 is simply wrong, even when 3 was the requirement.

Considered and rejected:

  • Keep "code is the source of truth" — rejected because it makes the spec unenforceable precisely where enforcement matters, and because a passing test would then also count as a requirement.
  • Declare "spec is the source of truth" — rejected for the mirror reason: a spec cannot answer what the code currently does, and treating it as authoritative for implementation would force spec edits for every refactor.
  • Single source with an exception list — rejected as an unmaintainable middle ground that still names one winner by default.

Adopted instead: authority by concern. Intended behavior belongs to the spec, current implementation to the code, contracts to the machine-readable artifact, database structure to migrations, and executable verification to the tests.

ARD-B — The standard lives in doc-organize, not a new skill

Placement, linting, and consolidation already belong to doc-organize, and its Sync mode is where drift is detected. A separate skill would have to duplicate the document standard to know what a spec is.

Considered and rejected: a new spec-driven-development skill with doc-organize keeping only a pointer. Rejected because the two would share the type list, the frontmatter contract, and the required sections, and the copy would drift.

ARD-C — Detail is carried in sibling files, not inline in SKILL.md

The material is seventeen sections. Inline it would have taken SKILL.md past 700 lines, and a skill that must be read in one pass cannot afford that.

Follows the existing pattern: domain-modeling/ADR-FORMAT.md and domain-modeling/CONTEXT-FORMAT.md. Sibling files travel with the directory, so the skill stays portable — it must not point at this repository's docs/, which does not exist in the projects the skill is deployed to.

ARD-D — The health field is named health, not status

state already tracks the authoring state (draft or final). A second field named status would be read as the same concept, and it accepted an overlapping vocabulary (draft, active, stale, deprecated) that made the overlap worse.

Considered and rejected: replacing state's vocabulary with draft | active | stale | deprecated. Rejected because it would invalidate every existing document to gain a distinction that a second field provides for free.

ARD-E — design and impl-plan cap at 1,000 lines; decision-history is exempt

The earlier guideline said feature specs run 500-1,500 lines, which contradicts a 1,000-line ceiling. The ceiling wins; the guideline is removed.

decision-history is exempt because it is append-only history. Trimming it would destroy the record that is its entire purpose. Exempting it also means the cap never creates pressure to delete a superseded decision.

ARD-F — A feature folder may hold more than one design or impl-plan

Supersedes the earlier rule "one file per type per feature" for these two types only, and removes the anti-pattern that forbade a second spec file.

prd, test-plan, decision-history, and how-to stay single-file: none of them grows without bound. design and impl-plan do, and capping them at 1,000 lines without allowing a second file would have made the cap unmeetable.

ARD-G — Spec parts take an aspect noun, plan parts take a number plus phase

code
payment-design-authorization.md        aspect noun, unordered
payment-impl-plan-01-schema.md       number plus phase, ordered

Considered and rejected: numbering both (payment-design-01.md). A number says nothing about the contents, and inserting a part forces a renumber across the set. A plan is genuinely ordered, so a number carries meaning there; a spec is cut by bounded context, so a noun carries meaning there.

ARD-H — Four content priority levels; L1 is never deleted

L1 decisive (behavior, contracts, invariants, constraints, error semantics, security rules, architecture boundaries, out of scope, assumptions, compatibility constraints, open questions), L2 rationale, L3 alternatives, L4 support. Trim L4, then L3, then compress L2. Never delete L1.

out of scope, assumptions, compatibility constraints, and open questions are filed at L1 rather than L2 because dropping any of them breaks the implementation in the same way as dropping a stated requirement.

A fact whose authoritative home is another document is L4 as a link, never a restated copy. This connects the level model to the duplication rule: restating a fact is a defect, not a level.

ARD-I — This feature carries two spec documents

Deliberate exception to decision ARD-F's one-spec-per-feature default, recorded here because the rule requires a logged reason rather than a silent breach.

This feature is named for the standard itself, so the standard's own spec belongs to it. wayfinder-import-design.md already occupied spec-driven-development/design/, and the wayfinder import is a distinct effort with its own lifecycle.

Considered and rejected:

  • Rename the feature — rejected because the initiative name is established in the project's working context.
  • Put the standard's spec in its own feature — rejected because the standard and the import are the same initiative; splitting them into two features would misrepresent the work.
  • Fold the standard into wayfinder-import-design.md — rejected as a restatement: two unrelated documents in one file.

The two files are distinguished by name, following decision ARD-G's aspect rule: spec-driven-development-design.md for the standard, wayfinder-import-design.md for the import.

ARD-J — Five stages plus an optional how-to

The PRD said six artifacts; pipeline-design.md and the document standard said five. The pipeline spec is right about stages: how-to is an output for the case where a human must operate the result, not a step every feature runs.

Considered and rejected: keeping six to match the PRD — rejected because it invents a stage most features never execute.

ARD-K — Every AI edit to a docs file is small

A large edit lands unreviewed and is hard to attribute when it breaks something. The limit is 10 lines or 200 characters; satisfying either is enough. A larger change is split into sequential edits. A restructure needs explicit human instruction, which is how this PRD's own revision was applied.

Considered and rejected: hard rejection of oversized edits — rejected because it blocks a legitimate restructure; warning only — rejected because nothing stops the edit.

ARD-L — Blind spots come from existing skills

research already has a Discover Unknowns branch and grill-with-docs already runs an adversarial interview. P4 says to use the current tools first.

Considered and rejected: a new dedicated skill — rejected while the existing mechanism works. A future skill may replace them without changing the requirement that the step runs.

ARD-Z — Five PRD fields, then design and decision history

Replaces the undefined six inputs in PIPE-E2. The PRD must state limitation, preference, timeline, resource, and tool. A missing one is marked not apply, not left blank. Downstream starts only after that PRD, the design, and the decision history all exist. Rejected: the word building, and a pointer at PIPE-F for a definition PIPE-F does not hold.

ARD-Y — Map split uses a 20-hour estimate

Provisional rule (PIPE-D item 6). AI shows several split options. One person able to understand the work within 20 hours stays one feature spec. AI estimates above 20 hours, so it splits into a peer or a sub-feature. AI both estimates and judges. Creating directories still waits for human confirmation (PIPE-D item 5).

ARD-X — Execution delivery is a mock MCP log

No live booking or trading. A mock MCP client calls a mock MCP server; the printed call log is success (PRD-O). Rejected: real side effects.

ARD-W — Readability judge is an undergraduate programmer

A second LLM plays a bachelor's-level programmer. Pass only if it understands; otherwise not delivery (PRD-M). ISO 24495-1 was found and not used as the score.

ARD-V — Hard problems stay on the same five artifacts

Shed, Beijing, a famous math problem, and a stock stay in this PRD (PRD-K) on the same five artifacts. Sub-problems name who acts; claims cite a found fact (PRD-L, PRD-N). Rejected: a new feature.

ARD-U — spec-pipeline orchestrator and Map/state model

SDD adds spec-pipeline as the entry skill that calls spec-organize and spec-write and prompts for spec-review before commit. Map relies on human interview; outputs (split, decision, scratch) are AI-judged, not a fixed file template. State lives in CLAUDE.local until feature create sets <f>, then in docs/features/<f>/raw/state/. Rejected: rigid Map MUST artifacts and repo-root BMAD-style state trees. Superseded as an entry skill by ARD-AJ. Create, Map, Converge, and Downstream stay in pipeline-design as reference steps.

ARD-T — wayfinder-import is not an SDD sub-feature

Wayfinder import is a separate skill-factory / import effort, not part of the SDD deliverable (spec-organize, spec-review, spec-write). The nested tree under spec-driven-development/features/wayfinder-import/ is removed; wayfinder work continues elsewhere if needed. ARD-I's multi-spec exception remains historical.

ARD-O — Skills are spec-organize (main), spec-review, spec-write

Deliverable skills use the spec- prefix because they serve spec-driven development, not generic document editing. The standard file stays inside the main skill as SPEC-STANDARD.md, continuing ARD-B's placement rule. Rejected: a separate spec-standard skill — three consumers, one extra copy to drift.

ARD-P — spec-review detects mechanical MUST violations too

Review outputs modification suggestions, not fixes. Mechanical MUST gaps must appear in that list or the user gets an incomplete review. Organize Lint may fix; review detects and suggests. Rejected: semantic-only review — gold-based eval cannot score review against the same MUST set as organize.

ARD-Q — Tests live under skills//tests/

Skills ship to arbitrary projects; tests must travel with them. Cross-skill checks, gold, and HTML reports live under spec-organize as the main skill. Rejected: repo-root tests/sdd/ — assets would not deploy with the skill bundle.

ARD-R — Two eval scores and gates

MUST compliance is a hard floor (x/total full pass). Exemplar comparison uses (plus−minus)×10/total and must not regress within one gold version. Rejected: a fixed exemplar cutoff — gold version bumps change the denominator.

ARD-S — Gold set grows and is versioned

New good and bad examples from runs append to annotations.yaml; gold.version increments. Scores compare only within one version. Rejected: frozen gold — no accumulation of review findings.

ARD-AA — Multi-participant decisions use the latest history entry, otherwise ask

PRD-F is closed. When two decisions conflict, the later entry in decision-history wins; if the order cannot be established, ask the user. The AI never guesses who is authoritative. Supersedes ~~ARD-M~~.

ARD-AB — Four skills including spec-pipeline

The deliverable is four skills: spec-pipeline (orchestrator), spec-organize (standard/lint), spec-review (findings), spec-write (edits). Supersedes ~~ARD-O~~, which listed three.

ARD-AC — PRD and document standard changes

PRD required sections drop Non-Functional Requirements; the parent PRD fills Overview, Goals and Success Metrics, User Stories, Functional Requirements, and Out of Scope. IDs are scoped to feature + type; cross-feature references use <feature>/<ID>. HLD architecture sections do not require DSGN IDs; how-to stays defined but unchecked.

ARD-AD — Eval uses deepseek-flash with 3 independent runs

Only the DeepSeek API is available, so gold generation and checker verdicts use three independent runs of deepseek-flash; cross-model bias is Unverified. Gold uses four terms: gold case, gold version, exemplar, annotations. runs/ and reports/ are not committed. The four non-software examples (shed, Beijing, math, stock) are skill-doc examples; their gold lives elsewhere. Supersedes the gold-example part of ~~ARD-V~~.

ARD-AE — Non-software mapping, ownership, evidence, and UNKNOWN

Non-software problems use the same five artifacts: research in raw/research/, decisions in decision-history, execution in design/impl-plan, verification in test-plan. Each feature design carries a sub-question ownership table (AI查 / 人决定 / AI查完人决定); every claim cites a source; unknowns are marked UNKNOWN. Unverified items use Unverified: <reason> (<condition>).

ARD-AF — Deliberately undefined areas

Failure policy, skill/spec versioning, source-trust grading, and data cleanup are intentionally not defined. Existing non-compliant features are not migrated; only the SDD tree is fixed.

ARD-AG — Convergence is auto-decided

PIPE-E1–E3 are checked automatically; every open decision must carry a structured blocking flag. The AI does not self-declare the spec "stable": the automatic check passes only when no blocking item remains.

ARD-AH — Reader is the only HTML deliverable

spec-driven-development-reader.html is the human-readable deliverable. The legacy spec-driven-development.html summary is deleted; references point to the reader.

ARD-AI — This consolidation is an authorized restructure

The human explicitly authorized a one-shot consolidation of the SDD spec docs. Edits larger than the normal 10-line / 200-character cap are allowed for this batch; the normal cap resumes afterward.

ARD-AJ — Entry skills are spec-write and spec-review

Entry skills are spec-write and spec-review. Path, permission, scope, what to write, and evidence live in skills/spec-organize/SPEC-STANDARD.md. Prose, format, style, tables, and icons live in skills/spec-html-standard/SPEC-PRESENTATION.md. spec-organize and spec-pipeline are not entry skills. Supersedes ~~ARD-AB~~.

ARD-AK — Markdown is the full text

A generated reader is rebuilt from markdown and carries no spec-paired meta. A hand-maintained HTML file names its markdown in spec-source and stores spec-source-sha256. If the hash differs, check paired_html_stale fails.

ARD-AL — Audience and per-section authority

audience may be internal or external. A missing key is not a failure, so existing documents stay valid. Any other value fails frontmatter. A section states which artifact owns its facts. A partner design may use different section ids.

ARD-AM — Step numbers are positions

A step number locates a procedure. It is not a permanent id. Inserting a step renumbers that section and the citations of it.

ARD-AN — Readiness and in-place revision

A decision may say it is settled here and waiting on another team. Wording may be revised in the same row. Open items are grouped by owner.

ARD-AO — One question tracker

When many docs cite the same questions, one tracker holds them. Other docs link. A tracker entry is QUES- plus a letter, with Question, Answer, and Owner.

ARD-AP — Old anchors stay

An id migration keeps an old-to-new table. A renamed heading keeps the previous anchor.

ARD-AQ — Cite the commit

A file:line citation in design or impl-plan names the commit it was read against.

ARD-AR — Invariants as data

An invariant is a table of stored records, or of states that must not occur, with who guarantees each row.

ARD-AS — Point at the new decision

Prose that drops an old claim points at the replacing ARD. A typo may be edited in place. Strike-through stays the decision-history form.

ARD-AT — Done line, order, mock

Each IMPL-* has a done line. Work that reads runs before work that writes. A partner port that is not live has a mock.

ARD-AU — Translation is a local copy

A <name>.<lang>.md copy is not committed. Its opening names <name>.md as the source. Headings in the copy may be translated.

ARD-AV — Required sections on the entry

A design split into parts requires the full section list only on <f>-design.md. A part links back and writes only its aspect.

ARD-AW — Number only a procedure

Required headings stay the English text, unnumbered. A section that exists to hold an ordered procedure may carry a number.

ARD-AX — Optional Ready column

The Decision Log may add Ready. It still has no Status column and no Supersedes column.

ARD-AY — Tracker may replace the ownership table

If every tracker row has Owner and Evidence, the design may link to that tracker instead of copying the ownership table.

ARD-AZ — Section links and step ranges

A link written as §N lands on heading N or on its parent or child. Step ranges in one document do not overlap.

ARD-BA — HTML changelog covers each md date

A hand-maintained reader has a changelog row for every date in the markdown Change Log.

ARD-BB — Tracker counts match

all N questions equals the number of tracker rows. A status tally equals the rows that carry that status.

ARD-BC — Cited status matches the tracker

The status next to a QUES link matches the tracker row. A closed row is not described as still open.

ARD-BD — External gold stays outside

The manifest stores the repo path, the defect commit, the gold commit, expected findings, and allowed misses. The private spec text is not copied here.

ARD-BE — Diagrams carry the flow

One flow, one diagram. A heading that says steps a–b and contains a sequence diagram has b−a+1 messages. State lives in a table. The diagram adds no fact the prose lacks.

ARD-BF — Spec HTML under book

docs/book/html/ repeats the docs/features/ tree. A parent reader is docs/book/html/<parent>/<parent>-reader.html. Other spec HTML uses that same relative path with a .html suffix. Markdown stays in docs/features/.

ARD-BG — One site, feature directory on the left

docs/book/html/index.html lists every feature. Each spec page is one line in that directory. Opening a feature shows that feature's pages on the left and the page body on the right.

ARD-BH — Deliverable is only spec-write and spec-review

The product ships two skills: spec-write and spec-review. SPEC-STANDARD.md and SPEC-PRESENTATION.md remain the files those skills read. They are not deliverables. spec-organize and spec-pipeline stay out of the deliverable. Supersedes the deliverable wording that listed the two standards beside the two skills in ARD-AJ.

ARD-BI — Left sidebar numbers and hierarchy

The feature sidebar is a hierarchy, and the numbers are visible. The order is 1 prd, 2 decision-history, 3 design, 4 impl plan, 5 test plan, 6 how to. Sub-features are not under design. They are group 10, and each sub-feature expands beneath that group. Design parts and the reader stay under 3 design. Pipeline has no HTML page.

ARD-BJ — Gold spec is this spec

The gold test spec is docs/features/spec-driven-development/. A passing run is this tree, not a generated iPhone purchase spec. skills/spec-organize/tests/gold/v1/ stays a practice case. It is not the gold spec.

Problem Statement

Parent PRD 定义的四类上游问题见 ../../../prd/spec-driven-development-prd.md。本篇补充 pipeline 要解决的 流程 问题：

  • 大 feature / initiative 难拆成可执行的 smaller feature，新人不知道顺序。
  • 多个 skill 并存，调用方 不知道何时用哪个。
  • 长会话后 不知道进度（做到哪、还剩什么）。
  • 提交前 容易跳过 review。

Solution

spec-pipeline 为统一入口，驱动四阶段：

code
Create → Map → Converge ⇄ (PRD ↔ design ↔ decision-history) → Downstream (test-plan ∥ impl-plan)
  • Create： 立项与 context（feature create、粗 PRD、搜索 → CLAUDE.local）。
  • Map： 与人 interview；AI 判断拆分/decision/scratch；无 固定 MUST 产物模板；可选 可替换 map 工具（示例 wayfinder，非 SDD deliverable）。
  • Converge： 三角循环打磨；收敛后 才进入 Downstream。
  • Downstream： test-plan 与 impl-plan 并行，均自 design 篇 总结（对齐 parent PRD Solution）。

User Stories

  1. 拆分大需求： 作为不熟悉 spec 的人，我希望经 pipeline Map interview 后，能拆出 smaller feature 并进入 spec-driven 写齐文稿。
  2. 恢复上下文： 作为中断后继续的人，我希望 pipeline recap：已做什么、state 字段、待办、建议下一步。
  3. 提交前： 作为提交者，我希望 pipeline 在「该提交了」时 询问 是否先跑 spec-review。

Implementation Decisions

  • 标准 = SPEC-STANDARD.md 与 SPEC-PRESENTATION.md；写 = spec-write；审 = spec-review。spec-pipeline 与 spec-organize 不是入口（ARD-AJ）。
  • Map 以 interview 为主；AI 判断 是否记 decision、建议拆 feature、或仅 scratch task；人确认 后才创建 docs/features/<f>/ 路径。
  • Map 工具（示例 wayfinder）经 推荐表 调用，可替换；不在 SDD deliverable 清单。
  • State： feature create 完成、<f> 未确定前 — 进度只写在 CLAUDE.local.md（或项目 CLAUDE 层），不 创建 raw/state/*.md。<f> 确定后 — 权威 state 在 docs/features/<f>/raw/state/state-<YYYY-MM-DD>.md（document-standard DSGN-B/C）。
  • Recap 由 pipeline 生成给人看；不是 source of truth（SO T = state 文件 + committed 文稿）。
  • 后期 task 管理：plug-in 其它 skill；本篇 不 引入 BMAD/GSD 级重框架。
  • 协作：读上游 artifact，禁止 silent 改；冲突 Detect → Report → Ask（同 document-standard DSGN-G）。
  • 本篇设计条目 ID 前缀 PIPE-*；不 用 DSGN-* 作 pipeline 内锚点（DSGN 保留给 document-standard）。

Design

PIPE-A — spec-pipeline 职责（MUST）

来源：PRD-A（在既有 pipeline 上改进，不另造编排）。

  • PIPE-A1 任意「写/改 spec」任务从 spec-write 进入，并先按 SPEC-STANDARD 判断新建或改哪些文（ARD-AJ）。
  • PIPE-A2 调用 spec-organize 执行标准、Lint、Organize（路径/格式以 organize 为准）。
  • PIPE-A3 调用 spec-write 执行文稿增删改（含 parent HLD §4 小步编辑 norm）。
  • PIPE-A4 在 提交/推送 committed 变更前，询问 是否 spec-review；用户拒绝则记录，不 silent 跳过审计痕迹。
  • PIPE-A5 用户请求或会话丢失时 recap：已做、当前 state、待做、建议下一步（list）。
  • PIPE-A6 维护/读取 PIPE-H 定义的 state；推荐 PIPE-G 表中的 skill。

PIPE-B — 四阶段总览

阶段 目的 典型失败
Create 建立 feature/initiative 与 context 无 PRD 锚点、context 只存在于聊天
Map 探已知/未知、判断是否拆分 silent 建目录、无 interview
Converge PRD/design/decision 循环至够稳 在 open decision 上写死 design
Downstream test-plan ∥ impl-plan 只写 test 无 regression，或 impl 无顺序

PIPE-C — Create

  1. feature create（walter-worker）建立或选定 <f> / initiative 根（peer vs nested 见 parent HLD §3.1）。
  2. 粗 PRD（示例：「推荐 iPhone 并协助购买」)— 可 draft，不要求一次写齐六要素。
  3. 搜索/调研 → 已知 context 写入 CLAUDE.local.md（或项目 CLAUDE 层）；不 替代 committed PRD。

PIPE-D — Map

  1. Interview 用户（及 context 包）；AI 归纳已知/未知。
  2. AI 判断（无固定 MUST 文件类型）：是否建议 新 feature、是否写 decision、是否在 scratch 留 task 线索、或 暂不拆 进入 Converge。
  3. Recap Map 结论：判断摘要、建议拆分、仍 open 项。
  4. 可选 调用 pluggable map skill（示例 wayfinder）；不得 替代 interview。
  5. 禁止 未经确认创建 docs/features/<f>/ 或移动 committed 树（Organize 模式负责路径）。
  6. 拆分标准（暂时）： AI 先给几个拆法推荐。一个人 20 小时以内能搞清楚的，算一个 feature spec；AI 估算超过 20 小时的，拆成 peer 或 sub-feature。小时估算和拆不拆的评判都由 AI 做。
  7. 子问题（PRD-L）： 每个子问题标成 AI 查、人决定、或 AI 查完后人决定。人没问到的盲区和风险，AI 必须提出。

PIPE-E — Converge

循环： PRD ↔ design 篇 ↔ decision-history（parent PRD Solution）。

收敛条件（MUST 全满足才进 Downstream）：

  • PIPE-E1 无未关闭的 blocking open decision；每条 open item 带 blocking: true|false，仍 open 的须在 design 中点名。blocking: true 不得进 Downstream（ARD-AG）。
  • PIPE-E2 PRD 写清 limitation、preference、timeline、resource、tool；没有的注明 not apply。design 篇与 decision history 都在，才进 Downstream。
  • PIPE-E3 design 篇列出 依赖的 decision 与 仍 open 项；含 implementation 所需的 contract/边界决策（impl 任务细节 下一轮 再定）。

PIPE-F — Downstream

  • test-plan 与 impl-plan 并行启动；互不 串行依赖；均从 design 篇 总结。
  • test-plan： 每项任务 完成检查 + regression guard（PIPE-F1）。
  • impl-plan： 每条任务写依赖与挡住谁；被挡住的后做，没被挡住的先做（PIPE-F2）。

PIPE-G — Skill 推荐（接口）

阶段 场景 推荐 skill 必选
Create 新 feature/initiative feature create（walter-worker） MUST
Create 补 context research（示例） 可选
Map 探图/拆分辅助 pluggable map（示例 wayfinder） 可选
Converge 写/改文稿 spec-write MUST（有改动时）
Converge 合规/路径 spec-organize MUST（create/move/merge 后）
任意 提交 committed 前 spec-review 询问（PIPE-A4）
Downstream test-plan / impl-plan 篇 spec-write + spec-organize MUST

wayfinder 等 map 工具 可替换，非 SDD 必装 deliverable。

PIPE-H — State

时段 存储 内容
<f> 未确定 CLAUDE.local.md（项目 CLAUDE 层） phase、粗需求、Map 笔记、open items
<f> 已确定 docs/features/<f>/raw/state/state-<YYYY-MM-DD>.md phase（Create/Map/Converge/Downstream）、feature、open_items、last_action、可选 scratch_ref
  • Recap 读取 state + committed 树；输出发给用户，默认不 commit recap 本身。
  • 方向性结论 升格 进 decision-history / PRD / design，不 长期只留在 state。

PIPE-I — 协作、血缘、齐备度

  • 读上游、不 silent 改；分歧 report + ask（DSGN-G）。
  • 多人 decision： 以 decision history 时间较晚的为准；看不出先后则问用户。AI 不猜测（PRD-F）。
  • decision 变更 → 点名需 review 的下游 artifact（PRD、design、impl-plan、test-plan）。
  • Parent vs sub 齐备： parent initiative review 见 parent HLD §8；sub-feature 不要求五篇齐全 — spec-review 执行，pipeline 转发 到 review，不 duplicate 规则。

PIPE-J — 边界

本篇管 不管
阶段、入口、skill 推荐、state、recap、提交前 review 询问 frontmatter、路径、ID 细则（document-standard）
收敛条件、Downstream 并行 map/research skill 正文
轻量 state 重 task/BMAD/GSD 框架

PIPE-K — 非软件问题的五篇映射

PRD-K / PRD-Q。 非软件难题走同一套五篇；不新增文档类型。

内容 落点

Problem Statement

Feature 文档多时，缺少统一 standard 会导致：无 authoritative artifact 时的 silent overwrite、路径混乱、stale 与 wrong 不分、同一 fact 多处 drift。

Solution

DSGN-A = 契约（MUST 主要来自 DSGN-A（含 DSGN-B–F）与 DSGN-M）。DSGN-G–DSGN-L = 语义与流程补充。

User Stories

  • 作为写 spec 的人，我希望知道文档放哪、叫什么、多大、谁是权威。
  • 作为 reviewer，我希望机械 MUST 能被脚本检查，语义问题只报告不静默改。
  • 作为 agent，我希望 frontmatter、ID、Change Log 规则明确，不用猜。

Implementation Decisions

  • 可执行摘要在 SPEC-STANDARD.md 与 SPEC-PRESENTATION.md。机械 MUST 由检查脚本执行；semantic 由 spec-review 报告。入口是 spec-write 与 spec-review（ARD-AJ）。
  • how-to 暂不机械检查；其余五类按 DSGN-E 执行。
  • 存量不合规文档不迁移，只报告（ARD-AF）。

DSGN-D — INDEX 与 book（派生层）

docs/features/ 里的 committed 文档是 source of truth。INDEX 与 book 都是 派生层，不用 DSGN-E frontmatter / Change Log，不写 新 decision：

INDEX book
回答的问题 在哪（路径、type、initiative 结构） 干了什么（短摘要，便于 AI/人决定要不要打开全文）
典型粒度 一行链接 + 标题（可带一句 summary） 每篇或每组 source 文档一段 组装摘要，链回 canonical 路径

docs/INDEX.md — 干什么
目的 全库 feature spec 各篇的 地图：哪个 initiative 下有哪些 PRD、design、plan，路径是什么。
给谁用 人、agent、脚本 发现文档 时先查 INDEX，再打开 docs/features/... 里的正文。
不是什么 不是 design 正文；在 INDEX 里改标题/链接 不等于 改 requirement；INDEX 里 不写 设计结论。
与 feature 树 每个 listed 链接必须指向 Commit = yes 的标准路径；tree 变了 INDEX 必须跟着变。

INDEX 怎么维护

  • 生成物：整文件 regenerate（改 generator/template，不长期手改一行行条目）。
  • 何时 regenerate：任一 committed 文档 create / move / rename / delete 之后；与 book 一样，push 到 GitHub 前/时 应与 docs/features/ 变更 同批同步（见 book 应然）。
  • 收录范围：只列 committed 文档（含 sub-feature）；不列 raw/、.scratch/。
  • 结构：按 feature（initiative） 分块，块内按 type 顺序（prd → design → … → decision-history）；链接相对 docs/。
  • 质量（DSGN-M MUST）：disk 有文件但未 listed → orphan；listed 但文件不存在 → dead link。

docs/book/** — 干什么

（与历史 doc-organize 一致：Assembled output, built from documents that are already final。 — 此处 final 指 feature 侧已接受的 committed 正文，不是 book 自己定稿。）
目的 由 feature spec 各篇 组装 的 摘要层：用短说明写清每份 PRD/design/plan 覆盖什么、得出什么、该去哪读全文 — 主要给 AI 检索与选篇。
给谁用 Agent / 人 先扫 book 再打开 docs/features/...；不是在此写第一版 design 或新 decision。
不是什么 不是 source of truth；不是 design 全文拷贝；不能 与 feature 正文 手维护两份相同 fact。
与 INDEX INDEX = 目录；book = 内容摘要。二者互补，通常 一起 更新。

book 写什么（摘要契约）

  • 每条摘要 必须 链到对应 canonical 路径（docs/features/...）。
  • 写 scope + 主要结论/状态（例如：document-standard 的 design 篇定 DSGN-A 契约；pending review 项），不 展开 L1 全文。
  • 新增/变更 decision 只改 feature / decision-history，再 重生成 book 摘要，禁止只在 book 改口径。

book 什么时候更新（应然）

  • 凡 docs/features/ 下 committed 文档 有变更并 push 到 GitHub，同一 push（或紧邻的前序 commit）中应已 regenerate 对应的 book（及 INDEX）。
    实现（pre-push hook、CI、bot、手动）属 impl；本 standard 要求 远端可见的 docs 与 book/INDEX 同步，避免 AI 在 GitHub 上读到新 spec 却仍是旧摘要。
  • 源文档 state: draft 时可暂不更新对应摘要；final 或已 merge 的 committed 变更 必须反映到 book。

其它

  • 路径：docs/book/**；无 DSGN-E frontmatter；Lint 查 link 有效、摘要指向的文件存在。
  • HTML：docs/book/html/ 镜像 docs/features/。摘要仍在 book 其他路径；HTML 不是 source of truth（ARD-BF）。
  • 可 额外 用于 MkDocs / Pages 发布；发布 nav 属 impl，不得与 feature 树、INDEX 矛盾。

其它豁免路径（同样不是 feature 文档，无 DSGN-E frontmatter；Lint 只查 link）：CONTEXT.md（domain glossary）、README.md（repo 导向）。

DSGN-F — 条目 ID（type 前缀 + 字母）

各 type 内可追溯条目用 {前缀}-{字母}，字母序同 Excel 列（A–Z → AA–AZ → BA–…）。可在已有条目之间 插入 新 ID（大方向顺序，见 DSGN-J）。

ID immutable（MUST）： 某 ID 一旦写入 feature spec（表、标题、正文、外链），该字符串 终身固定 — 禁止 改字母、改前缀、拼写「修正」、重编号、把 PRD-A 合并进 PRD-B。禁止复用 已出现过的 ID（即使 entry 被 strike / 整段作废）。口径变了 → 新 ID + 旧处 strike / link（DSGN-J）；不得 改旧 ID 本身。

Type 前缀 例

decision-history ARD ARD-A, ARD-AA
impl-plan IMPL IMPL-A, IMPL-B
test-plan TST TST-A, TST-B

跨文档引用 写全 ID（如 PRD-A、ARD-F）。how-to 无强制 letter ID。

作用域（MUST）： ID 在 feature + type 内唯一；跨 feature 引用写 <feature>/<ID>（如 document-standard/PRD-K）。裸 ID 只在本 feature 内有意义。

改已有正文（MUST，spec-write 执行）： 不删旧句。旧句用 ~~删除线~~，新句写在旁边，并加 ref 说明为什么改（ARD-* 或链到该 decision）。

Concern Authoritative artifact

API contract OpenAPI / protobuf / GraphQL / JSON Schema 等
Database structure migrations / schema

design 篇 权威 intended behavior；code 权威当前实现与内部结构。Machine-readable contract 不要在 Markdown 里手抄全文 — link 或 generate。Tests 是 verification，不是 requirement 替身。final 后 maintain，不整篇 rewrite。

DSGN-H — Design 文档 Scope（type: design 正文）

写： behavior、contract、invariant、constraint、error、state transition、外部交互、架构边界（含 diagram 类）。
不写： class 结构、private method、framework 内部细节（见 DSGN-I trim 时也应 absent）。
测试句： 可改 implementation 而不改 externally observable behavior → 不应改 design 篇。

Agent 加载顺序： Global rules → Domain design → Architecture → Contract → Examples/tests → Code。窄问题却要整篇 design → re-cut boundary。

体量与 split：DSGN-B。篇内设计决策 / 小节锚点用 DSGN-A 等（DSGN-F）。

DSGN-I — Content Priority

Trim 顺序 L4 → L3 → 压 L2；L1 永不删。仍 > 硬 cap → DSGN-B split。

Level Trim
L1 behavior、contract、invariant、error、security、boundary、out of scope、assumption、compatibility、open question — never
L2 rationale — 压缩
L3 alternatives — 先删
L4 引用、raw output — 先删；重复 fact 只能是 link

DSGN-J — Decision History — 语义

文件角色： 决策 索引 + 正文（Decision Log / ### <ID> 小节，格式 DSGN-E）。不是 PRD / design 篇 的摘要。

书写顺序： 倒序 — 每加一条，写在 Decision Log 最上面（最新在上，越往下越早）。

Decision ID： 格式 ARD-{字母}（DSGN-F，分配后 不可改）。Log 表 / ### ARD-A — … 与 ID 一致。

推翻旧 decision： 旧 entry 不删行；正文 ~~删除线~~；旁 link 到新 ID（如 → [ARD-F](#ard-f--…)）。新口径用 新 ARD ID 写满一条，倒序 插 Log 顶。旧 entry 仅 strike + 指链（DSGN-I 不 trim 被 strike 字句）。

拆 part（超 DSGN-B 硬 cap）： ID 全 feature 唯一；新 entry 写入 当前 part Log 顶部；旧 part 保留；part 间 link 即可。

什么时候加一条（agent 写 spec 时）： 细则表见 parent HLD §5。简记：

加 不加
别人定下来的口径（review、结对、stakeholder），团队要能看到 仅在你脑子里、还没写进 design 篇、也 没动代码 的试探
你的转向会 改已有代码或对外契约（breaking behavior、路径/rename、谁才是 authority） 只在 design 篇 改几句就能说清的推敲；「想过又改主意」不必每条都 log
rename / 撞名等流程要求记入的（DSGN-K） agent 默认不 自动批量 append；不确定问 human

DSGN-K — Paths and Names — 冲突处置

新 feature / 新文件名 必须 对照已有名称；命中任一 collision signal 即视为冲突：

Signal 例
normalize 后相同 Payment vs payment
token 子集 auth vs auth-service
单复数 / 常见缩写 doc vs docs
edit distance ≤ 2 payment-api vs payments-api

处置：同一 bounded context → merge 再按 aspect split design。不同 context 易混 → rename 双方并记入 decision-history。同 feature 内文件撞名 → 拉开 aspect 或 rename feature。Rename = decision，更新 inbound link，禁止 silent。

DSGN-L — Enforcement Modes

Mode 行为
Organize feature/type → collision → 路径/文件名 → frontmatter + sections → Change Log → INDEX
Lint walk docs/features/；MUST 机械 fix；semantic report
Consolidate propose → 批准；decision 全保留；raw/ legacy cite 或删
Sync drift；按 DSGN-G authority；semantic conflict report
Review（spec-review） 同 Lint 的 detect（机械 MUST + semantic）；不 fix，输出带 severity 的修改建议

内容质量（设计是否成立）由 Review 的 semantic 部分处理，不属本 standard 的 MUST。

DSGN-M — Quality Gates

MUST： DSGN-A 全满足（含 DSGN-F ID 不可改、不可复用）；DSGN-G 冲突不 silent；DSGN-I 不删 L1；consolidation 不丢 decision；Commit = no 路径未 commit；INDEX 无 orphan/dead link；含 docs/features/ 变更的 push 时 INDEX/book 已与源同步；collision 已查。

NICE： heading 不跳级；link 有效；CONTEXT 术语一致；last_verified 新鲜；context boundary 合理。

Testing Decisions

验证见 parent ../../../test-plan/spec-driven-development-test-plan.md：被测对象是 spec-organize / spec-review，不是本篇；本篇全部 MUST / 禁止 由 TST-A 扫入 must_registry.yaml，机械项 Python 判、其余 LLM judge 判。

Out of Scope

  • Pipeline 阶段编排（见 pipeline spec）。
  • 存量 tree 一次性 migrate（incremental 合规即可）。
  • CI / skill 如何实现 enforcement（文件数、prompt、hook）。
  • 自动 drift detection 产品化。

Alternatives Considered

  • 单一 spec 类型装全部内容 → 拒:体积失控,无法按 concern 分篇(DSGN-B)。
  • 目录按 initiative 而非 feature 组织 → 拒:与 docs/features/ 既有树冲突。

Drawbacks

  • 类型与必填节偏多,小 feature 也要写全;靠 sub-feature 豁免(parent HLD §8)缓解。

Risks and Mitigations

Open Questions

  • sub-feature 的 raw/ 是否全工具支持(待 tooling)。

Reversibility

入口文件：document-standard-design.md。

Aspect design： DSGN-N（spec reader / human HTML 汇编）。PRD：PRD-A–P 见 ../prd/document-standard-prd-spec-reader-html.md。与 DSGN-B 路径、DSGN-I 优先级、DSGN-F ID 引用一致。Implementation： SPEC-HTML-STANDARD.md 与 SPEC-PRESENTATION.md。MD 是全文，HTML 是阅读视图。spec-write 改 md；spec-review 查保真（ARD-AJ）。

Problem Statement

  1. Feature spec 多篇、多层，人类难以一次读全。
  2. 「人类可读 HTML」若写成 短摘要，review 与 onboarding 会 漏 MUST，与 document-standard「L1 永不删」冲突。
  3. 先前 v0 指引（spec-pipeline SPEC-READER.md）写「summarize and rephrase」易被理解成 大幅删减 — 废止该解读；以本篇 DSGN-N 为准。

Solution

定义 Spec Reader HTML 产物：单文件、Tab 化、富排版、保真优先 的 derived view；canonical 永远是 committed .md。

Design

DSGN-N — Spec Reader HTML 契约

DSGN-N-A — 产物与路径

项 Rule
文件名 汇编为 <parent>/<parent>-reader.html；其余 HTML 与对应 .md 在 docs/features/ 下的相对路径相同，扩展名改为 .html
目录 docs/book/html/（ARD-BF）。Parent 与 sub-feature 都在这棵树里，不放在 docs/features/ 或 site/
Source of truth 各 Tab 对应的一篇或多篇 committed .md；HTML derived。手写稿须带 spec-source 与 sha256（ARD-AK）

DSGN-N-H — 单篇阅读视图

.md 是 source，HTML 是派生物。<!-- html-skip --> 可省略，不许包住 L1。已 strike 的句子留在 HTML；一个按钮切换「显示删除线」和「隐藏删除线」。生成稿带 spec-source-sha256；手写稿带 spec-paired=hand-maintained。hash 不一致则重新生成。手写 changelog 对 md Change Log 的每个日期都有一行（ARD-BA）。 | 参考 | docs/book/html/spec-driven-development/spec-driven-development-reader.html — 由 tools/build_sdd_reader.py 自 canonical .md 生成（DSGN-N-B，ARD-BF） |

DSGN-N-B — 保真（MUST — 回应「不要精简这么多」）

映射 DSGN-I 到 HTML 汇编：

Level 在 HTML 中
L1 全部呈现：MUST/禁止/必须、functional req 表 行、test case 行、impl task 条目、decision-history Log 行（含 ID）、contract 表 数据行、Out of Scope 列表、assumption、boundary、security、error — 禁止 用一段话代替整张表或整节
L2 保留事实；表述可改写为更短句子或 callout，不得 删掉 rationale 中的结论
L3 Alternatives 等 可压缩 为 bullet +「详见 canonical md」
L4 可省略正文，MUST footer/link 指向 md

条目 ID（DSGN-F）： HTML 中 MUST 保留可见 ID 字符串（PRD-A、DSGN-B、ARD-C、IMPL-C、TST-A 等 — 以 md 为准），便于与 review / registry 对齐。

禁止（MUST NOT）：

  • 仅保留「Problem / Solution 各一段」而删掉 Design 下各 DSGN-* 小节主体。
  • 用「见 md」代替 整 Tab（允许 节内 L3/L4 指向 md）。
  • Markdown 预览器模式：整页 <pre>、或未排版的 raw md 粘贴。

允许：

  • 把 md 表格 重排 为 HTML <table>（列可合并显示，行集合不得少）。
  • 把长 prose 分段、加 callout、加 mini flow（Mermaid 或 ASCII），不减少 L1 断言数量。
  • 同一 type 多 part 文件 → 同一 Tab 内 按 part 分 <section> 或子 Tab。

DSGN-N-C — 结构与 Tab

Page header（MUST）： 说明本页为 阅读用汇编；权威修改在 .md；列出 parent slug。

Tab 组 1 — Parent： 每存在一类 committed 文档一个 Tab：PRD | Design | Impl plan | Test plan | Decision history（how-to 可选 Tab）。

Tab 组 2+ — Children： 每个 docs/features/<parent>/features/<sub>/ 一组 Tab（或一组内 section per type）。至少 纳入 <sub> 的 design/<sub>-design.md 及 design part 文件。

每 Tab footer（MUST）： Canonical: + 相对 repo 路径；多 part 时 列出全部 part 路径。

DSGN-N-I — 全站目录（ARD-BG）

全项目一份网站，入口 docs/book/html/index.html。每一篇 spec HTML 是目录里的一条。目录先进入 feature。进入 feature 后，左侧是该 feature 的目录，右侧是正文。

DSGN-N-K — 正文链接

DSGN-N-L — 左侧五篇

DSGN-N-D — 视觉与 HTML 技术

  • SHOULD 复用 initiative 已有 CSS 模式（参考 spec-driven-development.html、document-standard.html：layout、chip、card、callout）。
  • SHOULD 单文件自包含 CSS（v0），便于 file:// 或静态托管。
  • MAY 内联 Mermaid（若 initiative 已有先例）；否则 ASCII flow。
  • MUST NOT 依赖运行时 fetch 加载 .md 作为主内容（可 fetch 仅作 debug，非交付形态）。
  • MUST 标题、节、小节、条目各用不同字号、字重和形态。段落序号不用 a–z，也不用 1、2、3。

DSGN-N-E — 流程与标准边界

角色 职责
spec-pipeline 阶段感知；用户要 reader 或 major spec 更新后 提示/触发；指示加载 SPEC-HTML-STANDARD
spec-html-standard skills/spec-html-standard/SPEC-HTML-STANDARD.md — DSGN-N 可执行摘要；无 SKILL.md
spec-write 只改 md 正文，不拥有 HTML 模板
spec-organize 路径、INDEX；不替代 reader 汇编

spec-pipeline SPEC-READER.md（若仍存在）： 仅 pointer 至本篇 + SPEC-HTML-STANDARD，避免双契约。

DSGN-N-F — 何时更新 reader

  • Parent 或 child 任一 committed spec 实质变更（尤其 L1/L2）后 SHOULD 更新 reader。
  • 用户显式：「生成 reader」「human html」「spec 汇编」「reader 太简了补全」。
  • 不必 每次 typo 级 commit 都 regenerate（NICE）。

DSGN-N-G — 未来 md→html

Document Standard — Spec Reader HTML（PRD）

本章目录
OverviewGoals and Success MetricsUser StoriesFunctional RequirementsNon-Functional RequirementsOut of ScopeResources NeededChange Log

Aspect PRD： 人类可读的 feature spec 汇编 HTML（parent + child，Tab 浏览）。权威契约见 sibling design 篇 ../design/document-standard-design-spec-reader-html.md（DSGN-N）。可执行摘要：skills/spec-html-standard/SPEC-HTML-STANDARD.md（非独立 skill）；spec-pipeline 触发时加载该标准。

Overview

Committed feature spec 以 .md 为 source of truth，但 parent initiative 往往 多篇、多层（parent 五类 + features/<sub>/）。人需要 一次打开、按 Tab 读完 的视图，且 不能 因为「好读」而丢掉 spec 里的 MUST、表格行、条目 ID 与 L1 事实。

现有示例 docs/features/spec-driven-development/spec-driven-development-reader.html 过度精简（大量章节被缩成几句），与「spec 可读」目标不符。本篇定义 要什么、不要什么；设计细则在 DSGN-N。

Goals and Success Metrics

ID Goal Success
PRD-A 高保真阅读 读者在 HTML 里能看到与 .md 等价的 L1 信息（MUST/禁止、表格主体行、前缀 ID 条目、Out of Scope、关键 diagram/流程）；不得 做成 executive summary
PRD-B 富 HTML，非 MD 预览 卡片、callout、表格、可选 flow；禁止 仅 fetch + <pre> 或整页粘贴 raw markdown
PRD-C Parent + child 覆盖 Parent：存在的五类 prd / design / impl-plan / test-plan / decision-history 各一 Tab（或等价分组）。Child：每个 features/<sub>/ 至少纳入其 design；若另有 committed type 则一并纳入
PRD-D 可追溯 每个 Tab（或 major section）底部 Canonical: <path-to.md>；页头声明：改 spec 先改 .md，再更新 HTML
PRD-E 位置与命名 输出 docs/book/html/<parent>/<parent>-reader.html。其余 spec HTML 按 docs/features/ 的相对路径放在 docs/book/html/ 下（ARD-BF）
PRD-F 可演进 v0 可手维；后续可有 md→html 机械契约 或工具；本篇 + DSGN-N 在自动化之前仍是 norm

User Stories

  • PRD-G — 作为 reviewer，我希望在 Tab 里看到 完整 MUST 表与 TST/IMPL 条目，以便不必来回开十个 md 也能审 spec。
  • PRD-H — 作为 feature owner，我希望 HTML 排版更好读（标题层级、表格、callout），但 不丢 design 里的 DSGN- / pipeline 的 PIPE-** 等锚点内容。
  • PRD-I — 作为 agent，我希望有 PRD + design + SPEC-HTML-STANDARD，而不是散落在 spec-pipeline 里一句「rewrite」。

Functional Requirements

ID Requirement
PRD-J HTML 汇编 MUST 遵循 DSGN-N 保真规则（对齐 DSGN-I：L1 不删；L2 可压缩表述不可删事实；L3/L4 可摘要但 MUST link 到 canonical md）
PRD-K MUST NOT 将整篇 design/prd 压成一段 overview；若某 Tab 因体量需 part 文件，HTML MUST 按 part 分 section 或子 Tab，仍保留各 part 的 L1
PRD-L 视觉语言 SHOULD 与 initiative 已有 summary HTML 一致（如 spec-driven-development.html、sub 的 document-standard.html：serif 标题、mono chip、soft callout）
PRD-M spec-pipeline 在 Converge/Downstream 后或用户要求时 SHOULD 触发 reader 更新；agent MUST 按 skills/spec-html-standard/SPEC-HTML-STANDARD.md 汇编（无 spec-reader skill）
PRD-N 发现 HTML 与 md 冲突或 HTML 暴露 spec 错误 → Detect → Ask human → 先修 md → 再 regenerate HTML（同 DSGN-G 精神）

Non-Functional Requirements

  • PRD-O — 单文件 HTML（v0）：无构建步骤也可双击打开；不依赖 MkDocs 服务。
  • PRD-P — 不含 secrets、不含 raw/ 机器-only eval 正文（可 link 到路径）。

Out of Scope

  • 替换 book 摘要或 MkDocs 导航。Reader HTML 放在 docs/book/html/（ARD-BF）。
  • 每次 git commit 自动 sync（v0 无 hook 要求）。
  • 用 reader HTML 作为 lint/oracle（oracle 仍是 SPEC-STANDARD.md 与 committed md）。

Resources Needed

  • 一个静态 HTML 构建脚本 + 一个本地静态服务器;无后端、无数据库。

Templates fetched 2026-11-05:

What each template requires

KEP (ordered): Release Signoff Checklist, Summary, Motivation (Goals, Non-Goals), Proposal (User Stories, Notes/Constraints/Caveats, Risks and Mitigations), Design Details (Test Plan, Graduation Criteria, Upgrade/Downgrade Strategy, Version Skew Strategy), Production Readiness Review Questionnaire, Implementation History, Drawbacks, Alternatives, Infrastructure Needed.

Rust RFC: Summary, Motivation, Guide-level explanation, Reference-level explanation, Drawbacks, Rationale and alternatives, Prior art, Unresolved questions, Future possibilities.

Ours (SPEC-STANDARD.md, required headings):

Type Required

design Problem Statement, Solution, User Stories, Implementation Decisions, Design, Testing Decisions, Out of Scope, Further Notes
impl-plan Global Constraints
test-plan Test Cases, Test Execution Order, Expected Pass Threshold
decision-history Decision Log, Evidence Appendix

Gap matrix

Concept KEP Rust RFC Ours Assessment
Goals / Non-goals ### Goals, ### Non-Goals Motivation Out of Scope (prd, design) covered, but only as one-sided "out of scope"

Proposals (ranked)

P1 — design: promote Alternatives Considered to required

  • Why: the generated gold runs record what was chosen, never what was rejected. Both reference templates make this mandatory; we leave it at L3 optional.
  • Change: design required += Alternatives Considered.
  • Cost: SPEC-STANDARD.md table row, checks/sections.py one tuple entry, regenerate 3 gold runs, re-run both judges.

P2 — design: add Risks and Mitigations

  • Why: KEP requires Risks and Mitigations; our designs state behavior but not what can break. Directly improves decision quality for non-software cases too.
  • Change: design required += Risks and Mitigations.
  • Cost: same as P1.

P3 — decision-history: make open questions explicit

  • Why: ARD-AG already requires a structured blocking flag on open decisions, but no section forces them to be listed. Rust RFC has Unresolved questions.
  • Change: add ## Open Questions to decision-history required, table | ID | Question | Blocking | Owner |.
  • Cost: standard + checker + regenerated runs. Lower value than P1/P2.

Explicitly rejected

  • Graduation Criteria, Upgrade/Downgrade Strategy, Version Skew, Production Readiness Questionnaire, Scalability.
  • Reason: cluster/runtime-shaped. Adopting them would break PRD-Q (the same procedure must carry shed / Beijing trip / math problem / stock analysis).

Impact if P1+P2 are adopted

  1. sections.py — design required tuple gains two entries.
  2. SPEC-STANDARD.md — required-sections table gains one row of text.
  3. Gold runs — current three runs lack both sections and would drop to score 1 = 4/6. They must be regenerated with the updated standard.
  4. Judges — corpus hash changes; MUST + annotations verdicts must be re-run.
  5. Annotations — unaffected; no annotation asserts these sections.

Effort: 3 generation runs (~5 min) + one judge cycle (~4 min) + checker edit.

Recommendation

Adopt P1 only now; evaluate P2 after one exemplar is accepted, so the change set stays reviewable. P3 is worth doing only if open questions actually appear in the shed / Beijing-trip cases.
